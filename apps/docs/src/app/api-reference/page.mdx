# Overview and authentication

The public Inframeld API uses JSON over HTTP. Remote installations use their operator-supplied HTTPS backend URL. The reference below reads the committed native OpenAPI 3.1 contract directly.

## Authentication

The health and resource-metadata discovery operations are public within their configured availability. Protected operations require one supported credential family and current scope/action authority. Authentication identifies the actor, while the operation checks what that actor may do now.

For human bearer requests, use an actual Inframeld human access token accepted by that installation. Set `INFRAMELD_TOKEN` through your local secret-handling procedure. The browser account site maintains a Kratos session cookie. Browser writes also follow the installation's CSRF/Origin contract. SDK construction does not sign you in or create a credential.

Application credentials identify their own account and bound Project. [Application authentication](/guides/authenticate-an-application) explains complete-key verification, exact trusted bindings, current local eligibility and the separate application-session contract. The human session check rejects application keys, and the application identity check rejects human credentials. Ordinary product operations can authenticate a verified application and still deny human-only administration with `403`.

Malformed or competing credential families fail before verification. Invalid, expired, revoked or incorrectly bound application credentials receive `401`; verified local ineligibility receives `403`; required verification uncertainty receives `503`. No application-key failure falls back to Hydra or a human account. A successful identity response is not a permission snapshot.

This preview has no supported public application-key issuance procedure or complete saved CLI-login procedure. Issuance's mapping to trusted profiles remains unresolved. Use the access path actually supported by the selected installation and client, without constructing credentials. Start with [health](/clients/http#make-your-first-request) when no protected credential is available.

## Requests and responses

Use the exact method, canonical route and input names for the operation. Send `Content-Type: application/json` for JSON request bodies. Required idempotency headers and expected revisions protect the specific reviewed write.

An omitted field and an explicit `null` can have different meanings. [Model schemas](/api-reference/models) retain those distinctions. Response wrappers also differ between SDKs while preserving the same HTTP operation and typed body.

## Errors and uncertain effects

See [operations and errors](/api-reference/operations#errors-and-uncertain-effects). A network/decode failure or an `unresolved` observation does not prove a prior write failed. Retain its original identity and recovery context.
