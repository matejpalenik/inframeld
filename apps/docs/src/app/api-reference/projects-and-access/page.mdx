# Projects and access

These operations use current identity and authority. [Authentication](/api-reference#authentication) establishes the credential context. [Projects and permissions](/product/projects-and-permissions) explains the resource model.

## Inspect your session

<ApiOperation operationId="getCurrentSession" />

Read the current principal context with a valid human credential. [HTTP and cURL](/clients/http#call-protected-operations) shows a complete request. Each SDK exposes this operation through its generated client.

## Read your Organization access

<ApiOperation operationId="getMyOrganizationAccess" />

Read the actual admitted human's own Organization ID, principal ID, current Access revision and stored Organization grants. An eligible human without Organization grants receives `grants: []`. There is no principal selector, installation inventory or permission snapshot for a later action. [Create an additional Project](/guides/create-project#read-your-organization-access) explains how to use this read before creation.

## Admit an existing human

<ApiOperation operationId="admitHuman" />

Require a currently eligible human with permission to use Organization `admit-users`, the reviewed Organization Access revision and one retained idempotency key. `identityId` identifies Bob's existing Kratos identity, not a local principal or an email address. [Admit an existing human](/guides/admit-human) shows the existing browser-session producers and generated TypeScript call.

A fresh `201` returns `changed: true` and advances the Organization Access revision once. A fresh `200` returns `changed: false` for an already-admitted human without changing admission, credentials or that revision. Neither result grants Project membership, action permissions or starters. The response's `principalId` is the local Inframeld identity.

Exact business replay requires Alice's current authority and Bob's current admissibility. It returns the original status, result and `idempotencyExpiresAt`, without reinitializing credentials, restoring rights or repeating provisioning or audit. Generic original-request metadata lookup has its own disclosure contract. [Keep the original request after uncertainty](/guides/admit-human#keep-the-original-request-after-uncertainty) explains recovery and relevant failures.

## Create an additional Project

<ApiOperation operationId="createProject" />

Require current human `create-projects` authority on the requested Organization, the reviewed Organization Access revision and one retained idempotency key. Save the Project, creator membership, eighteen explicit creator grants, audit and original result together. Creation leaves the Organization Access revision unchanged. The new Project starts at Access revision `1` and metadata revision `0`.

The creation receipt's `initialGrants` describes the original assignments. Exact replay requires current authorization and returns that original result without restoring removed grants or reversing later renames. [The guide](/guides/create-project) covers the saved request, generated clients, current metadata and uncertain-result recovery. This operation creates no starter or RAG resources.

## Create an application account

<ApiOperation operationId="createApplicationAccount" />

Require a currently eligible human Project member with permission to use `create-application-accounts`, a reviewed Project Access revision and one retained idempotency key. Supply the exact `name`, `displayName` and `expectedAccessRevision`. Creation atomically saves the application identity, its one-Project binding and membership, three creator administration grants, audit and original result.

HTTP `201` returns one permanent `principalId`, also used as the application account ID, plus its original names, Project Access revision and three `initialGrants`. Those use-and-grant assignments belong to the human creator for Issue keys, Revoke keys and Delete account on this exact account. The application starts with no received actions, groups or keys. It inherits no human permissions and cannot move Projects.

Exact completed replay checks current creation authority and returns the same original `201`, account and receipt. It neither restores removed grants nor creates another account. [Create and inspect an application account](/guides/application-accounts) explains preparation, saved requests, generated clients and uncertain-result recovery. Key issuance, authentication, revocation and retirement remain separate unfinished operations.

## Read application-account metadata

<ApiOperation operationId="getApplicationAccount" />

Read one account by its permanent application principal ID. Require a currently eligible human Project member with permission to use at least one exact account action: `issue-application-keys`, `revoke-application-keys` or `delete-application-account`. Permission to create accounts does not expose a Project-wide account inventory.

The response contains safe account identity, naming, lifecycle metadata and the current Project Access revision. It supplies no grants, groups, key material or authority to issue or revoke a credential. [The guide](/guides/application-accounts#inspect-the-account-by-id-or-exact-name) explains ID and Name inspection.

## Resolve an exact application-account Name

<ApiOperation operationId="resolveApplicationAccount" />

Use `GET /v1/projects/{project_id}/application-accounts/resolve?name=...` with one exact Name and the same current account-metadata authority. The result uses `ApplicationAccountMetadataResponse`, identifying the actual Project and application principal. There is no display-name search, fuzzy match, normalization or broad account listing. Missing and hidden accounts retain the safe `404` disclosure boundary.

## Read application key metadata

<ApiOperation operationId="listApplicationKeys" />

Require a currently eligible human Project member with exact permission to use Issue keys or Revoke keys on this account. Delete account alone is insufficient. Metadata reads do not require the additional delegation and group-management authority used by the separate issuance contract.

The bounded page has only safe key metadata in `items` and a nullable `nextCursor`. It uses key-UUID order and `limit` from 1 to 100, default 25. Pass each returned cursor unchanged within the same scope. Every page checks current authority. A cursor is neither a snapshot nor a permission token, and denial is not an empty list.

<ApiOperation operationId="getApplicationKey" />

Read a specific retained key by its ID with the same exact Issue-or-Revoke authority. It returns the same safe item shape, without a secret or verifier. Neither read issues a key, authenticates it or changes its state. These GETs take no body, expected revision or idempotency key. [Inspect safe key metadata](/guides/application-accounts#inspect-safe-key-metadata) explains empty new accounts and continuation.

## Create an access group

<ApiOperation operationId="createAccessGroup" />

Require a currently eligible human Project member with permission to use `create-access-groups`, a reviewed Project Access revision and one retained idempotency key. The strict body supplies `name`, `displayName` and `expectedAccessRevision`. A fresh `201` creates the group with the creator's ordinary membership and management, advances Project Access revision once and saves the original receipt. It makes no separate document-action assignment.

`AccessGroupCreationResponse` identifies the Project, group, creator and original names, revision, operation and result expiry. It has no `initialGrants` inventory. [Manage access groups](/guides/manage-access-groups) explains setup, creation and current relationship reads.

## Read access-group members and managers

<ApiOperation operationId="listAccessGroupMembers" />

<ApiOperation operationId="listAccessGroupManagers" />

Both lists require a currently eligible human Project member who currently manages this exact group. Ordinary membership or management of another group is insufficient. `AccessGroupPrincipalsPageResponse` identifies the Project, group and current Access revision, with safe principal ID/display name/kind items and required nullable `nextCursor`.

Read in principal-UUID order with default limit 25 and range 1–100. Pass each cursor unchanged to its original member or manager list. Every page checks current authority. ## Add an access-group member

<ApiOperation operationId="addAccessGroupMember" />

Require current human management of this group, a retained idempotency key and an `AccessGroupMembershipRequest` containing only the reviewed Project `expectedAccessRevision`. The recipient must be an eligible admitted current Project human or application member. A new membership returns `201` with `member: true` and `changed: true`. An already-present eligible membership returns `200` with `changed: false`.

The original receipt describes that assignment, not membership after a later removal. Applications receive ordinary membership, never management. [Add an ordinary member](/guides/manage-access-groups#add-an-ordinary-member) explains inputs and replay.

## Remove an access-group member

<ApiOperation operationId="removeAccessGroupMember" />

Require the same current manager authority and original-key handling. DELETE takes one required canonical `expectedAccessRevision` query integer and no body. Removal also removes the recipient's management, preserving another eligible human manager when required. A fresh `200` reports `removed: true` and `changed`; an already-absent relationship is unchanged. Rejoining restores only ordinary membership.

Exact currently authorized replay returns the original receipt without removing a later rejoin or restoring an earlier relationship. [Membership removal and rejoin](/guides/manage-access-groups#remove-membership-and-rejoin-deliberately) explain the distinction.

## Appoint an access-group manager

<ApiOperation operationId="appointAccessGroupManager" />

Require current human management, one retained key and an `AccessGroupManagerRequest` containing the reviewed Project Access revision. Only eligible current Project humans may manage. Appointment saves any missing ordinary membership together with management, preserving existing membership. This includes access through the group to current and future shared documents.

A changed appointment returns `201` with `manager: true` and `changed: true`. An already-present eligible manager returns `200` with `changed: false`. These results make no separate document-action assignment. [Appointment and demotion](/guides/manage-access-groups#appoint-or-demote-a-manager) explain the reader-visible effects.

## Remove access-group management

<ApiOperation operationId="removeAccessGroupManager" />

DELETE takes the reviewed revision in its query, no body and one original idempotency key. Current management is required. The last eligible human manager cannot leave through ordinary demotion without a replacement. A fresh `200` reports `removed: true` and `changed`, leaving ordinary membership intact. An already-absent management assignment is unchanged.

All relationship changes save actual effects, Project revision, audit and original result together. Changed writes advance revision once. Fresh no-ops do not. Current authority precedes original replay, which never reapplies its historical effect.

## Delete an unused access group

<ApiOperation operationId="deleteAccessGroup" />

Require current human management, the reviewed Project Access revision as a query value, no body and the original idempotency key. Deletion rejects protected stored references without partial cleanup. Replace a reference through its owning authorized workflow first. An unused group and its owned relationships are removed together, returning synchronous `200` with `removed: true` and the original mutation fields. There is no cleanup job or application-shutdown stage.

Ordinary repeated DELETE and full receipt replay retain current-manager authorization. After deletion, the currently eligible original human may use the exact saved deletion identity or original operation ID for only content-free retained status. That path is independent of expired ordinary idempotency history and preserves the captured status expiry without renewal. [Group deletion recovery](/guides/manage-access-groups#recover-an-uncertain-change) and [status interpretation](/guides/read-deletion-status#read-status-for-a-deleted-access-group) explain these separate results.

Group responses and problems use `Cache-Control: no-store`. Fresh stale review, unsafe handover, unavailable Name and protected-reference conflicts return `409`. Current denial is `403`, hidden/missing scope is `404`, and malformed fields, query framing or body content use the existing `422` contract. POST/PUT accept one JSON object of at most 32 KiB with `Content-Type: application/json`, retaining `413`/`415` bounds. Cookie writes require the installation's Origin and CSRF safeguards.

<ApiOperation operationId="listProjectMembers" />

Request one page with default `limit: 25`, range 1–100, and an optional unchanged `cursor`. The response reports the current Project `accessRevision`, safe stored-member items and a nullable `nextCursor`. Inactive stored memberships remain in the list. There are no emails, grants or totals. Every page checks current authority and scope. A cursor is not a snapshot or permission token, and a denied read is not an empty result. No body or idempotency key applies to this GET.

## Add a Project member

<ApiOperation operationId="addProjectMember" />

Require a currently eligible human Project member with permission to use `manage-project-members`, one retained idempotency key and the reviewed Project Access revision. The recipient must be an eligible admitted human in the same Organization. The `ProjectMembershipRequest` JSON body contains `expectedAccessRevision`.

A fresh `201` creates bare membership and advances the Project Access revision once. A fresh `200` reports existing membership without that advance. ## Remove a Project member

<ApiOperation operationId="removeProjectMember" />

Require the same current human Project authority and a retained idempotency key. DELETE accepts one `expectedAccessRevision` query value and no body. The exact human recipient may be inactive. Departure preserves the required eligible human grantors and group managers or conflicts atomically.

A fresh `200` reports `removed: true` and whether membership changed. Actual removal clears only that recipient's membership and received Project/group/application-account action grants and group relationships within the Project, advancing its Access revision once. It preserves Project-owned resources, other Projects and grants issued to other people. Rejoin restores only membership.

Exact replay requires the actor's current authority and returns the original status, receipt and expiry without repeating removal or restoring access. [Departure checks and recovery](/guides/manage-project-members#check-responsibility-before-departure) explain the guards, self-departure and uncertain outcomes.

## Read your own Project access

<ApiOperation operationId="getMyProjectAccess" />

`GET /v1/projects/{project_id}/my-access` requires a currently eligible human member of the Project, without a separate action or membership-management grant. It accepts ordinary `limit`/`cursor` and no body or principal selector. `MyProjectAccessResponse` identifies the actual Project/principal and current `accessRevision`, plus stored `grants`, `groupMemberships`, `groupManagements` and required nullable `nextCursor`.

One combined page has at most `limit` entries across the three arrays, default 25 and maximum 100. Grants carry a typed exact Project/access-group/application-account target, `actionId` and `canGrant`. Group relationships carry only `accessGroupId`. Each page checks current authority and revision, with a principal/scope-bound cursor. It supplies no implied grants, hidden linked resources or permission snapshot. [The guide](/guides/assign-project-grant#read-your-project-access-and-current-revision) explains revision review.

## Set a Project action grant

<ApiOperation operationId="setProjectActionGrant" />

`PUT /v1/projects/{project_id}/grants/{recipient_principal_id}/{action_id}` supports the eighteen Project actions. Require a current eligible human member with exact use-and-grant authority, one retained idempotency key and a `ProjectActionGrantRequest` body containing only strict `canGrant` and reviewed `expectedAccessRevision`. A fresh recipient must be eligible for that action. Applications can receive only eligible use-only assignments.

New assignments return `201`. Existing assignments return `200`, including unchanged assignments. Changed writes advance Access revision once, while fresh no-ops do not. The original HTTP status and `ProjectActionGrantResponse` preserve the revision, expiry, exact recipient/action, requested level and `changed`. A downgrade must preserve another eligible coherently linked human member able to grant that same Project action. [The task](/guides/assign-project-grant#set-one-project-assignment) distinguishes use-only from removal.

## Remove a Project action grant

<ApiOperation operationId="removeProjectActionGrant" />

`DELETE /v1/projects/{project_id}/grants/{recipient_principal_id}/{action_id}` requires the same current human authority and original-key handling. It takes one canonical `expectedAccessRevision` query value and no body. It can clean an inactive or recovery-blocked recipient after scope checks, preserving the last-grantor guard.

A `200` `ProjectActionGrantRemovalResponse` records original `removed: true` and `changed`, whether removal changed the assignment or it was already absent. An unchanged result does not advance Access revision. Current actor authority precedes immutable original replay, before fresh-recipient/revision/handover checks. Replay neither restores a removed assignment nor removes a later one. [Recovery guidance](/guides/assign-project-grant#handle-a-stale-revision-or-lost-result) explains historical receipts and current reads. All three operations are no-store. Fresh-recipient/state conflicts are `409`, actor denial is `403`, and unsupported action/recipient/delegation combinations or malformed inputs are `422`. Existing credential/scope/dependency failures and PUT `413`/`415` bounds remain.

## Assign a use-only grant

<ApiOperation operationId="assignProjectUseOnlyGrant" />

This operation assigns the delivered use-only `create-access-groups` action to the specified recipient. Supply the reviewed Project Access revision and a retained idempotency key. A grant does not bypass membership or the actor's current ability to grant that action.

The request body's generated model is `ProjectUseOnlyGrantRequest`. [The compatible POST section](/guides/assign-project-grant#assign-the-permission) shows equivalent cURL, Python, TypeScript and Rust programs. The explicit Project PUT/DELETE operations retain separate meanings and original requests. Preserve the original request context before dispatch so [lookup](/guides/recover-original-request) can observe an uncertain result.

## Decide account-site consent

<ApiOperation operationId="decideHumanOAuthConsent" />

The browser write requires its current session and CSRF/Origin safeguards. The backend rechecks the request rather than trusting an earlier inspection. Use the [account site](/get-started/connect#review-a-consent-request) for an interactive decision. Keep the challenge and returned flow URLs private. A navigation-level consent result and complete Rust recipient-proof acquisition require distinct evidence.
