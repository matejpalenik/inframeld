# HTTP and cURL

Use your installation's backend URL to call its public HTTP API. An unauthenticated health request is a useful first check.

## Make your first request

Set the backend URL in your terminal. This local example matches the [development installation](/get-started/install-inframeld):

<CodeGroup>

```shell
export INFRAMELD_URL='http://127.0.0.1:8000'
curl --fail-with-body --silent --show-error --max-time 5 \
  "$INFRAMELD_URL/health"
```

</CodeGroup>

A successful response includes `"status": "ok"`. Remote installations use their operator-supplied HTTPS URL.

## Call protected operations

Follow [authentication](/api-reference#authentication) to obtain the credential supported by your installation. Protected examples use `INFRAMELD_TOKEN` for a current human bearer token. Keep it in your local secret-handling environment rather than source files or shared output.

This request supplies its header through stdin so the token is not expanded into curl's argument list:

<CodeGroup>

```shell
curl --fail-with-body --silent --show-error --max-time 5 \
  --header @- "$INFRAMELD_URL/v1/session" <<EOF
Authorization: Bearer ${INFRAMELD_TOKEN}
Accept: application/json
EOF
```

</CodeGroup>

The session response returns `principalId`, identifying the current human principal. A failed response remains a failure even when it contains useful diagnostic information. Avoid tracing commands that would reveal credentials.

## Use an application credential

An application key identifies a separate Project-bound account. [Check an application's identity](/guides/authenticate-an-application) explains the application-session contract, current credential/account checks and its availability. The human `/v1/session` example above remains human-only.

Use a complete compatible credential from its actual supported issuer through the documented Authorization bearer header. A public prefix or key ID is insufficient. [Authorized issuance](/guides/application-accounts#issue-a-key) supplies the full key only on first delivery. Account creation, metadata reads and original replay cannot retrieve it. Issuance pins each selected adapter to its configured trusted profile; a successful request through one adapter does not prove usability through another. The browser issuer integration uses its own human cookie. Keep that context separate from subsequent application-key requests.

Keep the credential outside argv, URLs, request bodies, browser distribution and logs. Send one supported family per request. Invalid application credentials remain on the application path without Hydra verification or a fallback to a human. Verification and current local denial have different failure outcomes, as [the component guide](/guides/authenticate-an-application#understand-a-rejected-or-unconfirmed-check) explains.

[Revoke a key](/guides/application-accounts#revoke-one-application-key) through a separate currently authorized human context. Revocation disables that parent key across its allowed adapters and may remove the last usable key. New credential checks reject it. The revocation receipt does not cancel already admitted work or retrieve the secret, and an uncertain response calls for exact original-request recovery rather than automatic replacement.
