# Register and select a target

Save your development installation as `dev` so you can refer to it by a short local label. A target records an installation connection. Registering or selecting one does not sign you in, select a Project or grant access.

## Before you begin

Use an `inframeld` executable that includes `target add`, `target use`, `target show` and their preference change views, available on your shell's `PATH`. The [CLI README](https://github.com/matejpalenik/inframeld/blob/main/apps/cli/README.md#build-and-check-from-source) explains source builds and [archive installation](https://github.com/matejpalenik/inframeld/blob/main/apps/cli/README.md#install-and-remove-a-packaged-executable). An older executable may reject these commands. This guide does not establish a published release or additional platform support.

Ask the installation operator for its exact public HTTPS API URL. The installation must already publish compatible discovery metadata and have its official OAuth client configured. Use that API identity, including any path or trailing slash, rather than an account page, arbitrary API route or private administration address. The example `https://api.dev.example.com` must be replaced with your operator's value.

Run these commands in your terminal from any working directory. Registration needs network access to the installation and its advertised identity provider, plus a writable local configuration directory. You need no account, token or administrator credential. HTTP API URLs, including manually entered loopback HTTP URLs, are unsupported by these commands.

## Register the connection

Choose a label of 1–64 ASCII letters, digits, dots, underscores or hyphens, starting with a letter or digit. Labels are case-sensitive, so `dev` and `Dev` are different names.

Choose the necessary trust inputs before the first registration. With certificates trusted by the system, run:

<CodeGroup>

```shell
inframeld target add dev --url https://api.dev.example.com
```

</CodeGroup>

If your operator supplies a private certificate authority, use this alternative instead. Replace the URL and certificate path with the supplied values:

<CodeGroup>

```shell
inframeld target add dev --url https://api.dev.example.com \
  --ca-cert /absolute/path/to/installation-ca.pem
```

</CodeGroup>

`--ca-cert` accepts a public PEM certificate bundle, not a private key. You can repeat it for up to eight files, each at most 256 KiB. The CLI saves absolute file references, without copying their contents or pinning their hashes. Keep those operator-managed files available. Their contents are read once for a network attempt, and changes affect the next attempt.

If your installation requires a proxy, add `--proxy http://proxy.example.com:8080` with the operator's actual proxy origin. Only explicit credential-free HTTP(S) origins are supported, without user information, a query or fragment. Inherited proxy environment variables are not adopted. Certificate and hostname verification remain enabled.

The command reads public API and identity-provider metadata without credentials. It checks their identity and supported protocol before saving the installation ID, API URL, issuer, official client and chosen transport settings. A successful registration exits `0` and reports the target, registration result, API and installation ID. It does not change your selected target.

After successful discovery, repeating an identical registration reports that it is already registered. The same label cannot silently replace a different identity or transport configuration. Choose a new label for a different connection.

## Inspect and select the target

Inspect the new connection explicitly, before making it your default:

<CodeGroup>

```shell
inframeld target show --target dev
```

</CodeGroup>

This reads the saved binding without contacting the server. Its API, issuer and installation ID are cached registration facts. They do not establish current reachability, TLS validity, compatibility, sign-in or permission.

Preview the saved-preference change first:

<CodeGroup>

```shell
inframeld target use dev --dry-run
```

</CodeGroup>

**Current / Proposed** compares the currently saved preference with `dev`. It does not save or reserve that change. A displayed `not selected` means the registry currently has no saved preference. A proposal equal to the current value is marked `unchanged` and remains a preview.

Add `--json` for structured observations. This is an illustrative `data.changes` entry for proposing `dev` when no preference is saved, not a captured result:

<CodeGroup>

```json
{
  "kind": "proposed",
  "resource": { "kind": "targetPreference" },
  "fields": [
    {
      "field": "savedTarget",
      "before": { "known": true, "value": null },
      "after": { "known": true, "value": "dev" }
    }
  ]
}
```

</CodeGroup>

Here `known: true` with `value: null` means an observed unset preference. It does not mean an unknown value. The preview's `effectiveTarget` and `source` describe the current selection, not the proposed preference.

Save `dev` as your local preference, then inspect the effective choice:

<CodeGroup>

```shell
inframeld target use dev
inframeld target show
```

</CodeGroup>

`use` works offline and changes only the saved target preference. It does not refresh credentials or edit shell variables. An unknown label fails without selecting another target.

A confirmed changed save displays **Before / Now**. Its old and new preferences come from the same locked update, so the old value can differ from an earlier preview if another process changed it. Structured output uses `kind: "confirmed"` in `data.changes`. Repeating an already saved choice reports `saveStatus: "unchanged"`, an empty `changes` array and neutral `Preference unchanged.` text, without a Before/Now change.

For `show`, the first applicable selector wins:

| Selector           | Effect                                                            |
| ------------------ | ----------------------------------------------------------------- |
| `--target dev`     | Uses that registered target for this invocation only.             |
| `INFRAMELD_TARGET` | Uses the label named by the current environment. It is not a URL. |
| Saved preference   | Used when neither override is present.                            |

An invalid or unknown effective selector is an error, not permission to fall back. A valid explicit flag ignores lower-priority environment values. `add` and `use` take their label as a positional argument and reject a competing `--target` flag.

If `INFRAMELD_TARGET` is set, `use` still saves your requested preference but warns that this shell continues to use the environment value. If that value cannot resolve, the effective target remains unresolved. Unset the variable yourself or inspect with an explicit `--target` override. The CLI never changes your shell configuration.

## Use structured output or preview a change

For a structured cached inspection, run:

<CodeGroup>

```shell
inframeld target show --target dev --json --no-input
```

</CodeGroup>

Check the process status and final `outcome`. Successful inspection has `data.verification: "savedBinding"`, and `data.source` identifies `flag`, `environment` or `saved`. Registration instead reports `discoveryValidated`, describing that registration attempt. Warnings remain separate from success and may also appear on stderr.

Choose `--jsonl` instead of `--json` for one final result record. These target commands emit no progress records. Help remains plain text. The [CLI output guide](/guides/inspect-cli-version#choose-a-final-jsonl-record) explains the shared final-record wrapper. `--plain` and `--no-color` affect presentation, while `--no-input` prevents interaction. These commands do not prompt or launch a browser.

Preview registration without contacting the server or saving a target:

<CodeGroup>

```shell
inframeld target add dev --url https://api.dev.example.com --dry-run --json
```

</CodeGroup>

Dry-run validates arguments and transport inputs and reads the local registry. If CA files were supplied, it reads and validates them too. Its plan describes intended effects. It does not validate remote metadata or prove that executing registration will succeed. Dry-run for `use` or `show` also reads local state and performs no network call or preference write.

Registration preview lists `publicApiIdentity` and `httpRequestMetadata` as intended outgoing network categories. These describe execution, not data sent by preview. Its destinations include the local registry and supplied API identity. Issuer-metadata and signing-key-set destinations remain unknown until discovery. An explicit proxy appears as an additional known destination. Unknown destinations have `known: false` and no `value`, rather than a guessed issuer URL.

Preference and inspection previews list no outgoing network data and only the local registry as a destination. Plans retain `remoteVerification: "notPerformed"` and identify unresolved facts such as an unperformed save or unverified remote health. They expose no credential or CA contents. An unresolved environment override is reported separately from a proposed saved preference.

## Recover from a failure

| Result                                                         | Next step                                                                                                                                                                         |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `discovery_tls` or `invalid_ca_file`                           | Check the operator's URL and public certificate bundle. Keep TLS verification enabled.                                                                                            |
| Discovery unavailable, unsupported or identity mismatch        | Confirm the exact API identity and provider configuration with the operator. Do not substitute an issuer from an error or treat this as a password failure.                       |
| `target_binding_conflict`                                      | Keep the existing binding. Use a different local label for the different connection.                                                                                              |
| `target_not_found`                                             | Check the label and selection source. Register the intended target explicitly.                                                                                                    |
| `target_state_busy`                                            | Another local update holds the registry lock. Retry after it finishes.                                                                                                            |
| `invalid_target_state` or `target_state_io`                    | Preserve the configuration and inspect its path and permissions. Do not delete other targets to repair this invocation.                                                           |
| `target_write_uncertain`, interruption or missing final output | The local change may already exist. Read back the registration or preference as described below before deciding whether to repeat a save. Missing output does not prove rollback. |

For uncertain registration, `inframeld target show --target dev` checks the registered `dev` binding. For uncertain preference changes, inspect without `--target` and with `INFRAMELD_TARGET` unset. Keep the same local configuration directory as the original command. This subshell leaves your surrounding shell's selector unchanged:

<CodeGroup>

```shell
(
  unset INFRAMELD_TARGET
  inframeld target show --json
)
```

</CodeGroup>

Readback observes the registry's current contents. Another process may have changed them. It does not prove how the earlier save finished or that its disk persistence completed. If readback fails, retain the uncertainty and investigate its safe error.

An unconfirmed preference save reports `saveStatus: "unconfirmed"`, null `savedTarget`/`effectiveTarget` values and no completed change record. Those nulls do not establish that no preference exists. An interrupted result can retain an already confirmed Before/Now change while still reporting interruption. Incomplete output can omit that evidence entirely. Check saved state before deciding what to do next.

Local state lives under `$XDG_CONFIG_HOME/inframeld`, or `$HOME/.config/inframeld` when `XDG_CONFIG_HOME` is unset. Registration and selection leave that intended local state in place. They create no installation resources, accounts or credentials.
