# Manage access-group members and managers

Create SupportKnowledge in your Support Project, add Bob as a member and appoint him as a manager when he should share responsibility for the group. A manager is always an ordinary member of that same group. Managing another group gives no authority over SupportKnowledge.

Ordinary membership is the audience relationship used to authorize access to documents shared with the group. Management additionally permits membership and manager administration. Appointing Bob therefore includes access through the group to **current and future documents shared with it**. Querying or building still requires the relevant action permissions.

## Prepare the Project and people

You need an existing Project, its permanent ID and a current human credential accepted by the installation. To create a group, you must be an eligible admitted human Project member with permission to use `create-access-groups`. Either grant level permits creation. Later administration requires current management of the particular group.

Use the `projectId` from Project creation or an authorized [exact-Name resolution](/guides/name-and-rename-project#resolve-the-name-and-keep-the-id). [Read your own Project access](/guides/assign-project-grant#read-your-project-access-and-current-revision) to review the required creation permission and current Project `accessRevision`. The server checks current authority again when saving each change.

Set up the installation URL and an existing human bearer token through [HTTP setup](/clients/http#call-protected-operations). Browser sign-in alone does not put a bearer token in your terminal. Use the local source-package setup for a [Python](/clients/python), [TypeScript](/clients/typescript) or [Rust](/clients/rust) alternative. Group administration has no delivered CLI command in this preview.

Prepare Bob and Carol as eligible admitted humans who already belong to the Project. [Human admission](/guides/admit-human) and [Project membership](/guides/manage-project-members) are separate operations. Use the returned human `principalId`, or an ID supplied by an authorized [Project-member read](/guides/list-project-members). A group manager cannot admit a person or create their Project membership through a group change.

An application account such as SupportBot may be an ordinary group member. Use the stable `principalId` returned by [application-account creation](/guides/application-accounts). Giving the account group membership needs no application key. An application cannot be a manager.

The supported account-to-client setup, complete engineering walkthrough and human acceptance for this task remain unfinished in [qualification #354](https://github.com/matejpalenik/inframeld/issues/354). That qualification also retains the later real default-reference case. This guide does not establish document-ingestion, query or application-authentication qualification.

For an exercise, choose positively identified disposable resources and agree on supported cleanup before starting. An unused group has its own deletion path. Application-account retirement remains separate, so an exercise that creates SupportBot may need a wholly disposable installation and its operator-supported teardown.

## Create SupportKnowledge

Choose an explicit Name and display name. Keep the returned permanent group ID for later requests. An exact Name selects the group within its Project. A display name is a label and does not establish identity or permission.

This example uses Name `support-knowledge` and display name `SupportKnowledge`. Names have 1–63 lowercase ASCII letters, digits or hyphens, start with a letter and end with a letter or digit. They are unique among groups in this Project, including groups you cannot inspect. Retired Names remain reserved. A collision requires another explicit choice rather than a silently added suffix.

New submitted display names are non-unique labels of 1–128 Unicode code points. They must be nonblank, have no surrounding whitespace and contain no controls, surrogates or line/paragraph separators. Reads preserve retained legacy labels instead of treating them as new input. Exact-Name resolution does not trim, lowercase or match a display label.

Save this complete file as `group-create.json`, replacing `0` with the Project revision you reviewed:

<CodeGroup>

```json
{
  "name": "support-knowledge",
  "displayName": "SupportKnowledge",
  "expectedAccessRevision": 0
}
```

</CodeGroup>

Choose one request key and keep it with the original installation URL, Project ID and complete file before dispatch. Each key has at most 128 characters:

<CodeGroup>

```shell
export GROUP_CREATE_KEY='support-knowledge-create-1'
```

</CodeGroup>

Choose one alternative and run from the directory containing `group-create.json`. Save the complete Python program as `create_access_group.py`, the TypeScript program as `create-access-group.ts`, or the Rust program as `src/main.rs` in its example project:

```python
import asyncio
import os
from pathlib import Path
from uuid import UUID

import httpx
from inframeld_sdk import ApiClient, Configuration
from inframeld_sdk.api.access_api import AccessApi
from inframeld_sdk.exceptions import ApiException
from inframeld_sdk.models.access_group_creation_request import AccessGroupCreationRequest


async def main() -> None:
    request = AccessGroupCreationRequest.model_validate_json(
        Path("group-create.json").read_text(encoding="utf-8")
    )
    configuration = Configuration(
        host=os.environ["INFRAMELD_URL"],
        access_token=os.environ["INFRAMELD_TOKEN"],
    )
    async with ApiClient(configuration) as client:
        try:
            receipt = await AccessApi(client).create_access_group(
                project_id=UUID(os.environ["PROJECT_ID"]),
                idempotency_key=os.environ["GROUP_CREATE_KEY"],
                access_group_creation_request=request,
                _request_timeout=5.0,
            )
        except ApiException as error:
            print(f"No usable creation receipt: HTTP {error.status}")
            print("Keep the original request file and key.")
            raise SystemExit(1) from error
        except httpx.HTTPError as error:
            print("No usable response. Keep the original request file and key.")
            raise SystemExit(1) from error

        print(receipt.to_json())


if __name__ == "__main__":
    asyncio.run(main())
```

Creation saves the group and your ordinary membership and management together. It makes no separate document-action assignment. A naming conflict, stale reviewed revision or failed commit leaves no partial new group or creator relationship.

HTTP `201` returns `projectId`, `accessGroupId`, the names, your `creatorPrincipalId`, the resulting Project `accessRevision`, `operationId` and `idempotencyExpiresAt`. A fresh creation advances the Project Access revision once. Keep the returned group ID and original receipt. It describes creation, not today's memberships or management.

An exact creation retry still requires your current Project creation authority. It returns that original group and receipt without recreating the group or restoring creator membership or management removed later.

Each page identifies `projectId`, `accessGroupId` and the current Project `accessRevision`. Its `items` contain only `principalId`, `displayName` and `kind`, with nullable `nextCursor`. A freshly created group lists you in both relationships. Stored relationship presence does not replace the eligibility checks for a later change.

Pass a continuation cursor unchanged within its original scope. Every page checks current management again. A cursor is neither a snapshot nor a permission token, and a denied read is not an empty list.

The default limit is 25 and the allowed range is 1–100, in principal-UUID order. If `nextCursor` is non-null, repeat that same list with `--data-urlencode "cursor=$GROUP_CURSOR"`, using the returned value as `GROUP_CURSOR`. Member and manager cursors belong to their respective lists. These GETs accept no body or idempotency key and change no relationships, revision or audit.

### Inspect with a generated client

These complete programs perform the same four reads as the cURL examples. They require current management for the list calls. Leave `GROUP_MEMBERS_CURSOR` and `GROUP_MANAGERS_CURSOR` unset for their first pages, or set each to the unchanged cursor from that same list.
```python
import asyncio
import os
from uuid import UUID

import httpx
from inframeld_sdk import ApiClient, Configuration
from inframeld_sdk.api.access_api import AccessApi
from inframeld_sdk.exceptions import ApiException


async def main() -> None:
    project_id = UUID(os.environ["PROJECT_ID"])
    group_id = UUID(os.environ["ACCESS_GROUP_ID"])
    configuration = Configuration(
        host=os.environ["INFRAMELD_URL"],
        access_token=os.environ["INFRAMELD_TOKEN"],
    )
    async with ApiClient(configuration) as client:
        api = AccessApi(client)
        try:
            group = await api.get_access_group(
                project_id=project_id, access_group_id=group_id
            )
            print("Group by ID:")
            print(group.to_json())

            resolved = await api.resolve_access_group(
                project_id=project_id, name="support-knowledge"

            print("Group by Name:")
            print(resolved.to_json())

                project_id=project_id,

            print(f"Group inspection failed: HTTP {error.status}")

            raise SystemExit(1) from error
```

```shell {{ title: "cURL" }}
  --header "Idempotency-Key: $GROUP_MEMBER_REMOVE_KEY" \
  --header 'Accept: application/json' <<EOF_HEADERS
Authorization: Bearer ${INFRAMELD_TOKEN}
EOF_HEADERS
```

</CodeGroup>

HTTP `200` reports `removed: true`, the original IDs and `changed`. A real removal advances the Project Access revision once. An already-absent relationship returns `changed: false` without an advance. Read both member and manager lists to inspect current relationships after a successful change.

For a deliberate rejoin, use the add-member operation with a fresh reviewed revision, a distinct request file and a new key. Do not replay the old add to restore access. That replay describes its original result and does not reapply membership.

Removal ends access through this group. A document shared with another group Bob still belongs to may remain accessible through that other relationship. Removing a group membership does not erase Project-owned documents or revoke unrelated action permissions.

## Delete an unused group

Delete a group only when it is no longer needed and no protected stored reference uses it. Replace a protected reference through the operation owned by that resource before preparing a fresh deletion. Managing a group does not authorize changing every resource that references it.

Deletion removes the group's owned relationships and the group together. A referenced-group rejection leaves those effects unchanged. Future Document, source, upload, default and case features supply their real references and deletion protection. The later default-reference workflow is separate from creating and administering this group.

Keep your current management until the group deletion. You do not need to remove the last manager first. For an unused group, deletion removes the scope and its owned relationships together.

Before dispatch, also prepare the [saved group-deletion identity](/guides/recover-original-request#recover-an-access-group-change) if you may need recovery without the returned operation ID. Keep the original installation and Organization IDs with the Project, group, method, concrete route and request key. The installation ID comes from a trusted [target registration](/guides/register-a-target#inspect-and-select-the-target) or your installation operator. Your [own Organization-access read](/api-reference/projects-and-access#read-your-organization-access) supplies the Organization ID.

Review the current Project Access revision, then keep the deletion key and reviewed query value with the original IDs and route. Replace `0` before sending:

<CodeGroup>

```shell {{ title: "cURL" }}

curl --silent --show-error --fail-with-body \

  --header @- \
  --header "Idempotency-Key: $GROUP_DELETE_KEY" \
  --header 'Accept: application/json' <<EOF_HEADERS
Authorization: Bearer ${INFRAMELD_TOKEN}
EOF_HEADERS
```

HTTP `200` returns `removed: true`, `projectId`, `accessGroupId`, the resulting `accessRevision`, `operationId` and `idempotencyExpiresAt`. Keep the operation ID when you receive it. The last field describes ordinary original-result retention. It does not select or renew the separate retained deletion-status expiry.

Save the complete original deletion identity before dispatch. Ordinary repeated DELETE and full-result replay still require current management. A completed synchronous group deletion has no cleanup job or application-shutdown stage.

## Recover an uncertain change

Before each write, retain the original installation, Project and group IDs, method, route, complete body or revision query, and request key. Use a distinct key for a distinct operation. A timeout, disconnect or decoding failure does not establish that the write failed.

For an ordinary retry, preserve the same key and complete original request, including its originally reviewed revision. The server checks current authority before returning a retained result. Replaying an old membership or manager change returns its original receipt without restoring or removing a relationship changed afterward. Read current relationships separately.

Deletion has an additional retained path for the currently eligible original human. The exact saved request identity or original operation ID can disclose only content-free deletion correlation and status after the group disappears. This does not restore management or permit a full business-result replay without its ordinary current authority.

The retained deletion path is independent of expired ordinary idempotency history. Its captured original status expiry does not renew when read again. An unresolved observation proves neither successful deletion nor absence of earlier effects. Preserve the original context before considering replacement work.

For a lost group-deletion response, use the complete closed-family request in [original-request lookup](/guides/recover-original-request#recover-an-access-group-change). It uses family `access_group_deletion`, action `delete-access-group`, method `DELETE` and the original concrete UUID path, without the query string. These values describe the saved deletion identity, not a new permission grant. A `retained` result is content-free status, not the original group deletion receipt.

If you already received the original `operationId`, use [retained deletion status](/guides/read-deletion-status#read-status-for-a-deleted-access-group) directly. For a settled group deletion, `admissionConfirmed`, `accessBlocked` and `physicalCleanupComplete` are true. `jobState` and `applicationShutdownComplete` are null because this synchronous group operation has neither stage. The returned `retentionExpiresAt` belongs to the captured group-status record, separately from ordinary `idempotencyExpiresAt`.

## Review a rejection before sending new work

An invalid credential, lost current authority, hidden scope, ineligible recipient, stale fresh review or unsafe last-manager change requires a different next step. Correct the stated prerequisite rather than treating an earlier successful read as permission for a later write.

For a confirmed stale fresh request, reread and review the current Project Access revision before preparing distinct work with its own key. For an uncertain result, keep the original request unchanged and use its recovery path first. A rejected fresh change leaves no partial membership or management change.

| Result                             | Meaning and next action                                                                                                                                                            |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `401`                              | Use a currently accepted human credential for this installation.                                                                                                                   |
| `403`                              | Current eligibility or manager authority denies this operation. An older successful read or retained key does not authorize it.                                                    |
| `404`                              | The group or requested scope is missing or hidden. A denied observation is not proof that an uncertain write had no effect.                                                        |
| `409`                              | Review the Problem Details for stale fresh review, unavailable Name, unsafe handover, protected reference or an original-request conflict. Preserve uncertain original work first. |
| `400` or `422`                     | Correct malformed authentication, invalid fields or query framing. Use one canonical nonnegative revision value and reject unsupported recipient kinds.                            |
| `413` or `415`                     | POST/PUT require one JSON object, at most 32 KiB, with `Content-Type: application/json`. DELETE has no body.                                                                       |
| `503`, timeout or decoding failure | No usable observation or receipt is established. Keep the original request and resolve the dependency or connection problem before choosing recovery.                              |

All group responses and problems use `Cache-Control: no-store`. Browser-cookie writes use the installation's actual Origin and cookie configuration with `X-Inframeld-CSRF: 1`. Do not combine a bearer token and a browser cookie. [The API reference](/api-reference/projects-and-access#create-an-access-group) reads the exact native operation and model contracts.
