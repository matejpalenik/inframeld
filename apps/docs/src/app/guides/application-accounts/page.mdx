# Create and inspect an application account

Create SupportBot in your Support Project as a separate identity for an integration. The account belongs to that one Project and starts with no action permissions, document-group memberships or keys. Creating it does not copy your human access.

You receive three permissions to administer this specific account. The account's permissions and its incoming credentials remain separate. This guide covers account creation, explicit key issuance, individual revocation and safe metadata reads. [Application identity authentication](/guides/authenticate-an-application) checks the resulting credential separately. Creation and metadata reads issue no key. Permanent account retirement remains a separate operation without a public procedure here.

Use [exact action-grant administration](/guides/manage-action-grants) to share one account-administration permission with another eligible human in the Project. Those grants control the human's authority over SupportBot. They do not give SupportBot an action permission, create a key or copy any human access. An application account cannot receive account-administration grants or grant authority.

## Prepare your access

You need an existing Project, its permanent ID and a current human credential accepted by the installation. You must be an eligible admitted human member of that Project with permission to use `create-application-accounts`. Either `canGrant` level permits creation. Project membership alone does not.

Set `INFRAMELD_URL` and `INFRAMELD_TOKEN` through the shared [HTTP setup](/clients/http#call-protected-operations). These examples assume an existing valid human bearer token. Browser sign-in alone does not put a bearer token in your terminal. If you have no supported protected credential, start with the [health request](/clients/http#make-your-first-request). The complete account-to-API procedure, engineering dry run and human acceptance remain unfinished in [qualification #352](https://github.com/matejpalenik/inframeld/issues/352).

For a generated SDK, follow the local source-package setup for [Python](/clients/python), [TypeScript](/clients/typescript) or [Rust](/clients/rust) in a separate example project. There is no delivered CLI command for this task.

Use the `projectId` from the Project's creation response or an authorized [exact-Name resolution](/guides/name-and-rename-project#resolve-the-name-and-keep-the-id). Set it in your example directory, replacing this recognizable example UUID with the Support Project's actual ID:

<CodeGroup>

```shell
export PROJECT_ID='00000000-0000-4000-8000-000000000003'
```

</CodeGroup>

Creation persists the account and its creator's administration grants. For a disposable exercise, use a wholly disposable installation and agree on its operator-supported teardown before creating accounts. This preview provides no public account-retirement procedure.

The response identifies your human `principalId`, the `projectId` and the current Project `accessRevision`. Review your exact Project grant for `create-application-accounts`. Follow `nextCursor` while it is non-null to read your remaining stored assignments. [Read your Project access](/guides/assign-project-grant#read-your-project-access-and-current-revision) explains this combined paging contract and the generated clients.

The revision detects competing access changes. It is not a permission snapshot. The server checks your current eligibility, membership and creation permission again when saving the account.

## Save the reviewed creation request

Choose `support-bot` as the exact Name and `SupportBot` as its display name. A Name selects the account. A display name is a non-unique label. The server assigns the permanent identity.

Names contain 1–63 lowercase ASCII letters, digits or hyphens, start with a letter and end with a letter or digit. Names are unique among application accounts in the Project, including accounts you cannot inspect. Retired Names remain reserved. An unavailable Name needs another explicit choice. The server does not silently add a suffix.

Display names contain 1–128 Unicode code points, are nonblank and have no surrounding whitespace, controls, surrogates or line/paragraph separators. Lookup uses the exact Name, without trimming, lowercasing, matching a display label or choosing a near match.

Save this complete new file as `application-account-create.json`. Replace `0` with the Project `accessRevision` you reviewed:

<CodeGroup>

```json
{
  "name": "support-bot",
  "displayName": "SupportBot",
  "expectedAccessRevision": 0
}
```

</CodeGroup>

Choose one request key for this creation. Keep the original installation URL, Project ID, complete request file and key together before dispatch. Use a distinct key for a distinct creation, with at most 128 characters:

<CodeGroup>

```shell
export APPLICATION_ACCOUNT_CREATE_KEY='support-bot-create-1'
```

</CodeGroup>

## Create the account

Choose one alternative and run it from the directory containing `application-account-create.json`. Keep the body and request key unchanged if you do not receive a usable result. Save the Python program as `create_application_account.py`, the TypeScript program as `create-application-account.ts`, or the Rust program as `src/main.rs` in its example project:

<CodeGroup>

```shell {{ title: "cURL" }}
curl --silent --show-error --fail-with-body \
  --max-time 5 \
  --request POST \
  --url "$INFRAMELD_URL/v1/projects/$PROJECT_ID/application-accounts" \
  --header @- \
  --header "Idempotency-Key: $APPLICATION_ACCOUNT_CREATE_KEY" \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json' \
  --data-binary @application-account-create.json <<EOF_HEADERS
Authorization: Bearer ${INFRAMELD_TOKEN}
EOF_HEADERS
```

```python
import asyncio
import os
from pathlib import Path
from uuid import UUID

import httpx
from inframeld_sdk import ApiClient, Configuration
from inframeld_sdk.api.access_api import AccessApi
from inframeld_sdk.exceptions import ApiException
from inframeld_sdk.models.application_account_creation_request import (
    ApplicationAccountCreationRequest,
)


async def main() -> None:
    request = ApplicationAccountCreationRequest.model_validate_json(
        Path("application-account-create.json").read_text(encoding="utf-8")
    )
    configuration = Configuration(
        host=os.environ["INFRAMELD_URL"],
        access_token=os.environ["INFRAMELD_TOKEN"],
    )
    async with ApiClient(configuration) as client:
        try:
            account = await AccessApi(client).create_application_account(
                project_id=UUID(os.environ["PROJECT_ID"]),
                idempotency_key=os.environ["APPLICATION_ACCOUNT_CREATE_KEY"],
                application_account_creation_request=request,
                _request_timeout=5.0,
            )
        except ApiException as error:
            print(f"Creation could not be confirmed: HTTP {error.status}")
            print(error.body)
            print("Keep the original request file and key.")
            raise SystemExit(1) from error
        except httpx.HTTPError as error:
            print("No usable response. Keep the original request file and key.")
            raise SystemExit(1) from error

        print(account.to_json())


if __name__ == "__main__":
    asyncio.run(main())
```

Run `.venv/bin/python create_application_account.py`, `node create-application-account.ts` with Node 26 in the ESM project, or `cargo run` from the Cargo project. The shared SDK setup pages supply the local dependency and runtime configuration.

HTTP `201` returns `principalId`, `projectId`, the chosen names and the new Project `accessRevision`. A fresh creation advances that Project revision once. Keep `principalId` as the application account's permanent ID. The account and its application principal use this same ID. There is no second account ID, and the account cannot move to another Project.

`initialGrants` records three assignments to you, each with `canGrant: true` and an exact `application-account` target for SupportBot:

| Action                       | Meaning                                                                                         |
| ---------------------------- | ----------------------------------------------------------------------------------------------- |
| `issue-application-keys`     | Issue a key for this account when all current delegation and group-management checks also pass. |
| `revoke-application-keys`    | Administer key revocation for this account when that separate operation is available.           |
| `delete-application-account` | Administer retirement of this account when that separate operation is available.                |

These grants belong to your human identity, not SupportBot. They do not administer other accounts or give the bot access to documents or models. Creation saves the account, required Project membership, three creator grants, audit and original result together. A rejected commit leaves none of those partial creation effects.

The response also includes `operationId` and `idempotencyExpiresAt`. These describe the retained original creation result. Its `initialGrants` is a historical receipt, not today's permission inventory. Read your own Project access again for your current stored grants.

## Issue a key

Alice can issue SupportBot a key without giving it her own identity. Issuance preserves the application's principal and permissions. Someone holding the new key can use SupportBot's full current access, so Alice needs all of these:

- Current eligible-human membership in the account's Project.
- Permission to use `issue-application-keys` on this exact account.
- Permission to use and grant every current action permission held by SupportBot, plus management of every group it belongs to.

Being able to read the same documents is insufficient. If another administrator adds SupportBot to a group Alice cannot manage, her Issue permission alone no longer authorizes issuance. The server rechecks the complete current state. An empty newly created account still requires the exact Issue permission, even though it has no received permissions or groups to cover.

Choose `allowedAdapters` as a nonempty unique subset of `http` and `mcp`. The server binds each selected adapter to its configured trusted profile. Selecting both keeps one parent key, secret and usable-key slot, including when the HTTP and MCP audiences differ. You supply no audience. A missing selected profile returns `503` before a secret is created; a missing unselected profile does not prevent issuance. Selecting MCP does not provide a mounted MCP server or client setup.

Omitting `expiresInSeconds` uses the configured default, which is 90 days by default. The configured maximum is 365 days by default. These are operator settings, not fixed duration guarantees. An explicit lifetime must be positive whole seconds within the configured maximum and safe-integer bound, and its expiry must fit a date the server can represent. Explicit `null`, booleans and fractions are invalid. There is no automatic renewal.

An account may have at most two unexpired, unrevoked parent keys across its adapters. A dual-adapter key counts once. A profile change or authentication failure does not free its slot. Expired or revoked history does not count. Issuance never silently revokes or evicts a key to make room, and this operation does not supply the separate revocation workflow.

## Submit from your existing human browser session

Use the installation's configured HTTPS account/API origin, where the account pages, Kratos session route and `/v1` API share an origin. Sign in as Alice through its supported `/login` flow. As in the [human-admission browser setup](/guides/admit-human#use-the-existing-browser-sessions), `/v1/session` identifies the current admitted human. The browser keeps its own cookie. Do not copy it into another client or add an application credential.

Use the permanent Project and application principal IDs from creation or authorized inspection. In the same signed-in browser, read `/v1/projects/{project_id}/my-access` using your actual Project UUID and review its `accessRevision`. For a new issuance, save that revision with the exact account, selected adapters, omitted or explicit lifetime and one unique idempotency key before dispatch. For recovery, use the original saved revision and key instead of refreshing the request from today's state.

Build the source TypeScript SDK through [its existing setup](/clients/typescript#build-and-install-the-package). Save this complete module as `issue-application-key.ts` in your existing browser application's client bundle on the configured account/API origin. Load it in Alice's browser profile. Its prompts take the saved original IDs, revision and key. This example selects HTTP only and omits the lifetime. Keep those choices unchanged when repeating it.

<CodeGroup>

```typescript {{ title: "TypeScript (browser)" }}
import {
  createClient,
  issueApplicationKey,
  type ApplicationKeyIssueRequest,
} from "@inframeld/sdk"

async function main(): Promise<void> {
  const projectId = window.prompt("Saved Project ID")
  const applicationPrincipalId = window.prompt("Saved application principal ID")
  const revisionText = window.prompt("Saved original Project Access revision")
  const idempotencyKey = window.prompt(
    "Saved original issuance idempotency key"
  )
  if (
    !projectId ||
    !applicationPrincipalId ||
    revisionText === null ||
    idempotencyKey === null
  )
    return
  const revision = Number(revisionText)
  if (
    !/^(0|[1-9][0-9]*)$/.test(revisionText) ||
    !Number.isSafeInteger(revision) ||
    !idempotencyKey.trim() ||
    idempotencyKey.length > 128
  ) {
    throw new Error("Review the exact saved revision and original request key")
  }
  const body: ApplicationKeyIssueRequest = {
    allowedAdapters: ["http"],
    expectedAccessRevision: revision,
  }
  if (
    !window.confirm(
      "Submit this saved HTTP-only issuance request? An explicit retry must keep the original inputs and key."
    )
  )
    return
  const client = createClient({
    baseUrl: window.location.origin,
    credentials: "same-origin",
    timeoutMs: 5000,
    responseStyle: "fields",
    throwOnError: false,
  })
  const result = await issueApplicationKey({
    client,
    path: {
      project_id: projectId,
      application_principal_id: applicationPrincipalId,
    },
    headers: {
      "X-Inframeld-CSRF": "1",
      "Idempotency-Key": idempotencyKey,
    },
    body,
  })
  if (result.error !== undefined) {
    console.error({
      httpStatus: result.response?.status,
      failureKind: result.error.kind,
    })
    if (result.error.kind === "api") {
      console.error({
        code: result.error.body.code,
        requestId: result.error.body.requestId,
      })
    }
    return
  }
  if (result.data === undefined) throw new Error("No usable issuance receipt")
  const receipt = result.data
  console.info({
    httpStatus: result.response?.status,
    operationId: receipt.operationId,
    accessRevision: receipt.accessRevision,
    idempotencyExpiresAt: receipt.idempotencyExpiresAt,
    metadata: receipt.metadata,
    secretAvailable: receipt.secretAvailable,
  })
  if (receipt.secretAvailable) {
    try {
      window.prompt(
        "First delivery only. Copy this key into your supported private credential store now. This dialog does not save it.",
        receipt.key
      )
    } catch {
      console.error(
        "Remote issuance succeeded, but local secret delivery could not be completed"
      )
    }
    console.info(
      "Private saving is not confirmed by this program. Keep the safe receipt"
    )
  } else {
    console.info(
      "Original metadata only. The key field is absent and cannot be retrieved"
    )
  }
}

void main().catch(() => {
  console.error(
    "No usable result. Preserve the original request and key. Do not create an automatic replacement"
  )
})
```

</CodeGroup>

The browser supplies its actual cookie and Origin; the request adds `X-Inframeld-CSRF: 1`. This is an integration module, not a key-management screen or a CLI login command. cURL, Python, Rust and Node issuance require a separately obtained eligible-human credential. Browser sign-in does not export one, and the generated SDKs do not acquire it. Do not substitute cookie extraction for a missing supported credential producer.

## Save first delivery privately

A successful first delivery is `201` with `secretAvailable: true`, the complete `key`, safe `metadata`, the original operation ID, Project Access revision and retained-result expiry. The example displays the secret in a private dialog for your deliberate copy. It does not save a file, access the clipboard or confirm that your credential store saved it. Some browser contexts may suppress the dialog. Keep the full key out of source, bundles, URLs, logs, screenshots and shared diagnostic output.

A usable first response confirms remote issuance even if local display, copying or saving fails. Preserve its safe receipt. The server cannot retrieve the secret later. An authorized exact replay is still `201`, but has `secretAvailable: false` and the `key` field is absent, not `null`. It cannot repair failed private delivery or mint a replacement.

Use the privately saved HTTP-enabled key with the [application identity check](/guides/authenticate-an-application), in a separate application credential context. Do not combine the key with Alice's browser cookie. That check should identify SupportBot's expected Project and principal, without adding Alice's access.

## Recover an uncertain key issuance

A timeout, cancellation, `503` or unusable response can leave remote issuance unknown. Preserve the original installation, same human, concrete UUID route, complete body, adapter order, omitted lifetime and idempotency key. Do not choose another key, change the revision or refresh the request into a different issuance automatically.

Explicitly repeat only the exact original POST. Current authority is checked again. A completed original returns its captured operation, revision, metadata and retention expiry without another key, audit or revision change. It stays historical even after the credential expires or is revoked, or server profiles and lifetime defaults change. Use the existing authorized key metadata reads for current lifecycle state. A replay neither rebinds the key nor renews retention. If the original did not commit, the same request can still be processed under its original meaning and current fresh checks.

Choosing a replacement after a lost secret is a separate deliberate decision. A human with the independent Revoke permission can [revoke that key](#revoke-one-application-key), then consider a separate issuance under its full current requirements. Issuance never revokes or replaces a key automatically.

## Inspect safe key metadata

Key reads require current permission to use `issue-application-keys` or `revoke-application-keys` on this exact account. `delete-application-account` alone is insufficient. Metadata reads do not require the additional delegation and group-management authority needed by the separate key-issuance contract.

Read one page of retained key metadata:

<CodeGroup>

```shell {{ title: "cURL" }}
curl --silent --show-error --fail-with-body \
  --max-time 5 \
  --get \
  --url "$INFRAMELD_URL/v1/projects/$PROJECT_ID/application-accounts/$APPLICATION_PRINCIPAL_ID/keys" \
  --data-urlencode 'limit=25' \
  --header @- \
  --header 'Accept: application/json' <<EOF_HEADERS
Authorization: Bearer ${INFRAMELD_TOKEN}
EOF_HEADERS
```

</CodeGroup>

A newly created account returns an empty `items` array and `nextCursor: null`, because creation issued no key. For an account with retained keys, each item gives safe binding and lifecycle metadata. `expiresAt` is its recorded expiry. `revokedAt` is null or its recorded revocation time. The item never contains the key secret or verifier. Listing a key does not establish that it can currently authenticate or use any particular action.

Lists use key-UUID order, a default limit of 25 and a range of 1–100. If `nextCursor` is non-null, repeat the same scoped GET with that value as the `cursor` query parameter, passed unchanged through `--data-urlencode`. Every page checks current authority. A cursor supplies neither a snapshot nor permission, and a denied read is not an empty page.

For an account that already has a retained key, set `APPLICATION_KEY_ID` to its `keyId` and read that one record:

<CodeGroup>

```shell {{ title: "cURL" }}
curl --silent --show-error --fail-with-body \
  --max-time 5 \
  --url "$INFRAMELD_URL/v1/projects/$PROJECT_ID/application-accounts/$APPLICATION_PRINCIPAL_ID/keys/$APPLICATION_KEY_ID" \
  --header @- \
  --header 'Accept: application/json' <<EOF_HEADERS
Authorization: Bearer ${INFRAMELD_TOKEN}
EOF_HEADERS
```

</CodeGroup>

The single-key response has the same safe item shape. It cannot retrieve a lost secret. These GETs take no body, reviewed revision or idempotency key. Account and key responses use `Cache-Control: no-store`. [The API reference](/api-reference/projects-and-access#read-application-key-metadata) shows their exact native contracts.

## Revoke one application key

Revoke a leaked or replaced credential while keeping SupportBot's account and permissions. You must be a currently eligible admitted human member of its Project with permission to use `revoke-application-keys` on this exact account. Issue keys, Delete account or authority on another account is insufficient. Revoke does not require issuance delegation, group management or document access. You may revoke the last usable key immediately.

Use your genuine human browser session and the installation's supported Origin/CSRF path, as for the [browser issuance integration](#submit-from-your-existing-human-browser-session). The application key being revoked is not your administration credential. Browser sign-in does not export a human bearer token for terminal examples.

Read the account's current metadata to review its Project `accessRevision`, and select the exact `keyId` from [safe key metadata](#inspect-safe-key-metadata). Preserve the installation, same human, Project ID, application principal ID and key ID. Send `POST /v1/projects/{project_id}/application-accounts/{application_principal_id}/keys/{key_id}/revoke` with a new saved `Idempotency-Key`. The JSON body contains only the reviewed `expectedAccessRevision`, a nonnegative whole integer within the safe revision range. Keep that complete original context before sending.

A successful response is `200` with the original `operationId`, Project `accessRevision`, `idempotencyExpiresAt` and safe nested `metadata`. It contains no secret or verifier. First revocation records `revokedAt`, advances the Project Access revision once and saves the revocation audit and original result together. The single parent key is revoked for every adapter it allowed, including both bindings of a dual-adapter key.

A fresh request for an already revoked key still requires current Revoke authority and the reviewed current revision. It returns `200` with the existing revocation time, without another revision change or revocation audit. This new request has its own retained original receipt. Issuing another key and permanently retiring the account remain separate decisions.

### Submit from the same human browser context

Use the [source TypeScript package setup](/clients/typescript#build-and-install-the-package) and the existing browser application on the configured HTTPS account/API origin described for issuance. Save this complete module as `revoke-application-key.ts` in that application's client bundle and load it once in the intended signed-in human's browser profile. Supply the saved original IDs, revision and revocation request key. The key ID is public metadata, not the full application credential. For a fresh request, review and save the current revision first. For recovery, keep the originally reviewed revision even if today's value has advanced.

```typescript {{ title: "TypeScript (browser)" }}
  if (
    !window.confirm(
      "Submit this saved revocation request? It may revoke the last usable key. Explicit recovery must keep every original input and key."
    )
  )
    return
  const client = createClient({
    baseUrl: window.location.origin,
    credentials: "same-origin",
    timeoutMs: 5000,
    responseStyle: "fields",
    throwOnError: false,
  })
  const result = await revokeApplicationKey({
    client,
    path: {
      project_id: projectId,
      application_principal_id: applicationPrincipalId,
      key_id: keyId,
    },
    headers: {
      "X-Inframeld-CSRF": "1",
      "Idempotency-Key": idempotencyKey,
    },
    body,
  })
  if (result.error !== undefined) {
    console.error({
      httpStatus: result.response?.status,
      failureKind: result.error.kind,
    })
    if (result.error.kind === "api") {
      console.error({
        code: result.error.body.code,
        requestId: result.error.body.requestId,
      })
    } else if (result.error.kind === "transport") {
      console.error({ reason: result.error.reason })
    }
    console.info("Keep the original request. No automatic repeat was sent")
    return
  }
  if (result.data === undefined) throw new Error("No usable revocation receipt")
  const receipt = result.data
  console.info({
    httpStatus: result.response?.status,
    operationId: receipt.operationId,
    accessRevision: receipt.accessRevision,
    idempotencyExpiresAt: receipt.idempotencyExpiresAt,
    metadata: receipt.metadata,
  })
  console.info(
    "Keep this historical receipt. Current account authority is separate"
  )
}

void main().catch(() => {
  console.error(
    "No usable result. Preserve the exact original request and key. Do not send an automatic replacement"
  )
})
```

</CodeGroup>

The browser supplies its actual cookie and Origin, and the module adds the CSRF marker. It sends one explicit POST and reports only safe metadata or fixed failure categories. A validated API failure exposes its code and correlation ID. A transport failure distinguishes network, timeout and cancellation, while decode and request failures remain separate kinds. An HTTP status without a usable typed receipt does not establish the revocation result. No failure triggers another write, changes the request key or issues a replacement credential.

### Recover an uncertain revocation

If a timeout, cancellation, `503` or unusable response leaves the result unknown, preserve the exact original POST route, body and request key. Explicitly repeat that same request under the same human's current Revoke authority. Do not replace its reviewed revision with today's value or silently choose another request key. A completed original returns its captured metadata, revision and retention expiry before fresh revision checks, with no repeated revocation or renewed retention. Current authority is checked before returning that result. The generic operation lookup does not support this request.

A current metadata read can show that the key is revoked, but does not prove which request revoked it. Missing or hidden state and a denied replay do not establish that the original failed. Retain the original context and use the installation's supported recovery procedure before considering distinct work.

After revocation commits, new requests through that credential are rejected by current key checks. Revocation does not delete SupportBot, remove its grants or undo committed effects. It cannot recall bytes or external calls already sent. An [already admitted job](/guides/authenticate-an-application#keep-admitted-jobs-separate-from-incoming-credentials) has its own current-account and authority checks rather than automatic cancellation by this credential operation.

## Read with a generated client

These complete programs repeat the account-by-ID, exact-Name and key-list reads above. Use the same `PROJECT_ID` and `APPLICATION_PRINCIPAL_ID`, and current Issue or Revoke keys authority. The exact Name is `support-bot`, matching this guide's creation request.

Leave `APPLICATION_KEYS_CURSOR` unset for the first key page, or set it to the unchanged `nextCursor` from the previous page. If the account has a retained key, set `APPLICATION_KEY_ID` to that item's `keyId` to include its single-key read. Leave it unset for a new account.

## Recover an uncertain creation result

A timeout, disconnect, `503` or decoding failure can leave creation uncertain. Keep the original installation, Project ID, `POST` method, account-collection route, complete request file and request key. Finding an account by Name alone does not prove which request created it.

Within the retained replay period, repeat the original POST with the same key and complete original body using a currently valid credential for the same human. Keep the originally reviewed revision, even if today's revision has advanced. The server checks your current eligibility, Project membership and `create-application-accounts` authority before returning a retained result.

An exact completed replay returns the original `201`, account ID, operation ID, names, revision, creator-grant receipt and expiry. It creates no duplicate account, restores no removed grant and does not extend retention. Use fresh account and own-access reads to inspect current state.

[Original-request lookup](/guides/recover-original-request) can inspect retained operation metadata when you also kept the original installation and Organization IDs. For this creation, use method `POST`, family `project_action_use`, action `create-application-accounts` and the original concrete route containing your actual Project UUID. For example, the route is `/v1/projects/00000000-0000-4000-8000-000000000003/application-accounts` for this guide's example Project ID. Replace that UUID with your original Project ID. The literal `{project_id}` template does not match this operation's retained route.

Supply the original Project ID and request key as well. Lookup does not replace the creation receipt. An unresolved observation does not prove that nothing happened. Preserve the original context and use the installation's supported recovery path before considering a distinct creation.

## Interpret a rejection

| Result         | Meaning and next action                                                                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `401`          | Supply a currently accepted credential for this installation. This procedure uses a human identity.                                                                  |
| `403`          | Current eligibility or exact operation authority does not permit the action. A retained key or earlier successful read cannot bypass current checks.                 |
| `404`          | The Project, account or key is missing or hidden under the current scope. Do not interpret this as a safe reason to create replacement work.                         |
| `409`          | Inspect the Problem Details for a stale reviewed revision, unavailable Name or original-request conflict. Preserve uncertain original work before changing anything. |
| `400` or `422` | Correct malformed authentication, invalid naming, revision, fields or cursor. Send each scalar query parameter once.                                                 |
| `413` or `415` | Send creation as one JSON object with `Content-Type: application/json`, at most 32 KiB.                                                                              |
| `503`          | A required dependency could not be confirmed. A creation outcome may remain uncertain. Keep its original context.                                                    |

For a confirmed stale fresh request, reread and review your Project access before preparing a distinct request. For a confirmed Name conflict, choose a different explicit Name. GET reads are safe to repeat with current credentials and authority, while writes retain their original request meaning.

Browser-cookie POST callers use the installation's actual cookie and Origin configuration and send `X-Inframeld-CSRF: 1`. Do not combine a bearer token and a session cookie. Errors use the shared [Problem Details contract](/api-reference/operations#errors-and-uncertain-effects).
