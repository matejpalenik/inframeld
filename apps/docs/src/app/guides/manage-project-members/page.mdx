# Add and remove Project members

Alice adds Bob to Support so he can see the Project. Membership supplies no action grants or document access. Later, removing Bob clears the access he received within Support while preserving permissions he assigned to other people.

Project membership commands are not yet available in the [CLI](/clients/cli/commands). Use the HTTP requests or generated SDK examples below.

## Review the people, Project and current revision

Alice must be an eligible admitted human, a current Project member and able to use `manage-project-members` on that Project. Permission to delegate the action is unnecessary. Removing yourself requires the same authority and departure checks.

Use the backend URL, permanent Project ID and current human credential described in [membership-read setup](/guides/list-project-members#prepare-your-project-and-permission). The cURL examples assume `INFRAMELD_URL` and `INFRAMELD_TOKEN` are already set through [HTTP setup](/clients/http#call-protected-operations). Browser sign-in does not produce a terminal bearer token. Complete account-to-API setup and [human qualification #319](https://github.com/matejpalenik/inframeld/issues/319) remain unfinished.

Bob must already be admitted to the same installation and Organization. To add him, he must also be currently eligible. These operations accept humans, not application accounts, and do not perform installation admission.

Obtain the inputs without substituting one kind of identity for another:

- Use the Project ID returned by [ordinary Project creation](/guides/create-project), or your existing authorized Project context.
- For a new member, Bob can read his own `/v1/session` under his current credentials and share only `principalId`. With the configured account origin, he can sign in at `/login` and open `/v1/session` in his own browser profile. This local principal ID is different from his Kratos identity UUID. For removal, use the exact human `principalId` from the [stored-member list](/guides/list-project-members).
- Read the member list and review its `accessRevision`. This is the Project's Access revision, not its metadata revision. The server checks current authority and the reviewed revision again when saving.

Replace these illustrative UUIDs and revision with your reviewed values. Save a unique add key with the exact request inputs before sending. The environment variables below supply those saved values to the examples:

<CodeGroup>

```shell
export PROJECT_ID='00000000-0000-4000-8000-000000000003'
export RECIPIENT_ID='00000000-0000-4000-8000-000000000002'
export EXPECTED_ACCESS_REVISION='1'
export ADD_MEMBER_KEY='replace-with-your-saved-unique-add-key'
```

</CodeGroup>

Choose the cURL request or one of the [generated-client programs](#use-a-generated-client) for each reviewed operation.

## Add bare membership

This request uses `PUT /v1/projects/{project_id}/members/{principal_id}`. Its JSON body contains only the reviewed revision:

<CodeGroup>

```shell {{ title: "cURL" }}
curl --silent --show-error --fail-with-body \
  --max-time 5 \
  --request PUT \
  --url "$INFRAMELD_URL/v1/projects/$PROJECT_ID/members/$RECIPIENT_ID" \
  --header @- \
  --header 'Accept: application/json' \
  --header 'Content-Type: application/json' \
  --data-binary "{\"expectedAccessRevision\":$EXPECTED_ACCESS_REVISION}" <<EOF_HEADERS
Authorization: Bearer $INFRAMELD_TOKEN
Idempotency-Key: $ADD_MEMBER_KEY
EOF_HEADERS
```

</CodeGroup>

A fresh `201` with `member: true` and `changed: true` adds Bob and advances the Project Access revision once. A fresh `200` with `changed: false` means the eligible human is already a member and leaves that revision unchanged.

Adding or rejoining creates only membership. It does not restore old action grants, group memberships or management roles. Bob still needs separately authorized assignments to perform actions or use documents.

Keep the response's `operationId`, `idempotencyExpiresAt`, `projectId`, `principalId`, `accessRevision` and `changed` with the original request. They describe that operation, not Bob's current access.

## Check responsibility before departure

Removal cannot leave a responsibility without an eligible human. Before Bob leaves:

- Each exact Project or application-account action he can grant needs another eligible human Project member who can grant that same action on that same target.
- Each group he manages needs another eligible human who is both a member and manager of that group.
- For a group's Add, Update or Delete documents action, an eligible human group member and manager can also supply the existing delegation alternative.

An application, inactive human, suspended or recovery-blocked human does not supply the required replacement. Adding another Project member alone establishes none of these responsibilities.

The endpoint never selects a replacement or appoints a manager. For an exact Project action, use [Project grant administration](/guides/assign-project-grant) to prepare another eligible human with that same grant authority before departure. Group-manager and application-account grant producers remain separate unfinished work. If a required replacement is missing, stop. Do not substitute a different recipient, host repair or repeated new keys to bypass the guard.

## Remove the reviewed human

Read the member list again and review its current Access revision. Replace the illustrative `2` below with that exact integer and choose a separate removal key. Keep the same Project and recipient IDs:

<CodeGroup>

```shell
export EXPECTED_ACCESS_REVISION='2'
export REMOVE_MEMBER_KEY='replace-with-your-saved-unique-removal-key'
```

```shell {{ title: "cURL" }}
curl --silent --show-error --fail-with-body \
  --max-time 5 \
  --request DELETE \
  --url "$INFRAMELD_URL/v1/projects/$PROJECT_ID/members/$RECIPIENT_ID?expectedAccessRevision=$EXPECTED_ACCESS_REVISION" \
  --header @- \
  --header 'Accept: application/json' <<EOF_HEADERS
Authorization: Bearer $INFRAMELD_TOKEN
Idempotency-Key: $REMOVE_MEMBER_KEY
EOF_HEADERS
```

</CodeGroup>

DELETE takes one `expectedAccessRevision` query value and no body. Stored inactive human members can be removed subject to the same departure guards.

A fresh `200` with `removed: true` and `changed: true` removes Bob's Project membership, received Project, group, application-account and model-connection action grants, and group membership/management within this Project. Those changes, the audit and original result commit together. The Project Access revision advances once, while Project metadata stays unchanged.

Removal preserves Bob's installation admission, other Projects, Project-owned resources and grants he gave other recipients. It does not delete application accounts or their keys. If he is already absent, a fresh `200` with `changed: false` leaves the Access revision unchanged.

## Use a generated client

These are operation snippets for an existing async application. Follow the package and client setup for [Python](/clients/python#install-from-a-checkout), [TypeScript](/clients/typescript#build-and-install-the-package) or [Rust](/clients/rust#set-up-an-example-project). The [shared setup below](#prepare-the-sdk-context-once) supplies imports, configured clients and error handling.

Prepare the same Project ID, recipient ID and current human credential as the HTTP examples. Python uses `UUID` IDs, while TypeScript and Rust use their string forms. Take `add_revision` or `addRevision` from the generated member-list response you reviewed. Keep the independently saved add key in `add_key` or `addKey`, with the original IDs and revision. The snippets reuse these values and do not generate keys or retry automatically.

### Add a member

Python's `add_project_member()` returns a typed receipt directly. Its IDs fill the route, `ProjectMembershipRequest` supplies the JSON body, and `idempotency_key` supplies the header:

<CodeGroup>

```python
receipt: ProjectMembershipResponse = await api.add_project_member(
    project_id=project_id,
    principal_id=principal_id,
    idempotency_key=add_key,
    project_membership_request=ProjectMembershipRequest(
        expectedAccessRevision=add_revision
    ),
)
```

```typescript
const result = await addProjectMember({
  client,
  path: { project_id: projectId, principal_id: principalId },
  headers: { "Idempotency-Key": addKey },
  body: { expectedAccessRevision: addRevision },
})
```

```rust
let response = client
    .add_project_member(
        &project_id,
        &principal_id,
        &add_key,
        ProjectMembershipRequest {
            expected_access_revision: add_revision,
        },
    )
    .await
    .map_err(report_error)?;
```

</CodeGroup>

Keep the returned receipt with the saved request. Python returns the model itself. TypeScript exposes validated receipt data after the error check below, and Rust keeps the typed body in `response.body`. Use Python's `add_project_member_with_http_info()` only when you also need HTTP status or response headers. Status alone does not override a decoding failure.

For an exact retry after uncertainty, pass the saved add key with the same IDs and original reviewed revision again. Do not generate a new key or read a newer revision for that retry.

### Remove a member

Complete the departure review, then [read the member list again](/guides/list-project-members). Keep its newly reviewed revision in `remove_revision` or `removeRevision`, and save a separate `remove_key` or `removeKey`. Other access changes may have occurred since the add, so do not assume its receipt contains the revision for a new removal.

Use the same configured client and exact Project and recipient IDs. Removal supplies the revision as a query argument and sends no body:

<CodeGroup>

```python
receipt: ProjectMembershipRemovalResponse = await api.remove_project_member(
    project_id=project_id,
    principal_id=principal_id,
    expected_access_revision=remove_revision,
    idempotency_key=remove_key,
)
```

```typescript
const result = await removeProjectMember({
  client,
  path: { project_id: projectId, principal_id: principalId },
  headers: { "Idempotency-Key": removeKey },
  query: { expectedAccessRevision: removeRevision },
})
```

```rust
let response = client
    .remove_project_member(&project_id, &principal_id, remove_revision, &remove_key)
    .await
    .map_err(report_error)?;
```

</CodeGroup>

Exact replay passes the original removal key and that removal's original reviewed revision again. Replaying a retained receipt does not repeat the membership change.

## Prepare the SDK context once

Configure the reviewed `backend_url` or `backendUrl` and current `human_token` or `humanToken` once. In Python, import the models below and place either operation snippet inside the open `async with` block of your async application. The block closes the client when the operation finishes or raises. In TypeScript and Rust, use the configured `client` for either operation. Rust's setup belongs in an async function returning `Result`.

<CodeGroup>

```python
from inframeld_sdk import ApiClient, Configuration
from inframeld_sdk.api.access_api import AccessApi
from inframeld_sdk.models.project_membership_request import ProjectMembershipRequest
from inframeld_sdk.models.project_membership_response import ProjectMembershipResponse
from inframeld_sdk.models.project_membership_removal_response import (
    ProjectMembershipRemovalResponse,
)

configuration = Configuration(host=backend_url, access_token=human_token)
async with ApiClient(configuration) as api_client:
    api = AccessApi(api_client)
```

```typescript
import {
  addProjectMember,
  createClient,
  removeProjectMember,
} from "@inframeld/sdk"

const client = createClient({
  baseUrl: backendUrl,
  headers: { Authorization: "Bearer " + humanToken },
  responseStyle: "fields",
  throwOnError: false,
})
```

```rust
use inframeld_sdk::client::{ApiOpError, HttpClient};
use inframeld_sdk::types::ProjectMembershipRequest;

/// Preserve uncertainty without printing protected response content.
fn report_error<E: std::fmt::Debug>(error: ApiOpError<E>) -> std::io::Error {
    if let Some(context) = error.api() {
        eprintln!("No usable membership receipt: HTTP {}", context.status);
    }
    std::io::Error::other("Keep the original request before deciding what to do next")
}

let client = HttpClient::new()
    .with_base_url(backend_url)
    .with_header("Authorization", format!("Bearer {human_token}"));
```

</CodeGroup>

Use the typed revision from the reviewed member-list response. Access revisions are integer numbers from 0 through 9,007,199,254,740,991, which all three clients preserve exactly. Copy the reviewed value unchanged. Reject invalid input instead of rounding it, and do not predict the next revision.

At the Python application boundary, handle `inframeld_sdk.exceptions.ApiException` and `httpx.HTTPError` without printing their raw bodies or exception text. Report the available HTTP status and preserve the original request. Rust's `report_error` similarly returns a safe error and ends the operation unsuccessfully. Neither an HTTP error nor a transport or decoding failure supplies a usable receipt.

In TypeScript, check the typed error branch after either operation. Only `kind === "api"` supplies a validated problem body. The other kinds can represent transport, decoding or local request failures:

<CodeGroup>

```typescript
if (result.error !== undefined) {
  console.error({
    httpStatus: result.response?.status,
    failureKind: result.error.kind,
  })
  if (result.error.kind === "api") {
    console.error({
      code: result.error.body.code,
      requestId: result.error.body.requestId,
    })
  }
  process.exitCode = 1
} else {
  const receipt = result.data
  console.info(JSON.stringify(receipt, null, 2))
}
```

</CodeGroup>

The failure branch logs no submitted inputs, credential or raw response body. Preserve the original request after an unavailable or unusable response, even when an HTTP status is available.

## Preserve the original request after uncertainty

After a timeout, cancellation, lost response or unusable response, keep the original installation, method, route, recipient, reviewed revision and idempotency key. Do not change the revision or choose a new key merely to retry an uncertain original operation.

Exact replay requires Alice's current credentials, Project visibility, membership and `manage-project-members` authority. It returns the original status, result and expiry before applying fresh-change preconditions. Replaying an old add after removal does not add Bob again. Replaying an old removal after rejoin does not remove him again or restore old access. A successful self-departure can leave Alice without authority to read or replay that Project's result.

[Generic original-request lookup](/guides/recover-original-request) is a separate metadata observation, not the membership receipt or continuing permission. A retained result is not guaranteed beyond `idempotencyExpiresAt`.

A `409` can mean a stale revision, an ineligible add recipient, changed request meaning or an unsafe departure. Resolve the actual cause before choosing a new operation. A `401` or `403` requires current credential/authority review. A `404` does not disclose whether an inaccessible Project or recipient exists. Malformed requests can return `400` or `422`, with `413`/`415` for an oversized or wrong-media-type PUT. A `503` or unavailable response leaves the outcome needing reconciliation.

See [the native membership operations](/api-reference/projects-and-access#add-a-project-member) for exact requests, responses and declared errors.
