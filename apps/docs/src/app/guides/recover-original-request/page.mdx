# Check whether your original request was accepted

If you submit a request and lose its response, use `POST /v1/operations/lookup` to check what Inframeld retained about that request. Lookup reads the original operation's record. It does not perform the operation again.

This guide uses an exact Project grant PUT: Alice submitted a request to grant Bob access, but did not receive the response. The same lookup endpoint supports retained Project and Organization operations with the appropriate authority guard. Its closed access-group deletion variant returns only content-free retained deletion status.

<Note>
  An `unresolved` result or a timeout does not mean the original request failed.
  Keep the original request details. Do not submit another operation just
  because lookup cannot confirm the result.
</Note>

<a id="before-you-begin" />

## Keep the original request context

You need:

- The backend URL for your Inframeld installation.
- A current human bearer credential for that installation.
- The original installation, Organization, Project, HTTP method, canonical route, request key, and authority guard. Retain these before sending the original request.
- Current permission to inspect the original scope. Grant-operation metadata requires current eligible-human use-and-grant authority for the original exact action and target. Project-scoped grants also require current membership and visibility. Group management alone is insufficient for this metadata lookup.

The authority guard describes the permission associated with the original operation. Supplying it does not grant permission. Authentication identifies the caller, so the request body has no actor field.

For these examples, set the following variables in your shell. Replace both values with the backend URL and credential supplied for your installation. Use a URL without a trailing slash.

<CodeGroup>

```shell
export INFRAMELD_URL='https://YOUR_INFRAMELD_BACKEND'
export INFRAMELD_TOKEN='YOUR_HUMAN_BEARER_TOKEN'
```

</CodeGroup>

For an SDK alternative, follow the shared [Python](/clients/python), [TypeScript](/clients/typescript) or [Rust](/clients/rust) setup in a separate example project. These examples use the delivered HTTP operations. [CLI command reference](/clients/cli/commands) lists available CLI tasks.

## Prepare the lookup

Save the following as `original-request.json` in your example project's working directory. Replace the illustrative UUIDs and key with the original values. Do not generate a new key for lookup.

<CodeGroup>

```json
{
  "installationId": "00000000-0000-4000-8000-000000000001",
  "organizationId": "00000000-0000-4000-8000-000000000002",
  "projectId": "00000000-0000-4000-8000-000000000003",
  "method": "PUT",
  "requestedRoute": "/v1/projects/00000000-0000-4000-8000-000000000003/grants/00000000-0000-4000-8000-000000000004/create-access-groups",
  "key": "grant-bob-1",
  "expectedAuthority": {
    "family": "project_grant_read",
    "actionId": "create-access-groups"
  }
}
```

</CodeGroup>

Use the original method and the exact route representation documented for that operation. This exact-target PUT uses the concrete original path containing the actual Project and recipient UUIDs and action. An exact-target DELETE uses its concrete path without the revision query. The original idempotency key belongs in the lookup JSON body.

Do not reconstruct the original scope from your current Project selection or an alias. Lookup takes no grant payload or request fingerprint. The JSON body is limited to 32 KiB. Unknown fields and duplicate JSON keys are rejected.

For other supported operations, preserve the original authority meaning:

| Original operation                   | `expectedAuthority.family`       | `expectedAuthority.actionId`           | `projectId`           |
| ------------------------------------ | -------------------------------- | -------------------------------------- | --------------------- |
| Project grant PUT/DELETE             | `project_grant_read`             | Original Project action                | Original Project UUID |
| Organization grant PUT/DELETE        | `organization_grant_read`        | Original Organization action           | Explicit `null`       |
| Access-group grant PUT/DELETE        | `access_group_grant_read`        | Original group document action         | Original Project UUID |
| Application-account grant PUT/DELETE | `application_account_grant_read` | Original account-administration action | Original Project UUID |
| Generic Project operation            | `project_action_use`             | Original Project action                | Original Project UUID |
| Other Organization operation         | `organization_action_use`        | Original Organization action           | Explicit `null`       |
| Project deletion status              | `project_deletion`               | `delete-project`                       | Original Project UUID |

For a Project metadata change, retain method `PATCH`, canonical route `/v1/projects/{project_id}/metadata`, family `project_action_use` and action `edit-project-metadata`. [Name and rename an existing Project](/guides/name-and-rename-project) explains the write and recovery path. Lookup observes its retained operation metadata. A separate Project metadata GET reports current fields.

For application-account creation, retain method `POST`, the original concrete route containing the actual Project UUID, family `project_action_use` and action `create-application-accounts`. [Create and inspect an application account](/guides/application-accounts#recover-an-uncertain-creation-result) explains its original-POST recovery and exact lookup context.

A grant lookup requires the exact grant-read family above. A weaker action-use guard cannot replace it. Lookup checks your current eligible-human exact use-and-grant authority before searching retained history. It does not repeat the recipient's eligibility or reviewed-revision check from the original assignment. A current group manager may replay an ordinary same-write result, but management alone cannot authorize this generic metadata lookup. Grant history has no deleted-target exception.

## Inspect historical use-only POST metadata

An older client may have sent the creation-only `POST /v1/projects/{project_id}/grants` for use-only `create-access-groups`. Preserve that original request's method, literal logical route, key, fingerprint, expiry and outcome. Its lookup identity uses the literal `{project_id}` route segment shown below, rather than the concrete UUID path used by exact-target PUT/DELETE.

For that historical request only, save this complete lookup input as `original-request.json` in its own example directory. Replace the illustrative scope IDs and key with the retained values:

<CodeGroup>

```json
{
  "installationId": "00000000-0000-4000-8000-000000000001",
  "organizationId": "00000000-0000-4000-8000-000000000002",
  "projectId": "00000000-0000-4000-8000-000000000003",
  "method": "POST",
  "requestedRoute": "/v1/projects/{project_id}/grants",
  "key": "grant-bob-1",
  "expectedAuthority": {
    "family": "project_grant_read",
    "actionId": "create-access-groups"
  }
}
```

</CodeGroup>

The common lookup programs below read this file without performing the old write. Current exact use-and-grant authority for `create-access-groups` on the original Project remains required. Retained history supplies neither renewed expiry nor new permission.

An uncertain original POST must never be automatically translated into PUT. POST rejected an existing assignment, while PUT can change its level. Missing, expired or unresolved evidence does not establish that the original failed or authorize a new mutation. Keep the original request evidence and make any later PUT a separate explicit decision with current authority and reviewed state.

## Recover an access-group change

For an ordinary group membership or manager change, preserve the original Project and group, exact method and route, request key and reviewed inputs. A currently authorized retry returns its original receipt without applying the relationship change again. Current management is checked before ordinary original-result disclosure. Management of a different group is insufficient.

An ordinary repeated group DELETE or full business-result replay also retains current-manager authorization. After deletion removes the group, its currently eligible original human has a separate retained path using the exact saved request identity or original operation ID. It returns only content-free deletion correlation and status. It does not restore management, expose the deleted group's relationships or authorize a full receipt replay.

That retained group-deletion path is independent of expired ordinary idempotency history. It preserves the captured original status expiry without renewal. [Manage access groups](/guides/manage-access-groups#recover-an-uncertain-change) explains the group workflow, while [retained deletion status](/guides/read-deletion-status#read-status-for-a-deleted-access-group) distinguishes synchronous group cleanup from Project deletion.

For this closed deletion lookup, use family `access_group_deletion` and action `delete-access-group`. These are matching inputs for the original deletion, not a grant of current management or a generic lookup for every group operation. The method is `DELETE` and `requestedRoute` is the concrete original path containing both actual UUIDs, without its revision query. A literal route template is not this deletion's canonical identity.

Save the following complete file as `original-request.json` in a separate group-recovery example directory. Replace all example UUIDs and the key with the values you retained before deletion. Keep earlier Project request files in their original directories. The common cURL and generated programs below can read this group-specific file without changing the client operation:

<CodeGroup>

```json
{
  "installationId": "00000000-0000-4000-8000-000000000001",
  "organizationId": "00000000-0000-4000-8000-000000000002",
  "projectId": "00000000-0000-4000-8000-000000000003",
  "method": "DELETE",
  "requestedRoute": "/v1/projects/00000000-0000-4000-8000-000000000003/access-groups/00000000-0000-4000-8000-000000000005",
  "key": "support-knowledge-delete-1",
  "expectedAuthority": {
    "family": "access_group_deletion",
    "actionId": "delete-access-group"
  }
}
```

</CodeGroup>

Retain the installation ID from trusted target registration or the installation operator, and the Organization ID from your own Organization-access read. A new group ID, current alias, changed defaults or replacement key cannot reconstruct the original binding. The reviewed revision remains part of the original DELETE request, but is not a field in this read-only lookup body.

An authorized exact retained match returns `outcome: "retained"` with the existing content-free deletion-status fields. For a settled group deletion, admission, blocked access and group cleanup are confirmed. `jobState` and `applicationShutdownComplete` are null. It returns no group Name, membership, manager inventory or business receipt. Use the same currently eligible original human. Another manager or administrator cannot inspect that human's hidden deletion history.

## Send the lookup

Choose one example below. Each reads `original-request.json`, authenticates the lookup, and observes the result without resubmitting the original operation.

<CodeGroup>

```shell {{ title: "cURL" }}
curl --silent --show-error --fail-with-body \
  --max-time 5 \
  --request POST \
  --url "$INFRAMELD_URL/v1/operations/lookup" \
  --header @- \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json' \
  --data-binary @original-request.json <<EOF_HEADERS
Authorization: Bearer ${INFRAMELD_TOKEN}
EOF_HEADERS
```

```python
# Save as lookup.py. Run with: python lookup.py
import asyncio
import json
import os
from pathlib import Path

import httpx
from inframeld_sdk import ApiClient, Configuration
from inframeld_sdk.api.operations_api import OperationsApi
from inframeld_sdk.exceptions import ApiException
from inframeld_sdk.models.original_operation_lookup_request import (
    OriginalOperationLookupRequest,
)


async def main() -> None:
    body = OriginalOperationLookupRequest.model_validate(
        json.loads(Path("original-request.json").read_text())
    )
    configuration = Configuration(host=os.environ["INFRAMELD_URL"])
    async with ApiClient(configuration) as client:
        try:
            response = await OperationsApi(client).lookup_original_operation_with_http_info(
                original_operation_lookup_request=body,
                _headers={
                    "Authorization": f"Bearer {os.environ['INFRAMELD_TOKEN']}"
                },
                _request_timeout=5.0,
            )
        except ApiException as error:
            print(f"Lookup could not be read: HTTP {error.status}")
            print(error.body)
            raise SystemExit(1) from error
        except httpx.HTTPError as error:
            print("Lookup did not produce a usable response. Keep the original request.")
            raise SystemExit(1) from error

        result = response.data.actual_instance
        if result is None:
            raise RuntimeError("Lookup returned no outcome")
        print(result.outcome)
        print(result.to_json())


if __name__ == "__main__":
    asyncio.run(main())
```

```typescript
// Save as lookup.ts in an ESM project with the locally built SDK installed.
// With Node 26, run with: node lookup.ts
import { readFileSync } from "node:fs"
import {
  createClient,
  lookupOriginalOperation,
  type OriginalOperationLookupRequest,
} from "@inframeld/sdk"

const baseUrl = process.env.INFRAMELD_URL
const token = process.env.INFRAMELD_TOKEN
if (!baseUrl || !token) {
  throw new Error("Set INFRAMELD_URL and INFRAMELD_TOKEN")
}

const body: OriginalOperationLookupRequest = JSON.parse(
  readFileSync("original-request.json", "utf8")
)
const client = createClient({ baseUrl, timeoutMs: 5000 })
const result = await lookupOriginalOperation({
  client,
  body,
  headers: { Authorization: `Bearer ${token}` },
  responseStyle: "fields",
  throwOnError: false,
})

if (result.error) {
  console.error("Lookup could not be read:", result.error.kind)
  console.error("HTTP status:", result.response?.status)
  if (result.error.kind === "api") {
    console.error(result.error.body)
  } else {
    console.error(result.error.message)
  }
  process.exitCode = 1
} else if (result.data) {
  console.log(result.data.outcome)
  console.log(JSON.stringify(result.data, null, 2))
}
```

```rust
// Save as src/main.rs in a separate Cargo project.
// Add the locally built inframeld-sdk as a path dependency, plus:
// serde_json = "1"
// tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
// Run from the directory containing original-request.json: cargo run
use inframeld_sdk::{HttpClient, OriginalOperationLookupRequest};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let body: OriginalOperationLookupRequest =
        serde_json::from_str(&std::fs::read_to_string("original-request.json")?)?;
    let base_url = std::env::var("INFRAMELD_URL")?;
    let token = std::env::var("INFRAMELD_TOKEN")?;
    let client = HttpClient::new()
        .with_base_url(base_url)
        .with_header("Authorization", format!("Bearer {token}"));

    match client.lookup_original_operation(body).await {
        Ok(response) => {
            println!("HTTP {}", response.status);
            println!("{}", serde_json::to_string_pretty(&response.body)?);
        }
        Err(error) => {
            if let Some(context) = error.api() {
                eprintln!("Lookup could not be read: HTTP {}", context.status);
                eprintln!("{}", context.body);
            } else {
                eprintln!("Lookup did not produce a usable response: {error}");
            }
            return Err(error.into());
        }
    }
    Ok(())
}
```

</CodeGroup>

The HTTP example uses a five second deadline. The Python and TypeScript examples set the same deadline. The Rust client's default is five seconds. These SDK defaults do not retry the operation automatically.

If your application uses browser cookies instead of a bearer token, send its trusted `Origin` and `X-Inframeld-CSRF: 1`. Browser SDK requests also need the existing installation's cookie and CORS configuration. Do not copy a browser session cookie into a shared example.

## Interpret the result

A successful lookup returns HTTP `200`. Check `outcome` to decide what the response establishes.

| `outcome`               | What it means                                                                                                       | What to do next                                                                                                     |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `completed_synchronous` | The original operation completed. The record includes its operation ID, result classification, and original expiry. | Use the operation ID to investigate the original result. Lookup does not replay its contents.                       |
| `accepted_asynchronous` | The original request was accepted. Its job reference may be known or unknown. Dispatch is not established.          | Keep the operation ID and any job ID. Neither confirms that a job started or finished.                              |
| `in_progress`           | The original synchronous operation has not finished.                                                                | Keep its operation ID. A later lookup can observe the same original request.                                        |
| `recovery_required`     | The original operation requires recovery. The record does not establish asynchronous acceptance.                    | Keep the operation ID and ask the installation's operator to investigate.                                           |
| `retained`              | The closed access-group deletion lookup found permitted content-free original deletion status.                      | Interpret its separate facts and captured expiry. It is not a full deletion receipt or permission to repeat DELETE. |
| `unresolved`            | Lookup cannot establish an authoritative retained match.                                                            | Keep the original details and investigate. Do not assume the operation never happened.                              |

For example, a completed response has this shape. The operation ID and expiry below are illustrative:

<CodeGroup>

```json
{
  "outcome": "completed_synchronous",
  "operationId": "example-original-operation",
  "classification": "safe_result",
  "idempotencyExpiresAt": "2030-01-01T00:00:00Z"
}
```

</CodeGroup>

`classification` describes the kind of completed result: `safe_result`, `issued_secret`, or `answer_receipt`. Lookup does not return the original secret, answer, or response body.

For an original Project action accepted for background work, lookup may identify its job. This complete response is illustrative, with example IDs and expiry:

<CodeGroup title="Illustrative accepted response">

```json
{
  "outcome": "accepted_asynchronous",
  "operationId": "example-background-operation",
  "admission": "confirmed",
  "jobReference": {
    "jobId": "00000000-0000-4000-8000-000000000004"
  },
  "dispatch": "not_established",
  "idempotencyExpiresAt": "2030-01-01T00:00:00Z"
}
```

</CodeGroup>

Keep `jobId` with the original operation ID and installation. It identifies the original work, but does not certify dispatch, execution state or completion. It grants no permission for a later job read, and a job-inspection endpoint is not available yet.

If a permitted reference cannot be established, `jobReference` is the string `"unknown"` and the result still confirms acceptance. That does not mean the operation has no job or that nothing was dispatched. Lookup never creates work to fill a missing reference.

An unresolved response contains only:

<CodeGroup>

```json
{
  "outcome": "unresolved"
}
```

</CodeGroup>

It does not say whether history was absent, expired, or did not match the full original identity. Repeating a successful lookup does not extend the original record's expiry. An accepted asynchronous result remains a statement about original acceptance, even if the job later changes state. Lookup does not provide a job URL or current job progress.

## Read a known Project deletion operation

If you already have the original deletion operation ID, [read its retained deletion status](/guides/read-deletion-status). That separate content-free reader permits the currently eligible original initiating human to read after ordinary Project membership disappears. It grants no cancellation, continuation or restored access.

If the first [Project-deletion response](/guides/delete-project) was lost before you saved its operation ID, use the same lookup clients above in a separate example directory, saving this request as `original-request.json`, the filename those programs read. Keep any other operation’s saved file unchanged. Replace these illustrative values with the exact context retained before your DELETE. The concrete route contains the original canonical Project UUID and excludes the `expectedAccessRevision` query.

<CodeGroup>

```json
{
  "installationId": "00000000-0000-4000-8000-000000000001",
  "organizationId": "00000000-0000-4000-8000-000000000002",
  "projectId": "00000000-0000-4000-8000-000000000003",
  "method": "DELETE",
  "requestedRoute": "/v1/projects/00000000-0000-4000-8000-000000000003",
  "key": "support-project-deletion-1",
  "expectedAuthority": {
    "family": "project_deletion",
    "actionId": "delete-project"
  }
}
```

</CodeGroup>

This lookup-only guard checks your current eligible-human credential and recovery state before matching the original initiating human and exact saved scope. It can return only retained content-free deletion status or the uniform unresolved result, including after ordinary membership loss. It does not require current Delete authority for this narrow read, supply that authority or return the full admission receipt.

An ordinary repeat of the DELETE still requires current membership and exact Delete authority and uses the original revision and key. Do not substitute a weaker guard or treat retained status as permission to send that write. An unresolved result proves neither completion nor absence and never authorizes another deletion.

## Handle an error or lost response

Error responses use `application/problem+json`. Read the HTTP status and problem details before deciding how to proceed. An SDK decoding error can also occur with HTTP `200`, so check the SDK error even when the status looks successful.

| Status or failure                        | Next step                                                                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `400` or `422`                           | Check the original identifiers, method, route, key, and authority guard. Remove unknown fields and duplicate JSON keys.                                |
| `401`                                    | Use a valid current human credential for this installation.                                                                                            |
| `403` or `404`                           | Check current eligibility and the authority required by the selected original family. A hidden scope is not evidence that the original request failed. |
| `413`                                    | Reduce the JSON body to the supported lookup fields, within 32 KiB.                                                                                    |
| `415`                                    | Send `Content-Type: application/json`.                                                                                                                 |
| `503`                                    | The lookup's dependencies are unavailable. Check installation health and try the same lookup later.                                                    |
| Timeout, disconnect, or decoding failure | Treat the result as unknown. Preserve the original details and investigate or repeat the lookup.                                                       |

Repeating **lookup** with the same original identity is a read. Submitting the original business operation again is a separate decision that these observations do not authorize.
