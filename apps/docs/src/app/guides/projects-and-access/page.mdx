## Understand access before changing it

Project names are exact selectors. IDs are permanent. Display names are labels. Read [Projects, people and permissions](/product/projects-and-permissions) for the distinction between sign-in, membership and action grants.

Human admission uses current Organization `admit-users` authority and verifies the requested Kratos identity. It creates no Project membership, grants or starters. It is separate from first-administrator bootstrap and provider account registration.

Membership changes use current Project `manage-project-members` authority. Adding an admitted human gives bare membership. Removal clears only that recipient's received access within the Project and preserves required human responsibilities. Rejoining restores no old grants or group roles. [The guide](/guides/manage-project-members) explains the current inputs, departure guards and original receipts.

[Project action-grant reads](/guides/list-project-action-grants) require current use and grant authority for the exact action on the Project. They list stored assignments, including suspended recipients, rather than effective permissions or every action the recipient may use. Your own-access read needs current eligible-human membership and returns a current Access revision, not a permission snapshot. Project grant PUT/DELETE require exact use-and-grant authority again, preserve original results and prevent removal of the last eligible exact-action grantor. `canGrant: false` means use-only, not removal. [The other Access-owned grant tasks](/guides/manage-action-grants) cover Organization permissions, group document actions, human application-account administration and eligible Project-recipient discovery.

Project creation uses your current Organization `create-projects` permission. It creates an ordinary Project with its membership and eighteen initial assignments. Private-starter provisioning remains separate unfinished work. The [API reference](/api-reference/projects-and-access) lists the operations you can call today.

Access-group creation uses current Project `create-access-groups` authority and gives the creator ordinary membership and management together. Current managers administer that group's relationships and protect the last eligible human manager. Demotion retains membership, while membership removal also removes management. [Manage access groups](/guides/manage-access-groups) covers scoped inspection, safe lists, unused-group deletion and the original initiator's content-free recovery path. [Document-action grants](/guides/manage-action-grants) are distinct from group membership and management. Changing which groups a document allows belongs to the document workflow.

Application-account creation gives an integration its own permanent identity in one Project. It starts without received action grants, document groups or keys. Its creator receives three exact account-administration grants. [The guide](/guides/application-accounts) explains creation, current metadata visibility, safe key reads and recovery after response loss. [Share an account-administration action](/guides/manage-action-grants) when another human needs that responsibility. Issuing or using application credentials and retiring an account remain separate unfinished operations.
