# Inframeld Access and Model Connections

Keep identity, application permission and outbound provider capability separate. They often meet in one setup or serving task, which justifies one skill, but Access does not become the owner of indexing or provider SDK behavior.

## Scope and sources

Default to read-only assistance. This skill grants no permission to edit code, issue credentials, contact a provider or change grants. Paths are repository-root relative. Read the applicable guide section and owning ADR before a detailed claim.

- `docs/ARCHITECTURE.md`: first-use, users/integrations and ModelGateway sections.
- `docs/adr/ADR-0005-api-enforced-tenancy-and-authorization.md`: Access policy; section 11 owns the administration matrix and section 12 owns the accepted relational data model, constraints, and lifecycle examples; section 13 provides the complete Access foundation table map, records the accepted application-account extension and write-coordination approach, and distinguishes remaining physical proposals.
- `docs/adr/ADR-0006-byok-provider-boundary.md`: connections, roles and egress.
- `docs/adr/ADR-0020-persistent-outbound-credentials.md`: accepted persistence requirement and accepted PostgreSQL/PyNaCl encrypted storage.
- `docs/adr/ADR-0019-default-onboarding-and-first-publication.md`: accepted private access defaults and accepted reversible publication modes.
- Read ADR-0007 for secret-bearing idempotency, ADR-0017 for feedback rights, ADR-0018 for MCP credentials and ADR-0014 for deletion/revocation as needed.

## Language and ownership

A Principal is the stable authenticated human/application actor. Organization and Project bound ownership. Action grants authorize operations; document-group allowlists narrow readable content. The access context has a verified actor and an optional verified delegated subject. In v1 fixed integrations have no subject.

An incoming integration credential authenticates a caller and is verified from a stored hash. An outbound provider credential is a secret the application must retrieve to call a model; hashing alone cannot support that use. A Connection records an approved endpoint and immutable semantic revisions. Embedding and generation are separate model roles, potentially sharing one connection and credential. Indexing owns EmbeddingProfile; Pipelines owns frozen generation configuration; Evaluation owns judge settings. None embeds the plaintext key.

Access owns principal/project/group/grant consistency. Connection and credential management are shared application capabilities with scoped authorization and separate secret-resolution infrastructure, not new proposed microservices. Do not infer a class/aggregate per grant, token or profile from these concepts.

## Security and lifecycle rules

1. Kratos owns human identity/sessions, including optional deployment-level external OIDC sign-in in OSS. Inframeld owns application authorization. Identity-provider email/groups do not automatically grant rights. Kratos is not Inframeld's OAuth issuer; Hydra and delegated-user flows remain deferred.
2. Incoming application credentials are opaque, expiring and revocable; store only a verifier and safe metadata. Permissions belong to the application account. Every valid key uses its current permissions, including later authorized additions/removals; v1 has no per-key action or group limits. Check current authority on each request and at the existing final dispatch/disclosure points. Credential validity, installation/audience binding and adapter restrictions still apply. Rotation preserves the stable principal. Distinct Query/Build/Evaluate/Manage releases/feedback grants do not imply admin rights. Lost show-once secrets cannot be recovered by idempotency replay.
3. Fixed integration access is its own configured ceiling. A user ID, affinity key, MCP argument or claimed group never verifies a human or expands scope. Everyone using SupportBot's authority can reach its allowed knowledge. Future verified delegation intersects actor ceiling with subject rights, not unions.
4. Project/action checks precede document access. PostgreSQL owns groups and allowlists. Current policy protects historical content, citations, final context, evaluation evidence, receipts and feedback. Receipt checks include uncited sources. Apply checks before retrieval and at the documented final dispatch/disclosure points; acknowledge already-admitted network races.
5. Every Inframeld model call uses ModelGateway. Custom/private OpenAI-compatible endpoints remain OSS. Operator-approved origins, DNS/destination checks, TLS/custom CA and bounded capabilities protect egress. A per-query URL is not a connection, and “compatible” is not proof of embedding support.
6. Probe embedding and generation roles separately. Share a provider connection when appropriate so the user does not re-enter its credential. Freeze semantic connection/model references in profiles/versions. Credential-only rotation preserves semantics; changed endpoint/model meaning does not. Under ADR-0020's accepted storage design, key replacement/removal invalidates its previous role-probe status. Changing endpoint origin requires a new connection and explicit credential provision; never forward the saved key automatically.
7. Persistent application-entered provider keys are required. Saved plaintext never returns to Studio or enters domain snapshots, jobs, logs, evaluator evidence, receipts or parser sandboxes. Only scoped credential operations create/replace/remove it; outward responses contain safe metadata.
8. The ADR-0020 PostgreSQL adapter using PyNaCl `Aead` and a separately supplied root key is accepted. Preserve its fail-closed behavior, authenticated resource binding and narrow plaintext-resolution boundary. Mounted files can supply bootstrap/root keys but do not replace the required runtime credential API. Do not add OpenBao or invent cryptography by default.
9. Missing credentials, root keys or required capabilities make affected calls unavailable; no silent default provider/key/model is selected. Central retry policy forbids hiding an ambiguous chargeable call in a vendor SDK retry.

## Accepted issue #24 access decisions

The 23–24 September 2026 analysis accepted the following policy. Read [ADR-0005 section 11](../../../docs/adr/ADR-0005-api-enforced-tenancy-and-authorization.md#11-bound-administration-grants-and-recovery) for the full decision, consolidated administration/visibility matrix, and remaining workflow questions. These are design decisions, not implemented or verified behavior.

- **Bound administration.** Project/installation administration grants neither document reading nor arbitrary sharing authority. Prevent indirect escalation through manager appointments, grant changes, and integration credentials. Group managers control disclosure; lack of ordinary read permission does not make content confidential from someone who can grant it to another account.
- **Separate human admission, suspension and restoration.** Admit users, Suspend users and Restore users are separate human-only permissions for the installation's organization, each with the usual two grant levels. Secure first-administrator bootstrap explicitly assigns their initial can-use-and-grant authority to the verified first administrator; keep ordinary scoped grants and handover rules. Admit users invites/approves people into controlled admission and private starter setup, without existing-project or installation-administration rights and without bypassing an existing suspension. Suspend users may immediately block any human in the installation, including an administrator or last manager/grantor, while retaining recorded rights; it needs no authority over the target's underlying grants and does not permit restoration. Restore users deliberately restores the same legitimate person only after required identity verification/security review and, for compromise, replacement of compromised sign-in methods and old-session invalidation. Removed rights stay removed. Check the actor's current admitted/unsuspended status, action grant and installation scope at each mutation. These permissions do not imply one another, document reading, identity takeover or server-operator reassignment. Kratos owns identity recovery; Access owns admission/status and remaining rights.
- **Bound project creation.** Create projects is a separate human-only permission for the installation's organization, using the usual two grant levels. Secure bootstrap explicitly assigns can-use-and-grant Create projects to the verified first in-app administrator, alongside the separate Admit users, Suspend users, and Restore users grants. This is an ordinary delegable permission, not an unrestricted administrator role or a separate post-bootstrap operator step. It creates additional projects; automatic private starter provisioning neither requires nor grants it. Record the new project creator's membership and explicit can-use-and-grant assignments for the agreed project administration actions: Manage project members, Create access groups, Create application accounts, Create Pipeline, Create Deployment, Manage upload defaults, and Delete project. Preserve each action's additional checks. These are ordinary initial grants, not an irrevocable creator role or wildcard over future actions/resources, and give no authority over existing projects or their documents.
- **Authorize whole-project deletion explicitly.** Delete project is a separate human-only permission per project, at the usual two grant levels and explicitly assigned to its creator initially. Check current membership/status, scoped authority and target at tombstone commit. It authorizes erasing all project-owned contents, including unreadable private data, without collecting per-resource Delete grants or group management. It never grants reading/sharing, and ordinary project/installation administration does not imply it. Follow ADR-0014: block affected access/work first, clean up resumably within scope, preserve out-of-scope data and apply retention rules. No replacement manager/grantor is needed for resources deleted with the project. Normal individual-resource deletion checks still apply in surviving projects. Do not leak private contents via deletion status or promise immediate physical erasure.
- **Use peer group managers.** An existing manager may explicitly appoint another admitted human project member for that same group. The starter creator gets an explicit initial assignment. Require a replacement before the last manager deliberately leaves an active group; never block emergency suspension to preserve a manager count.
- **Bound group creation.** Create access groups is a separate human-only, project-scoped permission at the usual two grant levels. Authorized creation explicitly assigns the creator as the new group's first manager. It grants no authority over existing groups or documents. An existing document becomes accessible through that group only through the authorized policy-change rule below.
- **Delete only unused groups.** A currently authorized human group manager may delete their group only after no Document or active upload/source configuration references it. Resolve dependencies through their normal authorization rules, and check current authority and dependencies at commit, including concurrent changes. Deletion removes memberships, manager assignments, and group-specific grants; it never deletes/reassigns documents, changes their allowlists, or selects replacement defaults. No replacement manager or action grantor is needed when deleting the group itself. Historical audit attribution may retain its stable identifier.
- **Bound changes to document access.** Only a currently authorized human managing every same-project group in the current or proposed allowlist may change an existing Document's groups, including adding, retaining or removing groups. Keep the resulting allowlist nonempty. Reading/editing content alone is insufficient. Check persisted current policy and authority at commit; the policy protects historical versions too. Require one person with all necessary manager authority in v1, without a multi-person approval workflow. Initial new-document policy follows the separate Add documents rule.
- **Bound new-document admission.** Add documents is a permission per access group that its manager may grant without appointing another manager. Use the usual two grant levels; applications receive can use only. Require it for every selected same-project group, including defaults, with a nonempty initial allowlist and normal membership/credential checks. This permits bounded initial policy assignment by humans or applications, not changes to existing policies. It grants no existing-document reading, replacement, deletion, group administration, Build or Manage releases. Names and deduplication cannot bypass this boundary.
- **Bound project upload defaults.** Manage upload defaults is a separate human-only, project-scoped permission at the usual two grant levels. Changing defaults also requires management of every group in the persisted current or proposed default allowlist, including retained groups. Keep the result nonempty and within the project, and check current settings and authority at commit. Neither this permission nor group management alone suffices; granting the permission confers no group management. Changes affect future admissions only. Existing policies stay intact, and every new admission still needs Add documents on all selected groups plus current membership/credential checks, without a fallback audience. Source-specific configuration authority remains separate and unresolved.
- **Bound existing-document updates.** Update documents is a separate permission per access group, grantable by its managers at the usual two levels; applications receive can use only. Require it for every group in the nonempty persisted current allowlist, checking current authority, membership and credential limits at commit. Preserve the Document identity and access groups; changed content creates a new immutable version, while unchanged-content idempotency remains. Add alone cannot replace content. Update grants no deletion, audience changes or group administration; reading, Build and Manage releases remain separate.
- **Bound document deletion.** Delete documents is a separate permission per access group, explicitly grantable by its managers at the usual two levels; applications receive can use only. Require it for every group in the nonempty persisted current allowlist, with current membership/credential checks at tombstone commit. Add and Update never imply Delete. It deletes the Document across all versions, distinct from removing a group or changing a future collection selection. Follow ADR-0014: block access and invalidate affected serving state before resumable cleanup; dependent deployments/evidence may become unavailable.
- **Use two action-grant levels.** Default to can use. Can use and grant also permits explicitly assigning either level to another eligible human for the same action and scope. It permits revoking others' grants or downgrading them to can use within that same action and scope, regardless of the original grantor. Applications receive can use only. Do not infer sharing authority from ordinary use or introduce recursive delegation levels.
- **Name individual resources.** Pipeline/Deployment operations require explicit resource assignments, project membership, and separate document checks where applicable. No grant covers all current/future resources in a project. Creating Pipelines and creating Deployments are separate project permissions; authorized human creation records initial can-use-and-grant assignments only for the new resource. Existing resources and document/model access are unaffected. For human creation, Create Deployment authorizes selecting the new Deployment's ready, same-project, compatible initial serving version. Commit the Deployment, its initial version, and the creator's explicit initial grants together, including can-use-and-grant Manage releases. Later releases need that specific Deployment's Manage releases permission; creator grants remain transferable/revocable. Before the default Deployment exists, first automatic publication checks current Create Deployment on the project alongside Build and input/mutation rights, with the existing mode/revision/readiness guards. No separate first-release permission, placeholder Deployment, future-resource grant, or authority over another existing Deployment is added. A competing creation cannot turn creation intent into permission to update its Deployment.
- **Separate deletion from ordinary operations.** Each Pipeline/Deployment has its own Delete permission, using the same can-use and can-use-and-grant levels. Editing, building, and publishing never imply Delete. This records authorization, not deletion mechanics or retention rules.
- **Separate deployment editing from release control.** Manage releases is the resource-specific permission formerly described as Publish/deploy: it covers publication, rollback, candidate/canary control, publication-mode switches and automatic-update input selection. Use the same two grant levels; no release-operation-specific grants in v1. Deployment Edit configuration covers non-serving details such as name/description. Manage releases does not imply Delete, Pipeline Build or document access; combined operations still check every required permission.
- **Keep administration human-only.** Appropriately authorized humans alone change permissions or manage incoming application credentials. Applications cannot invite people, grant access, appoint managers, or issue/manage those credentials. This does not replace ADR-0020's outbound-provider credential policy.
- **Create applications without inherited access.** Create application accounts is a separate human-only, project-scoped permission at the usual two grant levels. Create the application in that project without document-group access, operational action grants, or an automatic key; never copy the creator's permissions. Explicitly assign the human creator can-use-and-grant authority to issue and revoke keys and Delete application account for this new application only, in the same creation operation. The application itself receives no human administration rights. Assign its operational/group permissions and first key through the normal authorized operations; issuance still checks all current application permissions. Creation gives no authority over existing applications; deletion relies on its explicit initial grant, not an irrevocable creator privilege. Keep it separate from human-only Manage project members so integration setup and employee onboarding can be delegated independently.
- **Delete application accounts separately.** Delete application account is a separate human-only permission per application, at the usual two grant levels, explicitly assigned to its creator initially. Check current membership, suspension status, scoped authority and project binding at commit. Permanently stop the account, revoke all keys and remove its permissions/group access and human administration grants scoped to it; prevent concurrent issuance or grants from restoring use. No replacement administrator is required for the deleted account. Preserve project data it created and historical attribution under ADR-0014 retention/erasure rules; name reuse must not revive its principal or keys. Key issuance/revocation alone does not authorize account deletion.
- **Bound credential issuance and replacement.** Require a currently authorized human with both issuance permission for the specific application and authority to grant all of that application's current permissions: every action, resource scope, and document-group access. Ordinary use/read access or issuance permission alone is insufficient. There is no smaller per-key scope in v1. Check current authority, membership/suspension and application scope at issuance commit, including concurrent grant changes; replacement requires the same checks without relying on an earlier approval. Issuance does not change application grants. Preserve the principal and show-once secret behavior. These checks govern new issuance, not a permanent ceiling on existing keys. Revocation uses its separate permission below; credential lifetime limits remain undecided.
- **Replace keys with bounded overlap.** Permit at most two usable keys per application, counting unexpired, non-revoked credentials across audiences. Enforce this against concurrent issuance; retained expired/revoked metadata uses no slot. Create a second key, update/test the integration, then explicitly revoke the old key. Each step uses its existing issuance/revocation authority; add no Rotate permission or automatic revocation on creation, and do not evict an existing key to free a slot. Credential expiry still applies. Revoke compromised keys immediately rather than wait for replacement. Many concurrent keys were deferred in favor of one integration account with a spare for replacement; AWS deactivation/reactivation is not implicitly adopted.
- **Separate key revocation from issuance.** Revoke application keys is a separate human-only permission for each application, at the usual can-use and can-use-and-grant levels. Require current membership, unsuspended status, scoped revocation authority and a matching credential/application binding at commit. It does not require issuance permission or authority to grant the application's permissions. Issuance and revocation do not imply each other. Revocation grants no ability to read documents, act as the application, issue replacements or change grants. Allow revoking the last usable key without a replacement, even if this stops the integration. Preserve the application account, its grants and human administrators; their separate handover rules remain. Enforce revocation at subsequent authentication and applicable authorization checks, without claiming to recall dispatched work. The combined Manage keys alternative was rejected so shutdown and issuance can be delegated separately.
- **Keep permissions on the application account.** Valid keys use the account's current fine-grained permissions. Authorized additions and removals affect existing keys without replacement, subject to credential validity, installation/audience binding and adapter restrictions. Granting HR access to SupportBot authorizes everyone able to use a valid SupportBot key, including a previous issuer who could not grant HR access; a key does not inherit its issuer's current personal rights. Use separate application accounts when integrations need different access boundaries. Multiple keys distinguish credentials for rotation/revocation, not action/group scopes. Fixed per-key ceilings were considered and deferred to keep one permission layer in v1. AWS illustrates the identity/permission separation; do not import its full IAM model or weaken Inframeld's issuance checks.
- **Bound project membership management.** Manage project members is a separate human-only, project-scoped permission at the usual two grant levels. It adds already admitted humans to that project or removes human members; it does not admit installation accounts. Membership alone grants no document-group, manager or Pipeline/Deployment rights. Removal clears the member's own project access and preserves the existing replacement rules and grants they made to others. Application-principal membership remains part of the integration-administration design.
- **Do not cascade a grantor's departure.** Grants, including peer-manager assignments, remain until explicitly revoked. Removing a project member removes that member's own grants/group memberships; later readmission never revives them. Preserve grants they made to other people and attribution of the original grant.
- **Preserve an action grantor.** While a resource exists, ordinary departures, removals and downgrades must leave an active eligible human able to grant each affected action in its owning scope: a current project member for project/resource grants, or an admitted installation user for installation-level grants. Require a replacement first; suspended accounts and applications do not count. Apply the rule to project removal and concurrent grant changes too. Emergency suspension always remains possible, with account or scoped operator recovery if needed.
- **Distinguish the server operator from an in-app administrator.** The server operator controls the host, Compose deployment, database, storage, secrets, and backups, and is inside the infrastructure trust boundary. Application permissions cannot prevent that operator from inspecting data or overriding state through privileged server access. An in-app administrator has only explicit scoped application permissions. The same human may do both jobs, but their ordinary app session follows its grants. Do not add an unrestricted UI superadministrator; use the accepted separate maintenance recovery path.
- **Limit project and application visibility.** Current project members may see that project's name and ID, subject to current status and applicable credential checks; installation actions such as Admit users or Create projects do not reveal other private projects. Humans with Issue keys, Revoke keys, or Delete application account on a specific application may see its name and ID, with current membership/status checks. Authorized grantors also see eligible applications through the limited recipient directory. Neither route reveals keys or unrelated application rights; project membership alone does not reveal every application.
- **Separate basic visibility from sensitive details.** Any currently effective permission on a Pipeline/Deployment reveals its name, ID and basic availability status, including in lists, without another visibility grant. Configuration, documents and other sensitive details require their own checks; linked resources do not become visible automatically. Omit inaccessible resources from lists and return safe not-found results for direct references. Use access denied when existence is permitted but the requested action is not. Reuse RFC 9457 mappings to 404/403; project membership alone does not reveal all resources.
- **Limit access-group visibility.** Show a group's name and ID only to its current members, managers, or callers with an action permission on that group, with current membership/status/credential checks. Otherwise apply hidden-list and safe-404 behavior. This reveals neither documents nor the membership list. Group managers may inspect their group's members and managers. Do not list every group merely because someone belongs to the project.
- **Limit permission and recipient views.** Humans may inspect their own permissions. A human able to grant an action may inspect that action's assignments and grant levels within the exact scope they administer, without unrelated recipient permissions or the resource's whole sharing list. Group-manager membership views remain separate. Authorized project grantors may use a basic directory of eligible project humans/applications to choose recipients: stable ID, display name and principal kind, not their other memberships, access, credentials or private contents. This does not create an installation-wide directory or a view for all project members.
- **Expose safe key metadata to key administrators.** Humans with issuance or revocation permission for an application may list its key identifiers, safe prefixes, creation/expiry dates and status, subject to current membership/status/scope checks. Do not return secrets or verifiers/hashes through this view. The extra authority to grant all application permissions is required for issuance, not metadata listing. Directory visibility or application deletion alone does not grant this view. Defer a separate View application keys permission and add no MCP administration tools.
- **Allow read-only configuration review.** Each Pipeline/Deployment has an independently grantable View configuration permission at the usual two grant levels. It permits inspecting settings without editing or running operations. Query alone does not permit configuration browsing. Document and linked-private-resource checks remain separate, and saved API keys stay hidden. Do not introduce a grant per configuration field. Edit configuration includes viewing the same resource, subject to the same protected-data checks. Revoking View does not remove viewing while Edit remains; revoking Edit leaves read-only access only if View remains. Ordinary Edit grants no sharing authority. Granting Edit passes on its included viewing capability, but managing standalone View grants still requires View grant authority. Keep this implication fixed; exact readable/editable fields remain undecided.
- **Separate suspension from removal.** Immediately block a compromised account while retaining its recorded permissions. Recover the same principal, replace compromised sign-in methods, invalidate sessions, review suspicious changes, then deliberately lift suspension. Password reset alone is insufficient; removed grants never return.
- **Allow narrow operator recovery.** If the manager or last action grantor cannot return, privileged server-operator maintenance may assign a verified replacement for an exact group or restore can-use-and-grant authority for the specific missing action/resource. Preserve scope and record actor/reason/change. Keep the compromised account blocked. Ordinary in-app administrators have no takeover right. The operator is trusted with infrastructure and reassignment power; auditing does not eliminate that trust.

Do not silently decide the remaining action catalogue, exact readable/editable configuration fields and protected-reference handling, history visibility and visibility of other resource types, remaining group/project/application-principal administration, remaining contributor and collection operations, credential lifetime limits, or detailed handover/recovery mechanisms. The accepted Create Deployment rule covers initial default creation and serving; preserve the required automatic first-use path with explicit initial grants and no placeholder Deployment or wildcard. Issue #24 owns the shared policy/contracts and constraints, not all later Epic 2 workflows or future Pipeline/Deployment functionality. Put new accepted decisions in the owning ADR and guide as well as this summary.

## Accepted access data model

The 24 September 2026 discussion accepted one shared principal model for humans/applications and individual relational grant records with explicit target relationships. Read [ADR-0005 section 12](../../../docs/adr/ADR-0005-api-enforced-tenancy-and-authorization.md#12-persist-the-accepted-access-data-model) before proposing schema or Access contracts. It is the detailed source; the logical model, target-specific grant tables, unique recipient/action/target assignment, `can_grant` boolean, fixed code-owned action catalogue, and separate current-state/audit storage are accepted. They are not implemented tables. [Section 13](../../../docs/adr/ADR-0005-api-enforced-tenancy-and-authorization.md#13-proposed-access-foundation-table-map) provides the full 14-table foundation, keys and constraints, audit fields, lifecycle effects, and later-feature integration points. The developer accepted its small application-account extension with enforced project binding and its project-scoped write coordination with organization/project locks and scope revisions. Remaining field/type details, exact action identifiers, indexes, and event-specific audit fields still need implementation review; accepted design is not implemented behavior.

- **Keep v1 authorization in Access and PostgreSQL.** The review of the completed logical model explicitly retained product-owned policy; OpenFGA and PyCasbin are not selected. Read [ADR-0005's engine comparison](../../../docs/adr/ADR-0005-api-enforced-tenancy-and-authorization.md#introduce-a-general-authorization-engine-or-policy-language-now) for capability, operational, and consistency tradeoffs. Engines do not remove the application's handover, key-issuance, or concurrent-write invariants. Keep scoped queries/bulk checks, shared deny-by-default enforcement, and behavior tests; benchmark before adding authorization caches. Reconsider for real deep inheritance, independently deployed applications sharing authorization, or measured workload needs, not merely more documents/actions. Do not add a generic policy language or speculative engine adapters. Target-specific grant tables and separation of current grants from audit history are separately accepted; exact columns, audit details, and concrete concurrency implementation remain to be reviewed against the accepted protocol in section 13.
- **Keep the records distinct.** Principal identity/kind/status; verified external identity links; organization/project ownership; project membership; access groups; group membership; human peer-manager assignments; and scoped action grants serve different purposes. Project membership alone grants no action or document access. Group management and ordinary reading remain separate. One logical record does not mandate an aggregate, repository, or service.
- **Share policy, separate authentication.** Human identity links map verified authority/subject to a stable local principal, without email-based merging. Incoming application credentials identify their stable application principal; key metadata/verifiers and lifecycle belong to #30. Both kinds use the same access model, while human-only administration remains enforced. Do not duplicate human/application permission systems or copy grants onto keys.
- **Keep the accepted application-account extension.** `application_accounts` shares the principal ID and records the application's one owning project. Enforce project binding in membership relationships; humans may belong to several projects. This does not create a separate permission system or a right to move applications between projects. Keep principal/account/membership creation atomic, and prevent retained retired-account metadata from authorizing use. The alternative application-only field on every principal row was not selected.
- **Coordinate Access changes with the accepted scope guard.** Use short transactions: organization shared row lock, then affected project exclusive row lock, current policy/handover checks, required expected-revision check, state change, scope-revision increment, and audit commit together. Installation permission/status changes use the organization exclusive lock. All participating mutation paths must follow the protocol as delivered, including recovery, provisioning, later resource grants, issuance, and deletion. Take multiple project locks in stable ID order; bound waits and handle failure. Plain permission reads do not take exclusive administration locks, and no transaction spans user waits or external work. Narrower resource locks are deferred until measured contention warrants them. Scope revisions reject stale saves, including removal/regrant; they are not cached permissions. Concurrency behavior still needs implementation and tests.
- **Record grants individually.** Preserve recipient, one action, exact target/owning scope, and who assigned it and when. Enforce one current row per recipient/action/target. Use required boolean `can_grant`: the row supplies use authority subject to eligibility; true adds grant authority, while false is use-only, never an explicit deny. Applications cannot hold true. Attribution is not continuing control or a cascading delegation chain. The authoritative state is relational assignments, not a per-account JSON permissions document. Fixed implications such as Edit including View remain policy; no configurable roles or future-resource wildcard follows from the storage model.
- **Keep the action catalogue in code.** Each supported action declares its target kind and eligible recipient kinds. Reject unknown actions; no runtime custom-action table, role language, or policy-definition service. Exact identifiers and future actions still follow their owning decisions. Preserve fixed implications such as Edit including View without silently materializing extra assignments.
- **Separate grant tables by target type.** Organization, project, group, and each supported resource type have their own grant tables with real target/scope foreign keys. All actions for one target type share its table, such as Query and Manage releases in Deployment grants. Do not create a table per action/principal/resource instance, duplicate the policy algorithm, or pre-create future domain resources. The alternative single table with optional target columns was not selected.
- **Separate current grants from audit history.** Revocation deletes the current assignment; downgrade updates its level. Record who changed which recipient/action/target, what changed, and when in separate audit history, committing the state change and audit together. Authorization uses current assignments and normal eligibility checks, never historical rows. A regrant is a fresh assignment, not an inactive-row revival. Suspension still preserves grants while blocking the principal. Retention and history visibility follow the owning policy; this adds no event-sourced engine or blanket ban on resource tombstones.
- **Enforce scope in relationships.** Use real target references and organization/project-preserving foreign keys, including project identity with resource identity where required. A Support membership/grant/allowlist must not refer to a Finance group or resource. An unchecked resource-type/resource-ID pair is insufficient. Introduce resource-specific constraints with the real owning tables, not placeholder domain records. Current eligibility, grant authority, and last-manager/grantor rules still need application checks and transaction/concurrency protection; a foreign key does not authorize an actor.
- **Preserve lifecycle differences.** Suspension blocks use while retaining records; project removal clears the departing human's own access but preserves grants they made to others. Readmission does not restore removed rights. Key rotation preserves principal/grants; application deletion retires that account under its separate policy. Retained history cannot act as current authority. Creator assignments remain ordinary revocable grants.
- **Keep the implementation boundary explicit.** Section 13 records the accepted application-account extension and write-coordination approach within a map whose remaining physical details still need review. It is not an approved migration or implemented guarantee. Final table columns, status types, action identifiers, indexes, audit details, and concrete transaction implementation must follow the accepted grant-level boolean, unique assignment, catalogue ownership, target-type separation, current-state/history rules, and concurrency protocol. Do not store revoked grants alongside current assignments or implement later resource/key tables as placeholders. Access context is application-owned verified caller/scope information, not a Kratos/HTTP/ORM object or an authoritative client-supplied permissions payload. V1 has no delegated subject and rejects unsupported claims. Recheck current authority at the established dispatch, disclosure, and commit boundaries.

Use ADR-0005's Alice/SupportBot example when explaining the model: both belong to Support and its document group; Alice has separate group-manager and resource-grant assignments; SupportBot has Query on A, without releases on A/B or HR access. Removing Query versus group membership has different effects, and replacing a key changes neither. Verify those product behaviors and scoped database constraints as the owning features arrive; do not add structural/import-boundary tests or treat future resource examples as permission to implement their domains in #24.

## Accepted defaults and publication authority

The first useful answer without manual organizations/projects/groups is required. The accepted solution uses one provisioned organization, a securely claimed initial administrator and creator-private starter project/group, with ordinary ID-bound resources. Administrator status alone does not grant source reading. Other users and integrations receive access explicitly. Nonempty default allowlists apply on admission; changing a default does not retroactively make all documents public. Read ADR-0019 for the precise access boundary. The default starts automatic; new deployments default manual with an explicit automatic creation choice. Automatic update admission needs source/configuration rights, Build on the selected Pipeline and Manage releases on each specified existing Deployment; before the first default Deployment exists, human creation instead uses Create Deployment on the project and records the new resource's initial grants at creation. Queued work rechecks current authority before dispatch and publication. Mode alone never elevates upload-only or query-only access. Switching to manual invalidates pending publication; enabling automatic authorizes fresh selected inputs. Ordinary builds still have no release authority. The shared default-route shape does not alter these rules.
