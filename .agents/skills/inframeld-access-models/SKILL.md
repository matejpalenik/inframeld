# Inframeld Access Models

Explain who may act, which documents they may read, and how model credentials are kept separate from incoming application keys. Access owns local principals, memberships, groups, and action policy. ModelGateway owns the outbound model boundary. Do not blend those responsibilities.

## Essential boundaries

Shared Bearer transport does not merge credential families. Reject competing cookie/Authorization mechanisms and duplicate/malformed headers before provider I/O; never fall back. Human bearer checks remain current on every request, and `AccessContextDTO` remains principal-only. Recovery keeps product access blocked until both required provider outcomes are confirmed; otherwise active humans then resume automatically, while suspension still needs deliberate authorized restoration. Preserve original cleanup identity and never release a newer block from an older completion.

For CLI-first delivery and exact outstanding authority/identity contracts, read [the delivery plan](../../../docs/development/cli-delivery-plan.md), [Access automation eligibility](../../../docs/development/access-control.md#cli-automation-authority) and [configuration portability](../../../docs/development/configuration-portability.md). Preserve implemented Kratos/OIDC while adding Hydra and the required standalone account UI. Eligibility permits an explicitly granted operation, not human-only administration. Source/imported-case audiences need deliberate destination mapping; imported metadata never grants access. For pricing/limits, use [Model spending](../../../docs/development/model-connections.md#spending); the gateway owns enforcement, not client estimates.

Budget policy administration is a separate guarded **human-only** capability shared by setup, management and import. Applications may inspect permitted budget information and execute authorized work within limits, but cannot set, raise, lower or remove a project limit. Human identity still requires current project-specific authority. Follow [budget authority](../../../docs/development/model-connections.md#budget-policy-authority) and [import review](../../../docs/development/configuration-portability.md#destination-review): preserve is valid; a known-ineligible explicit apply is denied, not silently skipped or run as a saved human. Changes never reset usage, reservations or operation limits. Emergency suspension/restoration and scoped operator recovery have explicit delivery owners, not implicit coverage in ordinary membership administration. For CLI feedback, follow [CLI feedback capability](https://github.com/matejpalenik/inframeld/issues/191) and [feedback authority](../../../docs/development/answer-feedback.md#authorization): report access does not grant correction of another principal's rating, and current evidence checks filter totals as well as comments.

For direct Pipeline queries, read [Pipeline Query authority](../../../docs/development/access-control.md#pipeline-query-authority), [the lifecycle](../../../docs/development/pipelines-and-releases.md#direct-query) and [ADR-0052](../../../docs/adr/ADR-0052-separate-experimental-execution-from-release-ready-pipeline-builds.md). Query on a Pipeline executes its current working settings; Query on a Deployment uses its serving selection. Humans and applications are eligible for explicit grants on either resource. Separate query-trace inspection targets the exact Pipeline or Deployment and may cover other callers within current source access. Neither scope implies the other, and Query does not grant inspection. There is no Experiment resource. Current source/model access protects overrides, preparation and history. Policy-controlled automatic Build additionally needs target release authority; a selected workflow cannot silently downgrade after denial. The reviewed Access catalogue selects query/trace and six Evaluation use identifiers. The [fixed catalogue and creator assignments](../../../docs/development/access-contracts.md) now settle identifiers/targets/eligibility and explicit initialization. [Human case-audience administration](../../../docs/development/evaluation.md#case-audiences) and [non-query diagnostic deferral](../../../docs/development/observability.md#non-query-diagnostics) are settled. Exact public schemas/route mapping and runtime qualification remain delivery work; do not invent additional actions or automatic grants.

For traces, read [Access eligibility](../../../docs/development/access-control.md#trace-authority) and [recording/cleanup transitions](../../../docs/development/observability.md#trace-authority). The trace-access rules permit explicitly authorized human/application inspection with current source checks, but project tracing/retention mutation is human-only and explicit history deletion needs separate human deletion authority. Query, inspection and policy management are not interchangeable grants. Recording never depends on caller inspection. Imports may preserve destination policy; restricted apply must be denied without identity fallback. Automatic expiry and source erasure do not require fresh human approval per record. The query-inspection rules distinguish exact Pipeline and Deployment query-inspection grants; neither grants the other or unspecified non-query history access.

For generated tests and judges, read [Evaluation's explicit model bindings](../../../docs/development/evaluation.md#gateway) and [protected history](../../../docs/development/evaluation.md#history), with [ADR-0051](../../../docs/adr/ADR-0051-use-ragas-for-generated-tests-and-faithfulness-evaluation.md). Generator and judge may reuse existing authorized connections without another key, but no provider/model fallback is implicit. Ragas gets no credentials or independent clients; extraction, synthesis, judging and repairs all use ModelGateway. Generated questions/references inherit source protections. Recheck access before model egress and later disclosure; use the six reviewed exact-Pipeline Evaluation actions in the Access catalogue. Use [human Pipeline-scoped audience administration](../../../docs/development/evaluation.md#case-audiences) and [fixed creator assignments](../../../docs/development/access-contracts.md#initial-assignments); physical/wire implementation remains pending.

A principal is a stable human or application identity. Project membership, document-group reading, group management, and action grants are separate. A caller needs current account/membership/credential validity as well as the required action and document access. Default to denial; do not accept caller-supplied authoritative groups or permissions. Kratos verifies human identity, not product grants.

Keep [query denial separate from empty evidence](../../../docs/development/access-control.md#empty-evidence-scope). After successful Query authorization, an empty permitted source set takes the ordinary no-evidence path without a Chroma search. A forbidden query, empty saved document allowlist or lost access to a protected evidence bundle still denies the relevant operation; never hide a permission failure as a successful empty read.

Hydra is selected for first-party human CLI OAuth/OIDC, not deferred installation-wide. Kratos retains identities/browser sessions; both human paths resolve the same principal. Require private access-token introspection, current Kratos eligibility and local admission/state before authorization. Keep cookie CSRF, no credential-kind fallback, OS-store target/account isolation and documented refresh/revocation failure behavior. The inspected cookie adapter is not proof of Hydra deployment or bearer support. The Access guide owns the detailed registration, login transaction, credential lifecycle and qualification requirements; current contract gates remain open.

Application HTTP/MCP clients retain Inframeld-issued keys beginning with `ifm_app_`, not exported human cookies/tokens or implicit Hydra client-credentials grants. The public prefix is not identity or authority; full verification and no credential-kind fallback remain mandatory. Leave Ory token formats unchanged. Follow [key recognition](../../../docs/development/access-control.md#application-key-prefix); [dispatch](../../../docs/development/access-control.md#credential-dispatch) and [complete key syntax/lifetimes](../../../docs/development/access-control.md#application-key-contract) are accepted, with implementation/qualification still pending. MCP OAuth discovery and verified user delegation remain outside the accepted two-tool profile. The application-connection flow reviews account/group/action scope before separate issuance and optional paid testing; it cannot widen an existing account silently or recover show-once secrets from replay. Preserve the two-usable-key limit and current grant-authority checks.

Bound delegation by the exact action and target. Can-use-and-grant authority is different from can-use authority. Keep human-only administration, peer managers, replacement requirements, separate deletion permissions, and the full issuance checks in the Access guide. Do not infer permission from a title, creator history, installation administration, or membership alone. Every group manager must also have ordinary membership in that same group. Appointment explicitly records both, and reads use membership rather than a manager bypass. Ordinary membership alone never authorizes sharing. Empty document allowlists are never public.

Application keys identify their account and use its current permissions. Issuance requires the authorized human to pass both the management and delegation checks specified in the guide; it is not a permanent ceiling on an issued key. Incoming credential audiences, expiry, overlap limits, revocation, and account deletion remain distinct. Applications cannot acquire human-only grant or incoming-credential administration. Outgoing provider-key management follows its own policy.

Ordinary departure preserves required human management. Demotion removes management but retains membership. Membership removal also removes management, and rejoining does not restore it. Emergency suspension preserves both records while immediately blocking reading and administration, even for the sole manager. Scoped group recovery explicitly assigns both membership and management to an eligible replacement without reviving the compromised account or giving the operator ordinary unrestricted reading. Project, resource, document, group, and application-account deletion each follow their explicit permission and reference rules.

The Access schema uses shared principals with a small project-bound application extension, target-specific current grant tables, one recipient/action/target assignment with `can_grant`, and separate audit history. The migration enforces core scoped relationships, manager membership, principal/resource kinds, grant uniqueness, and application use-only grants. The fixed action catalogue remains application-owned and is not yet enforced by database checks. Every manager record requires the matching group-membership record. Creation, appointment, removal, and recovery must preserve that constraint. All participating writes use the accepted organization/project coordination, current checks, expected scope revisions, mutation, revision increment, and audit commit together. Keep external work outside the short transaction. The first use-only human project grant command implements this pattern with HTTP and PostgreSQL tests. Audit retention and the remaining administration workflows still need implementation and tests.

Keep policy in Access and PostgreSQL for v1. OpenFGA and PyCasbin were considered but not selected. Do not add a generic policy language, speculative engine adapter, or authorization cache without a demonstrated need. The [recorded engine comparison](../../../docs/development/access-control.md#section-introduce-a-general-authorization-engine-or-policy-language-now) preserves the actual reconsideration criteria.

All remote model calls use ModelGateway and approved destinations, including embeddings, generation, judges, probes, and repair calls. Synthetic preflight is optional and its absence is not an execution or first-publication blocker. Complete configuration, security checks and response validation remain mandatory. A successful real call automatically validates only its actual role/model/configuration and connection/credential revisions after response checks; it does not validate every model sharing a key, certify answer quality or make an incomplete index ready. Display untested configuration honestly, retain evidence source/time and later failures, and never repeat a paid call merely to record evidence. Credential replacement makes the new revision untested without blocking use solely for lack of evidence; a late old-key result cannot validate its replacement or revive a removed credential.

The operator-approved local Ollama HTTP exception is credential-free; any connection needing an authentication secret uses certificate-verified HTTPS. Credential-only replacement preserves the access/model contract. Connections have one current access configuration, not consumer-selected old revisions. Connection managers may approve shared live updates without per-Deployment release rights, with backend-bound review and current dependency/authority checks. Reject incompatible or unproven prepared/in-progress embedding dependencies before mutation. Origin/authentication-destination changes require explicit credential provision and atomic activation; never forward the old secret implicitly. Another connection is the isolated migration path. Restoration is a new guarded update, not secret recovery. PostgreSQL/PyNaCl authenticated encryption with a separate persistent root key is accepted; fail closed and keep plaintext resolution narrow.

The [implemented human-session boundary](../../../docs/development/access-control.md#implemented-human-authentication) records current outcomes and evidence. Read [the Principal model](../../../docs/development/data-model.md#implemented-principal-model) before changing account-state contracts. Authentication looks up state in a fresh session after provider verification; authorization readers remain bound to the caller's transaction. Do not put status or grants into `AccessContextDTO`.

## Explain and review

Use Alice and SupportBot: both can belong to Support, while only the bot has Query on Production. Removing Query prevents that action; removing its document-group membership changes readable evidence. Rotating a key changes neither grant. An unrelated Test remains separately protected.

Trace current checks at admission, commit, dispatch, and disclosure as relevant. Cite the precise rule, name proposals and qualification limits, and inspect code before claiming behavior exists. Preserve private defaults and Build plus target-specific Manage releases checks; automatic mode cannot elevate upload-only access. Do not implement future resource domains merely because their grant tables appear in the foundation map.
