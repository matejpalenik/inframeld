# Restructure a backlog without losing its product

Alice's grant issue currently promises administration for both Access targets and future Pipelines. Access can deliver its own targets before Pipelines exist. The Pipeline feature can own its real target integration. That separation is useful only when the integration, acceptance and dependency remain visible in a receiving issue.

Use this procedure for authorized splits, scope transfers, native relationship repairs and bulk rewrites. It does not authorize implementation or changes to a running delivery Goal.

## Preserve scope before publication

Snapshot issue bodies, comments, metadata, native parents/blockers and relevant PR associations outside the repository. Record the inspection time and source identity. For a broad rewrite, classify the complete inventory, including closed evidence, aggregate parents, implementation, specification, qualification and deferred work.

Prepare a temporary requirement map and complete proposed dependency graph before publishing. Give every existing requirement one destination: its retained issue, a named receiving issue, a necessary new issue, delivered evidence, or an explicitly deferred or unresolved decision. Match meaning, exceptions, failure behavior and qualification obligations rather than just headings. No unique requirement may survive only in this temporary map or Git history. Keep GitHub as the backlog rather than creating a permanent migration ledger in repository guidance.

Use Architecture for cross-domain coverage and the owning domain workflows/contracts for precise acceptance. Preserve the full accepted v1 scope and explicit deferrals. Standardizing Studio or post-v1 descriptions does not make those issues v1 work. Reconcile contradictory sources without inventing a new policy during editing.

## Assign a complete responsibility

Preserve an issue number when its coherent outcome remains. Split when the parts have distinct outcomes, owners or independently useful acceptance. Several routes, tables or PRs alone do not justify several tickets. A component closes against its own accepted scope, while its consumer owns integration with that component.

For each transfer, name the receiving issue, required capability, observable acceptance and consumer return action. Create a necessary receiver before removing the requirement from its former owner. Do not replace a broad unfinished promise with an unowned sentence saying another domain will handle it later.

Inspect open PR closing references, merged evidence, preserved branches and existing human qualification. A local adapter, open PR or ordinary successful path is not complete production integration. Do not claim new work is delivered or let an existing PR appear to close a changed issue accidentally. Retain useful source and verification evidence with its actual limits. Keep missing product behavior with implementation owners and actual human observations with qualification.

## Repair the real graph

Use native parents for decomposition and native blockers for actual producer capabilities. Avoid whole-epic blockers when a particular child supplies the input. Use GitHub's database issue ID where an API requires it. Keep the graph acyclic, avoid implementation/qualification cycles and ensure v1 never depends on deferred Studio.

For an epic-focused sequence, name one completion objective and only the external prerequisites it actually needs. Domain foundations should finish against their accepted real inputs. Future consumer integrations belong to their feature owners. Real dependencies still matter, such as starter provisioning needing ordinary resource creation. Preserve unrelated work as recoverable checkpoints rather than treating a scope rewrite as permission to discard it.

## Apply and reconcile

Review complete requirement allocation and graph safety before publishing. For a bulk change, use distinct authoring and review assignments with one publisher. Apply reviewed domain batches, resolving cross-domain transfers together.

Immediately before each mutation, re-read the body, update time and relevant relationships. Compare against the inspected baseline. Preserve intervening comments, metadata and work. If acceptance is actively changing, defer that issue until its current owner/state is reconciled rather than overwrite it. Change only metadata belonging to the approved rewrite.

Journal actual created issue IDs outside the repository. After an uncertain create, locate its outcome before retrying. After each batch, read back bodies, states, labels, milestones, parents and blockers. Check the resulting graph and receiving acceptance. Preserve comments without adding repetitive migration comments. Use the connector where it supports the operation, and a supported native GitHub API for missing relationship operations. Neither tool choice expands authority.

Do not close unfinished work as completed because it was split, moved or reformatted. If an issue is superseded, preserve replacement links and use the appropriate non-completion disposition. Ordinary delivery closure remains governed by Backlog Delivery. Preserve closed historical scope/results and comments. Add only necessary navigation or a clearly separated current clarification when that closed-record edit is authorized.

## Keep a running delivery scope separate

A rewritten issue changes the source to which its readiness evidence was bound. Reassess affected acceptance and evidence at a safe checkpoint. Preserve valid verification by inspected inputs, prior failures, branch/checkpoint ownership and actual cleanup state.

New issue IDs and transferred outcomes do not automatically enter an existing finite launch. Preserve the original snapshot and return an explicit old-to-new scope mapping for the authorized coordinator or human to reconcile. Do not directly modify the run record, reset repair history, operate workers or send steering messages merely because backlog editing is authorized. [Delivery gates](../../inframeld-backlog-delivery/references/gates-and-recovery.md#evidence-for-readiness) own evidence binding, and the actual launch owns permitted effects.

Finish with uncovered requirements, genuine decisions, graph defects and readiness limits. Formatting consistency and more closed ticket numbers cannot establish product completion or faster execution.
