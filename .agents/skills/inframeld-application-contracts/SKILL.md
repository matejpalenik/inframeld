# Inframeld Application Contracts

Keep one application behavior behind HTTP, Studio, workers, and MCP. Review ownership, safe retries, generated contracts, and transport boundaries without creating another domain or a universal review gate.

## Scope and reading route

- Before designing, generating or reviewing an application service, read the [service-writing guide](../../../docs/development/application-structure.md#service-writing-guide). Follow the implemented grant service for complete database commands: direct dependencies, checked authorization scope, explicit replay, domain behavior, repository save and atomic audit/completion. Keep transition invariants on the owning aggregate and orchestration in the service. Translate recognized domain errors using [stable application messages](../../../docs/development/error-handling.md#stable-domain-error-mapping) and preserve causes. The guide defines appropriate variations for aggregate creation, reads, provider verification and durable jobs. Supporting records and capabilities do not require artificial aggregates. Qualify new workflows behaviorally without adding a generic executor or architecture-enforcement tests.

- For shared eligibility, authorization operations or lifecycle aggregates, follow [ADR-0064](../../../docs/adr/ADR-0064-centralize-principal-eligibility-and-keep-access-aggregates-focused.md), [the component contract](../../../docs/development/application-structure.md#shared-access-eligibility), [Access behavior](../../../docs/development/access-control.md#shared-principal-eligibility) and [attempt-local inputs](../../../docs/development/data-model.md#principal-eligibility-inputs). Application workflows call stable Access operations instead of assembling account/recovery checks independently. The implemented common policy owns principal eligibility, with operation-specific policies adding authority. Read projections compose SQL expressions without hidden reader-to-reader execution. Preserve current-state replay checks, visibility ordering and application-owned grant transactions and caller-bound adapters. Linked recovery admission coordinates with grant writes through conflicting organization locks. Both grant-facts and recovery-admission adapters use fixed five-second database deadlines, including waits, with rollback owned by the caller. The implemented `IdentityRecovery` aggregate protects checklist transitions, while its specific repository retains original admission metadata outside the entity. Follow [recovery records](../../../docs/development/data-model.md#identity-cleanup-records) for exact-instance/transaction ownership and conditional saves. A conflicting changed save requires rollback and a fresh load before another decision, without automatically repeating provider calls. Unchanged saves do no writes or freshness checks. Provider cleanup, application release checks and concurrent first-local-admission qualification remain unfinished.

- For complete grant-write ergonomics, follow [ADR-0065](../../../docs/adr/ADR-0065-application-services-own-write-transactions.md) and the [implemented request chain](../../../docs/development/application-structure.md#grant-command-flow). Static `ProjectUseOnlyGrantMapper` methods build a flat Command and construct the typed response directly after narrowing the supported action. The service computes the unchanged fingerprint before opening `TransactionManager`, then calls `ProjectGrantAuthorizer`, `OperationIdempotency` and `ProjectMembershipRepository` through direct dependencies. Bootstrap supplies one clean request-local session. Pass the existing admission context, authenticated access, current authorization result, typed `RequestFingerprint` and expected replay kind to idempotency. Read the principal from access and both scope IDs from authorization, never by inspecting the Command. The complete grant service checks the returned project against its Command immediately after authorization, before reservation or replay. A mismatch is an internal runtime failure that rolls back. After matching, idempotency and membership loading use authorization scope. The service checks the loaded organization, project and recipient, calls `ProjectMembership.assign_use_only_grant()` and saves through the specific repository with the checked project revision and original operation ID. Keep requested grant details on the unchanged Command and actor identity on access. Scope matching does not replace the authorizer's current permission checks. Follow [ADR-0066](../../../docs/adr/ADR-0066-use-typed-operation-contexts-and-command-classification.md). Only `IdempotencyService` assembles the low-level reservation request. Commands retain business input. Required audit and safe replay metadata commit with the change. `IdempotencyService` validates the low-level reservation projection and returns distinct new, completed synchronous, accepted asynchronous or recovery-required outcomes. Synchronous expiry is required and asynchronous expiry remains optional. These outcomes carry metadata, not authority. Preserve current authorization before replay, the expected replay kind and existing lock/deadline rules. The admission-only helper shares `OperationIdempotency` while retaining its caller-owned transaction. This does not qualify a second complete product command. Low-level reservation adapters retain their contracts. Do not add a generic bus, repository framework or speculative recovery aggregate.

- For the membership aggregate, follow [ADR-0068](../../../docs/adr/ADR-0068-model-project-grants-through-project-membership-aggregates.md) and [the implemented repository boundary](../../../docs/development/application-structure.md#membership-aggregate-and-repository). A `ProjectMembership` owns all direct project grants for one recipient. Its composite identity is project plus principal. Immutable `ProjectActionGrant` children use project, recipient and action identity. The aggregate rejects duplicate assignments and application delegation. The repository loads existing membership only, preserves historical attribution and timestamps, and supports attributed use-only additions. Bind its exact instances and immutable value snapshots to one active caller-owned transaction. Discard them after transaction end or failed save. Compare levels and attribution explicitly instead of entity equality. Save additions with one conditional project-wide revision increment and required audit, without commits, new locks or retries. Authorization still owns current eligibility and delegation. Membership creation, revocation and cross-member lifecycle operations remain deferred.

- For authorization families, follow [ADR-0067](../../../docs/adr/ADR-0067-standardize-authorization-capabilities-with-typed-requests.md) and [typed capabilities](../../../docs/development/application-structure.md#typed-authorization). `ActionAuthorizer` and `ProjectGrantAuthorizer` explicitly specialize `Authorizer[RequestType, ResultType]` and expose the inherited abstract `require_authorization(access, request)` method. Concrete services and doubles explicitly inherit their family and use `@override`. Access-owned request DTOs remain separate from Commands and retry metadata. Trusted workflows select ordinary required actions. Reuse a family across operations and add one only for materially different inputs or rules. Both existing consumers match returned project scope before lookup. The grant workflow owns its transaction, while the admission helper leaves rollback to its caller. Signature conformance does not enforce authorization ordering - verify denial, scope mismatch, replay and database effects behaviorally. Preserve reader contracts, policy composition and visibility ordering.

## Essential boundaries

For the query-to-release loop, read [Pipelines](../../../docs/development/pipelines-and-releases.md#working-configuration), [API capabilities](../../../docs/development/api-contracts.md#expose-preview-and-policy-controlled-build-without-duplicating-execution), [query execution records](../../../docs/development/data-model.md#experimental-execution-records) and [ADR-0052](../../../docs/adr/ADR-0052-separate-experimental-execution-from-release-ready-pipeline-builds.md). Configuration history, direct queries and working-configuration evaluation share application behavior, not another service or MCP tool. Distinguish fixed captured working-configuration input from ready PipelineVersion. CLI Build captures saved configuration and coordinates policy-controlled publication; its underlying build remains readiness-only. Idempotent replay resolves original inputs/target before current settings, and stale reviewed revisions conflict. Exact action/wire mappings remain qualification work.

For Ragas, follow [the adapter boundary](../../../docs/development/evaluation.md#gateway), [frozen execution](../../../docs/development/evaluation.md#comparison), [Evaluation records](../../../docs/development/data-model.md#evaluation), and [ADR-0051](../../../docs/adr/ADR-0051-use-ragas-for-generated-tests-and-faithfulness-evaluation.md). Generation, review and evaluation are separate application operations shared by CLI and future Studio. Existing durable jobs own attempts and recovery; Ragas is not a new runner. Vendor schemas stay in infrastructure, public results remain application-owned, and the six Evaluation action identifiers/targets are [accepted](../../../docs/development/access-control.md#reviewed-capability-catalogue), while [human Pipeline audience administration/import defaults](../../../docs/development/evaluation.md#case-audiences) and [fixed creator grants](../../../docs/development/access-contracts.md#initial-assignments) are now accepted. Exact routes/public schemas still need specification. Gateway routing and cancellation cover preparation as well as final execution. No new MCP tools or SDK-distribution decision follows from this workflow.

Connections expose one current access configuration. Update/restoration/import share backend-owned authorization, reviewed-impact acknowledgment, revision/dependency checks, destination-bound credential handling and atomic outcomes. A client prompt is not enforcement. Connection management includes live impact without per-Deployment release rights; Pipeline Edit does not. Exports capture current connection definitions and exact immutable profiles, not access variants; name matches never authorize overwrite. Jobs observe current access revisions but cannot execute old ones or rebind after a change. Preserve partial/uncertain outcomes, while key-only rotation remains separate. Concrete action/wire/storage contracts remain delivery work.

Knowledge owns sources; Indexing owns verified search data; Pipelines owns builds, query, receipts and feedback; Evaluation owns offline evidence; Releases owns serving pointers; Access owns authorization. Entry points call their public application use cases. Read projections may join owners without becoming additional writers. Jobs and audit are supporting records, not a seventh domain or event-sourcing framework.

The [policy/feedback contract route](../../../docs/development/api-contracts.md#expose-policy-administration-and-feedback-through-their-owners) distinguishes budget administration from dispatch accounting, project tracing changes from imports, and CLI feedback from its backend owner. Suspension cleanup and operator maintenance are separately bounded workflows. Underlying builds accept caller-captured authorized inputs; only the explicit CLI coordinator selects current working configuration. Do not encode transport-specific selection or a recovery bypass in a shared operation.

Keep vendor SDK, HTTP, and ORM types outside application/domain contracts. Supply verified application-owned identity context. Shared authorization uses current grants and transactional audit. Group-manager appointment and recovery explicitly record ordinary membership too. Membership removal also removes management in the same transaction. Preserve the [required relationship](../../../docs/development/data-model.md#group-manager-membership-constraint) without treating manager status as a read bypass. Target-specific relational persistence does not imply multiple policy implementations. Grant, scope-revision, and account-status mutations participate in the accepted lock protocol.

FastAPI/Pydantic generates the native OpenAPI 3.1.x contract. Keep stable operation IDs, errors, bounded pagination, asynchronous outcomes, and first-answer/receipt-only variants. Do not hand-edit generated output or weaken server semantics for a generator. Shared pagination bounds `limit` to 1–100, default 25; feature-owned deterministic order includes a unique tie-breaker and current authorization on every page.

V1 delivers a Rust CLI and independent Ory account UI; full Studio is deferred. Application clients come from native OpenAPI with no generator package prescribed. Qualify against implemented contracts incrementally; intended language targets are not qualified deliverables. Future Studio uses its generated TypeScript client and the same CLI-led product rules. Browser calls retain user-session/CSRF protection; server rendering preserves that user's context without a global admin key or cross-user cache. Ory's own clients serve Ory contracts, not a competing Inframeld API.

MCP exposes only `query_deployment` and `get_answer_receipt` inside the existing API process. Authenticate every mounted request, reuse application behavior, and preserve business idempotency keys. Mounting does not automatically inherit protection. The [MCP guide](../../../docs/development/mcp.md#hosting) explains why the selected SDK path uses a low-level `Server` with explicit tool-argument validation and no advertised prompt, resource, or subscription capability. Header-capable trusted clients are supported; universal OAuth discovery and verified per-user delegation are not implied. Tool arguments and MCP request IDs cannot establish credentials or business retry identity.

The existing human HTTP dependency implements Kratos cookie and human Hydra bearer selection. The bearer application service privately verifies the token, checks current Kratos eligibility, then reads local principal state before authorization. Native OpenAPI declares the two credential alternatives and the implemented 400/401 problems/challenges. Preserve cookie CSRF and reject malformed/competing credentials before verification, with no fallback. PostgreSQL session and grant-write tests use real application behavior with mocked provider results, including current authority on replay and denial without durable changes. Separate real Hydra/Kratos cases exercise the provider SDKs through the backend. One private test container runs the whole integration directory with all provider flags enabled, then project-scoped cleanup preserves named test volumes. [The backend README](../../../apps/backend/README.md#integration-tests) owns commands and debugging. Both authentication paths enforce configurable provider/total deadlines. Production account-UI/CLI login and lifecycle qualification, the CLI request limit and verified-recovery cleanup remain ahead. API-audience human tokens do not become MCP credentials. The application-connection wizard uses ordinary application account/grant/key operations, never a second authority model, automatic issuance at setup or a paid query hidden in connection verification. Show-once secret delivery and partial outcomes retain the normal recovery rules.

Admit work and its idempotency reservation atomically in a short transaction. Do external work outside it; only the current fenced attempt can publish. A SQL lease cannot cancel a remote request. Same key and meaning finds the original operation; different meaning conflicts. Authenticate and authorize replay. Keep secret-bearing fingerprints keyed, generated secrets one-time, and answer replay receipt-only. Ambiguous paid calls cannot be silently repeated; frozen vector payload retries have their separate bounded protocol.

Defaults reuse normal commands and one resolver. Automatic updates uses normal Build then separate conditional publication; Indexing never moves traffic. Revisions protect mode switches and competing commands. For a default alias retry, locate the original logical-route idempotency record before resolving a new target, so rebinding cannot create another paid query. Selector details remain implementation recommendations.

## Review method

Trace validated request → verified context → owning use case → transaction or external call → typed outcome. Compare a lost response, concurrent repeat, and different command. For HTTP/MCP parity compare scope, selected version, receipt identity, and outcome. Use behavior and contract checks when implementation is authorized; do not add structural tests, speculative frameworks or custom generator development by implication.

For configuration transport, read [portability](../../../docs/development/configuration-portability.md) and the delivery plan's explicit schema/action prerequisites. Complete TOML definitions, protected JSONL datasets, credentials and runtime backups are separate. Domain owners enforce mutations; the CLI never creates a second permission/retry engine. Every command has scriptable output and descriptive dry-run; exact output/recovery contracts remain specification work. Preserve original context, receipt-only/secret-safe replay and uncertain paid-call boundaries.
