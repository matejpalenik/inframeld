# Understanding Inframeld

Inframeld helps a team connect models, upload its knowledge, and ask questions grounded in that knowledge. It also helps the team understand which documents and configuration produced an answer, compare a proposed change, and control when that change reaches users.

The central technique is **retrieval-augmented generation**, or RAG: find relevant passages first, then give those passages to a model as evidence for its answer. Finding a passage does not prove that an answer is correct. Inframeld preserves the identities and evidence needed to investigate results and improve the pipeline.

This introduction explains the **accepted design**. Acceptance means we have chosen the behavior; it does not mean every feature is implemented or tested. The owning references distinguish selected rules, proposed implementation details, deferred features, and qualification still required. The [backend README](../apps/backend/README.md), [HTTP error reference](../.agents/skills/inframeld-application-contracts/references/http-errors.md), and [pagination reference](../.agents/skills/inframeld-application-contracts/references/pagination.md) describe concrete foundations already present. Inspect the relevant code when answering what works today.

For a diagram-led reading route, start with [system context](../.agents/skills/inframeld-architecture/references/system-context.md), then [runtime topology](../.agents/skills/inframeld-architecture/references/system-overview.md) and the [module map](../.agents/skills/inframeld-architecture/references/module-map.md). Each domain has its own architecture reference. These views explain the accepted guides and inspected code. Pending recommendations are explicitly labelled and do not become accepted decisions through publication here.

## A small journey from document to answer

Suppose Alice wants a support assistant to answer questions about her company’s handbook.

1. **Alice signs in and receives private starter resources.** Kratos verifies her human identity; Hydra supplies the accepted browser-assisted human CLI login and token lifecycle. Inframeld’s Access rules decide what her local account may do. A project groups her resources; document groups control who may read the evidence. These are ordinary application resources, not a security shortcut.
2. **She configures the required model capabilities.** A connection describes how to reach a model service; each role separately selects its model. Connections have one shared current access configuration and a separately replaceable provider credential. Remote requests pass through ModelGateway, the application-owned boundary for approved destinations and provider interaction.
3. **She uploads the handbook.** Knowledge records its stable Document identity and a DocumentVersion for these bytes. Untrusted files are processed in a restricted execution boundary. Successful upload, successful parsing, and readiness to answer are different milestones.
4. **The application prepares searchable evidence.** Indexing creates text chunks, obtains embeddings, and verifies the prepared data. An embedding is a numerical representation used to find similar text. PostgreSQL records collection membership; Chroma stores derived vectors.
5. **A build prepares a pipeline version.** A Pipeline describes retrieval and generation settings. A PipelineVersion freezes selected settings and prepared inputs. Finishing a build makes that version ready; it does not itself move customer traffic.
6. **A separate release step chooses the version to serve.** A Deployment is the stable destination callers query. The default onboarding deployment uses Automatic updates, so an authorized update can request a normal build and separate conditional publication. A newly created deployment defaults to Manual releases unless its creator explicitly chooses automatic mode.
7. **A question uses current permissions.** The application checks the right to query the deployment and applies document access when selecting evidence. ModelGateway sends the permitted final evidence to generation. An answer receipt records which version and evidence served the answer without creating a hidden full-answer replay cache.

The [onboarding guide](../.agents/skills/inframeld-architecture/references/first-use-and-private-defaults.md) explains the whole journey, including incomplete configuration and provisioning retries. Its first-answer timing goal is flexible and aspirational, not a measured guarantee.

## One backend with clear responsibilities

Inframeld is an Apache-2.0 application designed for one server using Docker Compose. A **domain** is an area of the product with its own rules. These domains are separate responsibilities inside one backend, not a network service each.

| Domain | What it owns | Example question |
| --- | --- | --- |
| Knowledge | Sources, document versions, collection membership, uploads, and synchronization | Which handbook version belongs to this collection revision? |
| Indexing | Processing and embedding profiles, chunks, vectors, layouts, verification, and materializations | Is the exact search data this version needs usable? |
| Pipelines | Working configuration/history, execution-input snapshots, builds, direct/live execution, receipts, and feedback | Which configuration and evidence produced this answer? |
| Evaluation | Test cases, frozen benchmarks, evaluator revisions, comparisons, and history | How did two fixed configurations or versions perform under the same test conditions? |
| Releases | Deployment serving pointers, canaries, promotion, rejection, rollback, and publication modes | Which ready version should answer the next request? |
| Access | Local identities, memberships, grants, document groups, and authorization | Who is calling, and what may that caller do now? |

Application use cases coordinate these owners. Adapters connect them to HTTP, MCP, databases, and external products. Domain and application contracts use application-owned types rather than vendor SDK, HTTP, or database ORM types. A command changes state; a query reads it. This separation does not require a command bus, generic repository, or workflow engine.

Read [Application structure](../.agents/skills/inframeld-application-contracts/references/components-and-services.md) for dependency rules and examples. The [contracts and data guide](development/guides/contracts-and-data.md) routes to implemented definitions and logical relationships. A logical concept does not automatically imply one table, class, service, or endpoint.

For named resources, distinguish **name**, **display name** and **ID**. Alice selects `legal-research` by its name, sees `Legal Research` as its display name, and the backend retains its permanent ID in relationships and admitted work. Display names never resolve resources. This is accepted vocabulary, not a completed schema migration. The [resource-naming contract](../.agents/skills/inframeld-architecture/references/resource-names-and-identity.md#resource-naming) owns scope, rename safeguards and the distinction from existing physical fields.

## Versions explain change without rewriting history

An **immutable** record cannot be edited after creation. A change creates another version. Imagine a collection containing A1 and B1. Replacing document B creates B2. An authorized selection can then create a collection revision containing A1 and B2. The earlier revision still identifies A1 and B1, so an answer can be traced to the evidence that actually served it.

Different changes have different identities. Replacing bytes changes the DocumentVersion. Changing parsing or embedding settings changes the relevant profile selection. Changing retrieval or generation settings changes pipeline configuration. A release selects a ready pipeline version; changing a serving pointer does not itself recompute vectors.

Unchanged work can be reused when its full identity matches. Reusing A’s vectors avoids embedding A again, but validating a complete collection revision can still require substantial work. A **materialization** records prepared search data for an exact collection revision and profile combination. The [Indexing guide](../.agents/skills/inframeld-indexing/references/profiles-and-preparation.md) explains matching, layouts, retries, and verification. The [Indexing data model](../.agents/skills/inframeld-indexing/references/records.md#indexing) owns record definitions.

History does not override current access or deletion. A historical pipeline version can become unavailable when required evidence is deleted. Removing a document from a new collection revision is different from deleting all its historical data. See [Knowledge lifecycle](../.agents/skills/inframeld-knowledge/references/documents-and-collections.md) and [Retention and deletion](../.agents/skills/inframeld-knowledge/references/deletion-and-retention.md).

## Permission to act and permission to read are separate

Authentication verifies identity. Authorization evaluates permission. Kratos owns human identities and browser sessions; Hydra supplies OAuth/OIDC for first-party human CLI login under [ADR-0053](adr/ADR-0053-use-kratos-and-hydra-for-human-cli-authentication.md). Access owns application authorization using PostgreSQL state. A **principal** is the stable local identity of a human or application account.

Browser cookies and verified Hydra CLI tokens resolve to the same existing human principal. The backend implements both authentication paths. CLI token verification includes private introspection and current Kratos identity eligibility before local admission and permission checks. Real-provider integration tests exist, while complete account-UI, CLI and recovery qualification remain unfinished. The small browser account UI does not require the full Studio. [Access](../.agents/skills/inframeld-access-models/references/credential-dispatch.md#implemented-human-authentication) records implementation evidence and its limits.

Common account eligibility has one domain-policy owner under [ADR-0064](adr/ADR-0064-centralize-principal-eligibility-and-keep-access-aggregates-focused.md). Human authentication, project action checks and the supported human grant command reuse that rule. Access services coordinate current database reads, and linked recovery admission coordinates with grant writes through organization locks and bounded database work. The supported grant workflow now uses a focused `ProjectMembership` aggregate to protect one member's direct grant assignments under [ADR-0068](adr/ADR-0068-model-project-grants-through-project-membership-aggregates.md). Recovery checklist persistence and local completion are implemented. Native callbacks, the dedicated provider-cleanup worker and protected host continuation now have inspected implementations. [ADR-0070](adr/ADR-0070-use-bulk-hydra-revocation-for-identity-recovery.md) selects bulk Hydra recovery cleanup, accepting that delayed attempts may require another CLI login. [The Access guide](../.agents/skills/inframeld-access-models/references/eligibility-and-current-authority.md#shared-principal-eligibility) explains the implemented flow and implementation limitations.

[ADR-0071](adr/ADR-0071-use-native-kratos-login-and-checked-hydra-consent.md) keeps human CLI login with Kratos's native Hydra integration and consent policy with Access. The implemented cookie-only consent API checks the current browser, exact requested installation access and recovery block. Remembered consent defaults to one configurable hour. OAuth consent can precede local admission and grants no project permissions. A separate [installation command](development/getting-started/local-setup.md#configure-the-cli-client) reconciles the CLI client, and development Compose includes private Hydra administration and native lifetime configuration. The [recovery workflow](../.agents/skills/inframeld-access-models/references/recovery-completion.md#implemented-execution-and-proof-backed-completion) and [protected host continuation](../.agents/skills/inframeld-access-models/references/host-maintenance.md#recovery-cleanup-continuation) have inspected implementations. Browser pages, packaged runtime delivery and first-local-admission integration remain unfinished.

Project membership alone does not grant every action. A caller may need Query on Deployment A, while document-group membership determines the evidence it may read. Every group manager must also be an ordinary member of that group. Appointment explicitly records both assignments, so managers have the document access they may share. Ordinary members cannot share access merely because they can read. The [Access references](../.agents/skills/inframeld-access-models/references/memberships-groups-and-handover.md#group-managers) explains appointment and removal.

For example, SupportBot may query Deployment A and read the Support group. It cannot query Deployment B merely because both deployments belong to one project. A valid application key identifies SupportBot; the account’s **current** permissions are checked when the key is used. Granting or removing account permissions changes what an already issued valid key can do.

Administration is bounded too. The ability to grant a permission is separate from using it, and delegation remains limited to the permitted action and target. Human-only checks still apply where required. Ordinary departure must preserve required management coverage. Emergency suspension can block a compromised sole manager immediately, with a scoped operator recovery path. Host operators control the installation but do not automatically become unrestricted readers through ordinary product APIs.

The [Access references](../.agents/skills/inframeld-access-models/references/authorization.md) owns the complete permission matrix and recovery rules. [Access records](../.agents/skills/inframeld-access-models/references/identity-and-grant-records.md#access) distinguish the accepted model from proposed physical details in the 14-table foundation. Incoming application keys are different from outgoing provider credentials, which belong to [Model connections](../.agents/skills/inframeld-application-contracts/references/model-gateway-and-connections.md).

## Preparing a version and releasing it are different actions

Alice can first edit the Pipeline's saved working configuration, query that Pipeline directly and evaluate it without creating a release-ready version. Query on a Pipeline and Query on a Deployment are separate exact-resource grants; neither implies the separate query-trace inspection grant on that resource. Each admitted query captures exact settings, corpus and prepared-data bindings; later edits cannot change an admitted run. Temporary overrides affect only that query. Restoring old settings creates a new working revision, not a production rollback. Direct querying uses the same execution and gateway behavior, not an Experiment resource, another service or a second live Deployment. [ADR-0052](adr/ADR-0052-separate-experimental-execution-from-release-ready-pipeline-builds.md) records this development loop; [Access](../.agents/skills/inframeld-access-models/references/query-and-document-authorization.md#pipeline-query-authority) specifies the exact-resource permission rules.

**Shared connectivity is a separate operational dependency.** Under [ADR-0054](adr/ADR-0054-use-shared-current-model-connections.md), Pipeline versions select stable connection identities, not historical access settings. A connection manager may update shared access after a guarded review, affecting consumers even in Manual release mode. Prepared/in-progress embedding incompatibility or unknown compatibility rejects the update before it changes anything. Relevant access changes stop remaining model dispatches in admitted work rather than mixing configurations. Executions record what was actually used; Pipeline rollback does not restore connection settings. Use another connection and the query/build/release path for an isolated migration. [Model connections](../.agents/skills/inframeld-application-contracts/references/model-connection-changes.md#shared-current) owns this boundary.

When satisfied, Alice invokes `inframeld build` on the current saved configuration, not an evaluation run. The workflow captures its inputs and chooses the sole live Deployment or requires a choice when there are several. With none, an ordinary build creates an unpublished version; first-publication onboarding retains its existing separately authorized path. In **Manual releases**, the version awaits explicit release, with optional further comparison and canary review. A canary sends a defined share of callers to a candidate. Rollback selects an eligible earlier ready version, separately from configuration restoration.

The underlying build establishes readiness, not release authority. For **Automatic updates**, the user-facing Build workflow can authorize that preparation and a separate conditional publication together. Current permissions and publication guards still apply. There is no separate CLI apply command. Editing, querying the Pipeline directly and evaluating never publish. Authorized live-input document updates retain their automatic path using the Deployment's explicitly selected configuration, not the changing working copy. Evaluation scores do not authorize releases.

Suppose Alice starts an automatic update, then switches the deployment to manual mode. The delayed build may finish, but its old publication authority cannot move traffic. Switching back to automatic admits fresh work under current controls; it does not revive that old job. Canaries and rollback require manual mode. See [Pipelines and Releases](../.agents/skills/inframeld-pipelines/references/configuration-queries-and-builds.md) for all transitions and concurrency examples, and [deployment records](../.agents/skills/inframeld-releases/references/records-and-transitions.md#releases) for saved state.

## Evaluation and feedback answer different questions

Offline evaluation can first generate starter cases from a frozen permitted sample of processed sources using embedded **Ragas**. Users review the proposed question, answer, and exact source passage; accepted revisions form the default regression benchmark. Generation, review, and evaluation are separate optional actions, not first-answer prerequisites.

A **frozen benchmark** fixes the cases used by a run. Comparisons execute both selected inputs afresh against the same benchmark and evaluator revisions. Either side can be a ready pipeline version or a fixed execution-input snapshot with verified dependencies. Ragas claim-based faithfulness measures support in the final context actually sent to generation; deterministic passage coverage and citation checks remain separate. All nested model calls use ModelGateway with explicitly selected connections. Source-inspected compatibility, calibration, and runtime integration still need qualification under [ADR-0051](adr/ADR-0051-use-ragas-for-generated-tests-and-faithfulness-evaluation.md).

Online feedback records what the originating principal thought of a particular live answer. Direct Pipeline queries and evaluation results stay outside production feedback statistics. There is one current rating per answer and originating principal; editing it replaces the rating rather than adding a vote. A shared application account is one principal, not proof of how many humans it represents. Late feedback remains attached to the version that produced the answer. Feedback does not automatically change releases.

Use [Evaluation](../.agents/skills/inframeld-evaluation/references/generation-and-review.md) for comparisons, denominators, and history, and [Answer feedback](../.agents/skills/inframeld-pipelines/references/answer-feedback.md) for ratings and reporting. Their records are defined in the [logical records](development/guides/contracts-and-data.md).

## Failures and operations are part of the design

Long-running work is saved as durable jobs so a browser closing or worker restarting does not erase admitted work. Jobs have controlled attempts; only the current authorized attempt may publish a result. Database transactions stay short, with external work outside them.

**Idempotency** means recognizing a repeated request as the same operation. After a lost response, the same caller, key, and request meaning can find the original outcome. The same key with different content conflicts. An expected revision separately detects whether another command changed the state first. A timeout after a paid model request was dispatched does not prove the provider did no work. Uncertain outcomes cannot simply be retried as new work. A repeated answer request can return receipt-only status without replaying a saved full answer. Read [Jobs and idempotency](../.agents/skills/inframeld-application-contracts/references/jobs-and-recovery.md).

PostgreSQL owns application state, Chroma holds derived vectors, and SeaweedFS provides object storage through the application’s S3 boundary. Required state and encryption keys must be recovered coherently. Restoring older data can restore old permissions too, so access stays restricted until required security reconciliation is complete. Numerical recovery targets remain provisional; this documentation has not certified capacity or recovery performance.
