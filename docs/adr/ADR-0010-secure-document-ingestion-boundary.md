# ADR-0010: Enforced document-parser isolation

**Status:** Accepted — isolation design; host and implementation qualification pending. **Revised:** 19 September 2026. **Required approach:** A dedicated offline parser service with a fresh, restricted sandbox for every processing attempt in production Docker Compose. **Related:** [Runtime deployment](ADR-0011-hosted-vercel-and-aws-deployment-profile.md), [processing and reranking](ADR-0016-docling-processing-and-cross-encoder-reranking.md).

## Context

Inframeld turns uploaded documents into text and **chunks**: excerpts that can later be indexed and retrieved to answer questions. **Parsing** is the work of reading a document’s format and extracting its content. Docling performs this work, but the documents it receives are untrusted.

The background worker has access to the database, stored application artifacts, and model services. A parser must not inherit those permissions merely because the worker needs a document converted. A malformed or malicious file could cause excessive resource use or exploit the parser, so the boundary must remain useful even when the parser behaves unexpectedly.

From first principles, **processing one document should require access to that document, the approved parser runtime and model assets, and limited temporary storage—not credentials, application storage, or another user’s document**.

Separating the parser from the worker addresses only part of the problem. A compromised parser process that remains alive could try to read the next document it receives. Each attempt therefore needs its own isolated environment and complete cleanup before another attempt starts.

## Decision

**Run a fixed Docker Compose `parser` service containing a small trusted supervisor. For each document-processing attempt, the supervisor starts a fresh Docling child process inside a Linux bubblewrap sandbox.**

The worker sends bounded file bytes and validated processing configuration through a private Unix socket. The parser has no external network access or application credentials. After processing, the worker validates the returned output before admitting any immutable artifacts.

This is an accepted design contract, not evidence that the implementation or host has passed its security tests. **A host that cannot enforce the sandbox must report parsing as unavailable, not fall back to a less isolated execution path.**

### 1. Validate and bound uploads before accepting them

Accept **one PDF, Markdown, or plain-text file per upload request**, with a maximum size of **25 MiB**.

Stream the upload into **private staging**: temporary storage that is not available to queries. Count actual bytes as they arrive and reject an upload that exceeds the limit before **durable admission**, the point at which the application records that it has accepted the upload.

A streaming implementation may write temporary bytes before discovering that the file is too large. It must delete its own rejected staging file and must never make that file queryable. **The guarantee is bounded, private handling and cleanup—not that no byte touches disk before the full size is known.**

Validate the file extension, a bounded content-signature/encoding check, the one-file request shape, and whether the parser supports the format. A content signature helps identify the format from its bytes; encoding describes how text bytes represent characters. Do not treat a filename extension alone as sufficient validation.

Unsupported, ambiguous, or invalid uploads fail before document processing or model calls.

Storage keys are generated by the server. An original filename is display text, never a filesystem path. Source hashes and ordinary application commands establish immutable document-version identity; parser execution does not create a competing identity scheme.

### 2. Separate the worker, supervisor, and document-processing child

These components have different responsibilities:

| Component | Responsibility and access |
| --- | --- |
| **Worker** | Uses the application’s database, artifact storage, and model access. Sends the document for processing, validates the result, and stores accepted immutable artifacts. An artifact is a stored output such as extracted text or a chunk manifest. |
| **Parser supervisor** | A small trusted process in the dedicated `parser` container. Receives bounded requests, creates each sandbox, supervises its execution, and returns a checked output envelope. It does not own business state. |
| **Docling child** | Processes one file inside a fresh sandbox, using only the approved runtime/assets and its attempt-specific input, scratch space, and output channels. Its output remains untrusted. |

The processing flow is:

```text
Worker
    -> bounded file bytes + validated processing profile
        -> private Unix socket
            -> trusted parser supervisor
                -> fresh sandboxed Docling child
                    -> one file + pinned runtime/model assets
                    -> bounded output
                -> supervisor checks the output envelope
    <- bounded result

Worker
    -> validates attempt, source identity, spans, counts, and hashes
    -> admits validated immutable artifacts
```

A **processing profile** is the selected configuration for processing the document. The supervisor’s **output envelope** is the structured message carrying an attempt’s result; checking that message does not establish that its content is safe or correct.

Process **one file at a time initially**. The supervisor persists between requests, but the document-processing child does not. This is a narrow infrastructure adapter, not another business-domain service, queue, or database.

### 3. Restrict the outer parser container and its communication channel

The outer container provides a first isolation layer. It must not receive the worker’s environment or access merely to make integration convenient.

| Boundary | Required configuration |
| --- | --- |
| **Networking** | Set `network_mode: none` and publish no ports. The container has no external network route. |
| **Credentials and application data** | Supply no provider or database credentials, and mount no application artifact volume. |
| **Host control and visibility** | Mount no Docker socket and share neither the host’s PID nor IPC namespace. PID concerns process identifiers/visibility; IPC concerns interprocess communication. |
| **Filesystem** | Keep the root filesystem and model assets read-only. Give scratch space an explicit size limit. |
| **Service resources** | Apply CPU, memory, and PID limits to the whole service, including the supervisor and its children. |
| **Privileges** | Run as an unprivileged user with dropped Linux capabilities and `no-new-privileges`. Do not use `privileged` mode or grant host `SYS_ADMIN`. |

Linux **capabilities** are specific privileges that can be granted to a process. The selected configuration removes unnecessary privileges rather than giving the parser broad host control. `no-new-privileges` prevents execution from gaining additional privileges through the normal executable privilege mechanisms.

#### Use the shared volume only for the Unix socket

A **Unix socket** is a local communication endpoint accessed through a filesystem path. It does not require a published TCP port or external network connection.

A small shared volume contains **only a permission-restricted Unix socket**, accessible to the worker and supervisor. It is not a general file mailbox and does not expose the worker’s filesystem.

The request carries file bytes and validated processing configuration. It must not carry caller-selected host paths, shell commands, or arbitrary model URLs.

The supervisor uses a fixed entrypoint, bounded message framing, attempt IDs, and timeouts. A **fixed entrypoint** means the application chooses what program runs. **Bounded framing** means the communication format limits how much input or output can belong to a message. Attempt IDs associate a result with the processing attempt that requested it.

**Disabling container networking does not disable a mounted Unix socket.** The supervisor needs this channel; the untrusted Docling child must not inherit access to it.

### 4. Give every attempt its own sandbox and process lifetime

Use **bubblewrap**, the selected Linux isolation tool, to create new user, mount, PID, IPC, and network namespaces for every attempt.

A **namespace** gives a process a separate view of a category of operating-system resources. Here, the namespaces separate user identity, filesystem mounts, process visibility, interprocess communication, and networking. They work alongside explicit mount selection and resource restrictions; they are not a complete application security policy by themselves.

#### Expose only what this document needs

Inside the child, expose the pinned read-only parser runtime and model assets, the single staged input file, a minimal private `/proc` and device view, and bounded scratch/output space belonging only to that attempt.

`/proc` exposes process and runtime information. The child receives a minimal private view, not the supervisor’s or host’s process view.

Do **not** bind the supervisor’s socket, earlier attempt directories, application storage, host directories, or secret mounts into the child.

Start a new process session. Close inherited socket and control **file descriptors**, the operating-system handles for open files and communication channels. Pass only the bounded input/output channels the child intentionally needs. Hiding the socket path is not a reason to leave an already-open control connection available.

The child must not be able to inspect the supervisor’s processes or reconnect to its Unix control socket.

#### End the whole attempt, not just its main process

On completion, timeout, or supervisor failure, kill and reap the **entire sandbox process tree**. Reaping means collecting exited child processes, not merely sending a stop signal and assuming cleanup is complete.

Use parent-death handling and namespace teardown so a child cannot survive the supervisor’s failure or leave a background daemon running into the next attempt. A daemon is a process that remains running in the background.

Clear temporary attempt files before admitting the next attempt. Retries use fresh attempt-specific scratch locations while retaining the same domain identity.

For example, a compromised parser processing Alice’s document must not remain alive to inspect Bob’s subsequent upload. **Serial execution alone is insufficient; the old process tree and its temporary environment must be gone before the next attempt starts.**

### 5. Qualify the host and security policies together

Apply a **parser-only seccomp policy** and the applicable host **Linux Security Module (LSM) policy**. Seccomp filters the system calls a process can make; an LSM policy, such as AppArmor, applies additional host-enforced access restrictions.

Permit the unprivileged namespace setup required by the pinned bubblewrap build, then constrain the child’s system calls. Do not disable seccomp or AppArmor globally to make the parser start.

The supported Linux host profile must pass an installation self-test for unprivileged namespaces and these restrictions. If the host forbids the required setup, parsing is unavailable with a clear setup error.

**There is no fallback to running Docling in the worker or to a privileged parser container.** Docker Desktop development uses its Linux virtual machine and must pass the same checks.

#### Pin and test one deployment artifact

Pin the exact image digest, distribution packages, bubblewrap build, seccomp/LSM policy, Docling revision, and model assets. Test them together as one deployment artifact rather than assuming individually selected components produce the intended sandbox.

An **image digest** identifies exact container-image content. Pinning the surrounding packages and policies matters too: the security boundary depends on the actual assembled runtime and supported host.

The source records bubblewrap **0.12.0** as the upstream release observed on the research date. That observation is not an accepted, tested command line or proof that a particular sandbox configuration is secure.

### 6. Limit processing work as well as upload size

**A 25 MiB upload limit is not a processing-resource limit.** Extracted output can exceed input size, and a bounded file can still cause excessive processing work.

| Limit | Enforcement responsibility |
| --- | --- |
| **Elapsed time** | The supervisor enforces a wall-clock timeout and kills the complete attempt when it expires. Wall-clock time is actual elapsed time, not just CPU execution time. |
| **CPU, memory, and process count** | Container cgroups enforce the whole service’s bounds. Cgroups are Linux controls for grouping and limiting resource use. |
| **Processing and output size** | Attempt limits bound page count, extracted-text bytes, chunk count, token count, and output streams. Tokens are the text units counted by the configured processing/tokenization behavior. |
| **Temporary storage** | Explicit limits bound service scratch space and the attempt-specific scratch/output locations. |

Exhaustion or timeout produces a **typed failure**, a defined error outcome that the application can distinguish. No chunks from that failed attempt are published for serving.

The upload cap is fixed here at 25 MiB. The other limits require explicit values in the qualified deployment; this ADR does not supply their numerical settings.

#### Prepare assets before processing begins

Prepackage model and **optical character recognition (OCR)** assets, or obtain them during controlled operator setup. OCR extracts text from images, such as scanned pages.

Disable Docling’s remote-service and external-resource features. During document processing, permit no runtime downloads, URL fetching, embedded-script execution, or user-installed plugins.

The parser uses only the assets supplied to its sandbox. A future remote processor needs a separate data-egress and security decision; it is not implicitly permitted by this local adapter.

### 7. Validate output before making it application data

**A successful parser exit does not make its output trusted.** The worker validates the result even after the supervisor accepts its envelope.

| Check | What the worker verifies |
| --- | --- |
| **Attempt and document identity** | The result belongs to the expected attempt and document hash. |
| **Schema** | The returned data follows the required structure and types. |
| **Source spans** | Reported locations refer to the expected source. A source span identifies where an extracted excerpt came from. |
| **Counts and text limits** | Returned content stays within the required counts and size bounds. |
| **Manifest hashes** | The recorded inventory and hashes of processing outputs match the expected validation contract. |

Refuse **symlinks** and **path traversal**. A symlink redirects one filesystem location to another; path traversal attempts to escape the intended directory. Ignore any storage path supplied by parser output. The worker determines where accepted data is stored.

Stream returned output into worker-owned staging. Only after validation may the worker **atomically admit the immutable output**: unchecked partial results must not become published chunks.

Quarantine failures rather than publishing them. A retry starts with fresh scratch locations and the same domain identity; it must not treat failed output as an accepted result or a new logical document merely because another attempt runs.

### 8. Keep operating-system isolation separate from content safety

The selected boundary must satisfy these behaviors on a qualified host:

| Attempted behavior | Required protection |
| --- | --- |
| **A PDF tries to fetch a URL.** | The parser has no external network route, and remote-resource features are disabled. |
| **The parser tries to read a provider key.** | Its sandbox exposes neither secret mounts nor the worker’s processes. |
| **The parser tries to inspect the next user’s document.** | It sees only its own input; its process tree and temporary environment are removed before the next attempt. |
| **The parser never finishes or exhausts resources.** | The configured timeout and resource limits terminate or fail the attempt without publishing its chunks. |

These are requirements, not completed security-test results. The verified host/kernel and trusted supervisor remain part of the security boundary. **A container is not proof against kernel vulnerabilities.**

#### Extracted text is still untrusted input to a model or browser

Isolation controls what the parser can access and execute. It does not prove that the extracted text is true or that its instructions are safe to follow.

Source text and model output both remain untrusted. Prompts must clearly delimit evidence, instruct the model not to obey commands found in documents, and allow no tools or external actions. Backend-owned retrieved identifiers establish citations; the model cannot invent valid source identities. The browser escapes rendered text rather than treating it as executable content.

These controls reduce risk. They do not prove **semantic groundedness**, meaning that an answer is supported by its evidence, or immunity to **prompt injection**, where untrusted content attempts to redirect the model’s behavior.

### 9. Test the actual failure boundaries before release

Run the required tests against the actual supported host and pinned deployment artifact. Report the host and versions tested, not just that the sandbox configuration exists.

| Area | Required tests and outcome |
| --- | --- |
| **Upload admission** | Exercise the one-file, supported-format, and 25 MiB limits. Rejected staging is cleaned up and never becomes queryable. |
| **Network and control-channel access** | Attempt outbound IPv4, IPv6, DNS, and private Unix-socket access from the child. The child must not reach external services or the supervisor’s control socket. DNS resolves hostnames to addresses. |
| **Filesystem and process visibility** | Attempt to read secret mounts, host paths, and other-attempt paths, and inspect parent processes. The forbidden resources must not be visible or accessible. |
| **Process survival** | Try to leave descendant processes alive after the attempt. Confirm the complete process tree is removed before the next attempt. |
| **Resource exhaustion** | Emit excessive text, repeatedly create child processes, allocate excessive memory, and hang. Limits must produce a bounded failure, not published chunks. |
| **Malformed output** | Return invalid envelopes/content, identities, spans, counts, hashes, and unsafe path representations. Unvalidated output must not become serving artifacts. |
| **Restart behavior** | Restart the supervisor or container mid-attempt. Confirm the failed attempt leaves no artifacts that can serve queries and the next attempt starts cleanly. |
| **Host compatibility and normal behavior** | Exercise the installation self-test and restrictions. Confirm normal supported PDFs still parse under the same isolation and limits. |

These are release criteria. They have not been performed by this documentation change.

## Consequences

### Positive

- **Document conversion does not inherit worker access.** Database/provider credentials, application storage, and host-control interfaces remain outside the parser environment.
- **Attempts are isolated from one another.** Fresh sandboxes, restricted mounts/channels, complete process cleanup, and new scratch locations prevent a persistent parser child from becoming the route to the next user’s document.
- **Failure does not mean partial publication.** Input/output limits, timeouts, and worker-side validation keep rejected or unvalidated results out of serving. The design uses a small supervisor and a maintained isolation tool rather than a general container-orchestration system.

### Negative

- **Host compatibility is a deployment requirement.** Linux namespace support and the relevant security policies must work together. Unsupported hosts lose parsing capability rather than receive a weaker fallback.
- **The adapter needs lifecycle and security testing.** The supervisor, socket protocol, descriptor handling, process-tree cleanup, resource limits, and output validation are implementation responsibilities. Pinning components does not replace testing the assembled deployment.
- **The boundary deliberately restricts functionality and concurrency.** Processing starts one file at a time, uses prepackaged or operator-prepared assets, and cannot fetch resources or install plugins at runtime. It also does not eliminate kernel risk, prompt injection, or incorrect extracted/generated content.

## Alternatives considered

No separate comparative evaluation is recorded. The approaches below are excluded or outside the scope of this decision.

### Run Docling inside the application worker

**Ruled out.** The worker has database, artifact, and model access that document conversion does not need. A separate parser boundary prevents the processing runtime from inheriting that environment. Running in the worker is not an acceptable fallback when sandbox setup fails.

### Keep one document-processing process alive for all uploads

**Not selected.** A compromised persistent parser could remain present for a subsequent user’s document. The supervisor may persist, but each Docling child gets a fresh sandbox and must be completely terminated and cleaned up before the next attempt.

### Rely only on container networking restrictions

**Insufficient.** `network_mode: none` removes the external network route, not a mounted Unix socket or an inherited control descriptor. The child also needs restricted mounts, private process visibility, closed descriptors, resource limits, and per-attempt teardown.

### Use a privileged container or disable host security to make sandboxing work

**Ruled out.** Do not use `privileged`, grant host `SYS_ADMIN`, or disable seccomp/AppArmor globally. The supported host must pass the required self-test; a setup error is preferable to silently removing the selected isolation boundary.

### Let the application create arbitrary job containers through Docker

**Not selected.** Use one fixed Compose parser service and bubblewrap for fresh child sandboxes. Do not give the application a Docker-daemon control interface or introduce a general job-container orchestration system for this task.

### Permit remote conversion or runtime resource downloads

**Outside this decision.** The selected parser runs offline with supplied runtime/model assets. Remote processing requires its own egress/security decision, not a URL or plugin accepted through the current processing request.

### Recorded external evidence

The source ADR records the following references as checked on **19 September 2026**. They explain the selected mechanisms; they do not establish that an Inframeld implementation has passed its security tests.

[Docker’s `none` network driver](https://docs.docker.com/engine/network/drivers/none/) documents a container with only loopback networking. It does not remove a mounted Unix socket, which is why the child must not receive the supervisor’s socket mount or an inherited control connection.

[Docker resource constraints](https://docs.docker.com/engine/containers/resource_constraints/) document CPU and memory controls. [Docker’s seccomp documentation](https://docs.docker.com/engine/security/seccomp/) describes system-call filtering. The deployment must apply and test the required limits and policies.

[Bubblewrap’s security model](https://github.com/containers/bubblewrap/blob/main/README.md) explains namespace isolation, mount selection, and the caller’s responsibility for sandbox policy. [Release 0.12.0](https://github.com/containers/bubblewrap/releases/tag/v0.12.0) is the observed release recorded by the source, not a ready-made application security policy or an already-qualified deployment pin.

[Docling’s advanced options](https://docling-project.github.io/docling/usage/advanced_options/) document model-asset configuration and explicit remote-service options. Inframeld disables remote services and external-resource processing in this adapter.
