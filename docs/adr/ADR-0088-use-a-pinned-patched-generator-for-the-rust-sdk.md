# ADR-0088: Use a pinned patched generator for the Rust SDK

> **Subsequent promotion:** [ADR-0091](ADR-0091-promote-selected-sdks-and-retire-generator-comparisons.md) promotes the selected packages, implements shared conformance and retires alternative implementations and comparison reproduction. The context and evidence below describe the original decision.

**Status:** Accepted. Selects the Rust implementation of ADR-0055's generated-client direction.

**Date:** 2026-10-27. The developer approved the generator-and-patching approach and its decision record on this date.

## Context and Problem Statement

Alice needs the Rust CLI to exercise delivered backend operations as the API grows. Maintaining each HTTP method manually would repeat the contract's encoding and response rules. An unmodified generator can also mishandle those rules, so generator selection needs observed behavior and a maintainable way to fix gaps.

The comparison found native multipart and success-response metadata gaps in `openapi-to-rust`. Targeted source patches resolved those measured gaps in local qualification. Their shared implementation points make them useful beyond individual endpoints, but no generator-upgrade rehearsal or universal future capability guarantee follows from that result.

## Considered Options

- Generate the full client with `openapi-to-rust` and maintain a pinned, tested source patch set.
- Use an unmodified generator. The evaluated unmodified candidates retain measured contract gaps.
- Generate models only and maintain HTTP methods ourselves.
- Handwrite both models and HTTP methods, accepting manual synchronization with the authoritative contract.

The last two alternatives were discussed rather than implemented as comparison candidates. The existing report owns measured results and their limits.

## Decision Outcome

Select the full Rust client generated by `openapi-to-rust` from native FastAPI OpenAPI, with the repository's pinned source patches. Versions, source identity, patch order, hashes and local revision remain in the existing machine configuration. Generation is explicit development work and ordinary SDK compilation consumes included generated source.

Maintain reusable source fixes with behavioral regression coverage. Verify source inputs, apply the ordered patches and qualify generated output without hand-editing it, weakening the backend contract or substituting handwritten HTTP methods. Upstream contributions are not required.

[ADR-0055](ADR-0055-deliver-cli-first-v1-through-openapi-generated-clients.md) remains authoritative for CLI-first delivery and native generated clients. This decision supplies its previously unselected Rust generator implementation. It does not replace the CLI-first scope or create a custom generator platform.

The [Rust SDK skill](../../.agents/skills/inframeld-rust-sdk/SKILL.md) owns Rust consumption and its [maintenance reference](../../.agents/skills/inframeld-rust-sdk/references/generator-maintenance.md) owns Rust-specific obligations. The [shared SDK maintenance reference](../../.agents/skills/inframeld-sdks/references/generator-maintenance.md) owns common patch and upgrade policy. Existing runbooks retain command and cache procedures. Application Contracts retains HTTP semantics and compatibility decisions. This ownership split preserves the Rust selection and rationale.

## Consequences

- More operations using qualified patterns can be regenerated without another handwritten HTTP implementation. New capabilities still require qualification.
- We own a small downstream patch set, deliberate upgrades and regression coverage. Repeated invasive or endpoint-specific changes trigger a review of that maintenance cost.
- Preserve response metadata and inspectable failures without automatic redispatch after an uncertain outcome. Generator correctness cannot establish that a timed-out write did not complete.
- The selected implementation remains in the existing unpublished experimental packages. This documentation decision does not rename crates, implement the CLI or publish an SDK.
- Local qualification is evidence for tested contracts. Remote platform qualification, generator-upgrade rehearsal and future workflow qualification retain their recorded limits. Public release and CLI/server compatibility remain separate work.
