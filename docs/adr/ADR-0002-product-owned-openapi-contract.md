# ADR-0002: Product-owned code-first OpenAPI contract

**Status:** Accepted — native OpenAPI 3.1.x, RFC 9457 HTTP errors, contract ownership, and the in-app workflow.  
**Date:** 17 September 2026.  
**Revised:** 23 September 2026. **Source:** [Canonical architecture guide](../ARCHITECTURE.md).  
**Related:** [Tenancy and authorization](ADR-0005-api-enforced-tenancy-and-authorization.md).

## Context

Inframeld is a centralized knowledge application for customer AI applications. Engineers use it to configure pipelines, maintain test cases, compare versions, and operate releases. A pipeline describes how to retrieve information from documents and use it to generate an answer. This approach is called **retrieval-augmented generation (RAG)**.

The API connects the backend to **Studio**, Inframeld's Next.js web console; official **software development kits (SDKs)**, which are client libraries for calling the API; and customer applications.

All these clients need to agree on the available operations, authentication requirements, request and response formats, and errors. Together, these rules form the **API contract**. If each client maintains its own version of those rules, they can drift apart: a client may send or expect something the backend no longer supports.

The MVP therefore needs one contract that can be reviewed in Git, served by the running API, and used to generate SDKs. Maintaining it must not require a second, handwritten description of the FastAPI application.

The API also needs to support two different activities: customer applications asking questions through an existing integration, and engineers changing the knowledge and pipeline versions behind that integration. **The customer application should not need a new integration for every compatible pipeline release.**

## Decision

**Inframeld owns one versioned OpenAPI contract for each public API version. The v1 contract is generated from the backend code, and all application clients use that contract.**

The same API supports the in-app build, evaluation, and release lifecycle. Studio presents that workflow; it does not implement a competing set of business rules or maintain competing business state.

### 1. Author the contract in FastAPI and generate the public artifact

**OpenAPI** is the machine-readable description of the HTTP API. **Code-first** means that developers define the API in backend code and generate the OpenAPI document from it, rather than authoring the document separately.

The source consists of FastAPI route declarations, Pydantic request and response models, shared response components, and explicit application metadata.

The responsibilities are distinct:

| Part | Responsibility |
| --- | --- |
| **FastAPI source** | The authoring authority: where developers define and change the API. |
| **Generated OpenAPI contract** | The client authority: what each operation means and how requests, responses, authentication, and errors are represented over HTTP. |
| **Committed JSON artifact** | The generated, reviewable contract included with a release. SDK generators and Studio consume it rather than defining parallel public models. |

The v1 generation and publication points are:

| Purpose | Command or location |
| --- | --- |
| Generate the runtime schema | `create_app().openapi()` |
| Store the generated artifact in Git | `contracts/openapi/v1/inframeld-v1.json` |
| Serve the schema from the running API | `/v1/openapi.json` |
| Regenerate the committed artifact | `pnpm openapi` |

The JSON artifact is generated output and must not be edited by hand. Generated clients are also downstream build artifacts and must not be edited by hand.

Public field names use **lower camel case**. Operations must have stable `operationId` values—the identifiers used to distinguish API operations—and schemas must use reusable components and explicitly describe error responses.

Inframeld's repository CI checks for **contract drift**: a mismatch between the schema generated by the FastAPI application and the committed artifact. A mismatch fails the check. This is a software-development quality check, not the workflow for releasing a customer's pipeline version.

#### Use native OpenAPI 3.1.x, not a relabeled 3.0 document

The contract uses **native OpenAPI 3.1.x as emitted by the selected FastAPI and Pydantic versions**. Pin the emitted schema dialect—the version and schema rules it uses—with those backend versions.

This replaces the earlier requirement to obtain OpenAPI 3.0.3 directly from `create_app().openapi()`. Changing only the document's version string does not convert nullable types, unions, or other schema keywords to another OpenAPI version.

The SDK Kit assessment recorded in this ADR identifies 3.0-specific handling in its existing planner that can lose constraints. Its ability to consume the required 3.1 contract has not been established. This is a compatibility issue to resolve, not a reason to change the contract's meaning.

**SDK Kit must consume the authoritative contract correctly. Do not weaken schemas or introduce a down-conversion framework to accommodate the old generator.**

#### Use bounded cursor pagination for lists

List endpoints use an optional opaque `cursor` and a `limit` between 1 and 100, defaulting to 25. They return `items` and a nullable `nextCursor`. Ordering must be deterministic and end in a unique tie-breaker. Every page request receives the owning feature's authorization and scope checks; a cursor conveys position, never authority.

The shared HTTP models enforce the request shape, validate cursor syntax, and describe the response in OpenAPI. The shared contract is implemented; the owning feature validates the cursor's contents against its sort, filters, and scope and implements the actual query when its list endpoint is built. See the [pagination guide](../development/pagination.md).

#### Use RFC 9457 for HTTP errors

The application uses **RFC 9457 Problem Details**, serialized as `application/problem+json`, for its HTTP error responses. The shared handlers, response models, diagnostic protections, and OpenAPI declarations are implemented. The [maintainer reference](../development/error-handling-reference.md#qualification-checklist) records behavioral coverage and developer-reported passing backend and integration tests as of 23 September 2026. This does not qualify future business endpoints.

The Inframeld profile includes `type`, `title`, `status`, and safe `detail`, with `code` and `requestId` extensions. Request-validation problems also contain bounded, sanitized `errors`. The HTTP status and body status agree. The `type` URI is the primary problem identifier; a documented short `code` identifies the same problem for application clients. Problem identities remain stable independently of Python exception class names. Human-readable descriptions are not machine identifiers. The RFC's optional `instance` member is omitted initially.

Domain and application exceptions remain ordinary Python exceptions with no HTTP status, response model, logging implementation, or request context dependency. HTTP adapters explicitly map supported application failures to public problems. A domain rejection is translated into a public application failure only where its meaning is established; unknown failures use the safe internal-error response. Application exception text is not automatically public.

The supporting logging policy preserves correlation while excluding submitted values, traceback locals, and unreviewed exception messages or notes from operational output. One unexpected failure has one diagnostic traceback; command and request summaries may still describe their separate outcomes. Cancellation propagates. An HTTP error response is not a retry authorization and does not replace ADR-0007's operation-specific recovery rules.

The [error-handling guide](../development/error-handling.md) defines the selected profile, starter error vocabulary, safe logging, and feature workflow. The [maintainer reference](../development/error-handling-reference.md) maps the implemented components and regression checks. Registering exception handlers and declaring OpenAPI responses are separate responsibilities, verified with behavioral fixtures without exposing artificial business endpoints.

Routes use `problem_responses(definition)` to declare applicable errors. A narrowly scoped hook wraps FastAPI's native OpenAPI method and corrects the media type only for these marked responses, preserving generated model components, caching, successful responses, and the native dialect. It removes its internal marker from the exported contract. This accommodates the installed FastAPI version's placement of additional response models under the route's default media type; reassess the hook when upgrading FastAPI. The existing exporter and drift check remain authoritative.

Reference: [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html).

### 2. Keep public documentation separate from protected product operations

Product routes live under `/v1`. **Every product operation requires authentication and authorization:** the backend must establish who is calling and whether that caller may perform the requested action.

The following application endpoints are unauthenticated:

| Endpoint           | Purpose                   |
| ------------------ | ------------------------- |
| `/v1/openapi.json` | The generated API schema. |
| `/docs`            | Swagger UI documentation. |
| `/redoc`           | ReDoc documentation.      |
| `/health`          | Health reporting.         |

These endpoints do not change product state or expose organization data, source content, or credentials. Public documentation must also exclude internal operational details. Swagger UI's **Try it out** feature still requires credentials when calling a protected operation.

The API serves different callers with different authority:

| Caller | What it does |
| --- | --- |
| **Customer AI application** | Queries a stable Deployment endpoint using its scoped integration credential. It supplies a stable affinity key for canaries and does not choose the current pipeline version itself. |
| **Engineer using Studio** | Calls authorized configuration, build, test-case, evaluation, and release operations through the same application API. |
| **Optional customer or future automation** | May call supported operations when explicitly granted the necessary build, evaluate, or deploy rights. This does not require a GitHub integration, external runner, or separate workflow engine. |

**Kratos authenticates engineers.** Customer applications authenticate with fixed, scoped, opaque integration credentials: secrets that identify the application without being treated as a description of its permissions.

The application's group permissions apply independently of which version receives its request. A query-only application cannot build or deploy. CI and service credentials remain available capabilities, but their availability does not mean external CI owns the product's release workflow.

### 3. Keep the customer endpoint stable while changing pipeline versions

A **PipelineVersion** is a frozen pipeline configuration with the complete bindings needed to use its prepared indexes. A **Deployment** is the stable serving target that decides which version answers a request. It is not a deployment of customer application code.

A Deployment owns changeable references, also called **pointers**, to its current version, optional candidate, and designated previous version. These references can change without changing the customer's query endpoint.

For example, versions **P12** and **P13** must both satisfy the Deployment's query contract before either can serve it. Changing a prompt, the **corpus**—the selected set of documents—or compatible model settings therefore need not change the customer's URL, credential, or request/response integration.

An incompatible API or schema change is outside this promise. Moving a pointer cannot make an incompatible version compatible.

For a **canary**, some traffic is routed to a candidate while the current version continues serving the rest. The customer application supplies a stable, opaque **affinity key** representing an end-user or session for routing purposes. Related requests can then stay in a consistent routing group, or **cohort**.

**An affinity key is routing input, not a verified end-user identity and not an additional permission.**

### 4. Record long-running work so it survives a browser session

A long-running command returns **HTTP `202 Accepted`**, a stable operation or job identity, and a `Location` header identifying where to follow the operation. Acceptance means the server has recorded the work; it does not mean the work has finished.

Commands carry **idempotency keys**, which identify the same requested action across retries. Release changes also carry an **expected deployment revision**, which identifies the state on which the engineer based the decision. These solve different problems: repeating one action versus competing changes to the same Deployment.

Once work is durably accepted, or **admitted**, closing Studio does not cancel it. Reopening a screen follows the existing job and reads authorized status and results instead of submitting chargeable work again.

Studio uses ordinary authenticated polling to read durable build and evaluation status. Polling uses bounded backoff—waiting longer between checks within defined limits—and shows both terminal outcomes and uncertain outcomes clearly. It requires neither an external runner to stay alive nor a completion callback.

Jobs have their own deadlines, resource budgets, and safe-retry rules, independent of browser lifetime. Polling intervals and numerical budgets remain implementation details to test. [ADR-0007](ADR-0007-durable-jobs-idempotency-and-recovery.md) defines recovery and the responses used for safe retries.

### 5. Build a pipeline version without changing live traffic

A **build** prepares a frozen RAG configuration for use. It does not compile customer application code or read a Git branch.

There are two publication modes: **Manual releases**, where the engineer explicitly builds and makes release decisions, and **Automatic updates**, where an authorized upload or apply action can request a build followed by separate conditional publication. Both use the same build behavior.

#### Step 1: Choose the exact inputs

The engineer edits a copy of the pipeline's settings: exact collection revisions, processing and embedding profiles, retrieval and reranking options, the prompt, and the generation connection and configuration.

A **collection revision** identifies an exact set of document versions. Processing and embedding profiles identify how those documents are prepared for search. Retrieval and reranking settings control how evidence is found and ordered.

Editing the form does not change the deployed version.

#### Step 2: Validate and freeze the build request

In Manual releases, the engineer clicks **Build candidate**. In Automatic updates, an authorized upload/apply operation invokes the same build with frozen inputs.

Inframeld validates the request and stores its inputs durably. It may reserve the display identity P13, but a pending build is not yet a PipelineVersion that can serve answers.

Retries refer to the same build. Later edits require a new request; they cannot modify the inputs of work already admitted.

#### Step 3: Reuse compatible results and create what is missing

The worker reuses ready, compatible processing results and **index materializations**: prepared search indexes for the selected documents and profiles. It creates only the missing work.

A prompt change or a change to **top-k**, the number of retrieval results requested, can reuse the whole index. A changed document needs new chunks and vectors. Changing the embedding profile may require embedding the entire selected corpus.

**The interface must not imply that every build is cheap or only processes a small change.**

#### Step 4: Verify readiness and publish immutable bindings

Inframeld verifies the required materializations, profiles, artifact references, and compatibility with the query contract. Only then does it publish the complete, immutable bindings for P13.

Until this succeeds, P13 cannot be treated as ready for evaluation or serving. Progress and failure belong to the build job. A version that was ready can still become unavailable later if a required dependency is lost.

Publishing these ready bindings is not the same as releasing the version to customers. **Building alone never changes Deployment pointers or sends customer traffic to the new version.** Attaching a built version to a Deployment's candidate slot is a separate release transition.

Evaluation also remains separate. It records the benchmark and evaluator identities used for a run without changing P13's serving configuration.

### 6. Support Automatic updates and Manual releases through the same API

The first-use path is:

```text
Set up an account and models -> Upload documents -> Ask a question with citations
```

A new user does not need to create collections, profiles, pipelines, or Deployments manually. The private defaults and publication behavior are defined in [ADR-0019](ADR-0019-default-onboarding-and-first-publication.md).

No benchmark or judge setup is required before the first answer.

#### Which publication mode is used

| Situation | Publication mode |
| --- | --- |
| **Default onboarding path** | Starts in **Automatic updates**. |
| **Explicitly created Deployment** | Starts in **Manual releases**, unless Automatic updates is selected at creation. |
| **Existing Deployment** | Can switch in either direction through authorized mode commands. |

In Automatic updates, an authorized source or configuration action can request the ordinary build and conditional publication of an eligible, complete result. Publication remains a separate operation; build completion alone does not change serving pointers.

In Manual releases, new source content does not change the serving selection. The engineer uses explicit build and release actions.

There is no separate **Prepare and ask** endpoint or one-time publication gate. Automatic updates is a reversible publication mode, not a special permission that disappears after the first answer.

#### What the contract must expose

The API exposes the publication mode, its **control revision**, the selected input binding, the current version, and any pending update with its status. The control revision identifies the mode/control state on which a change is based; the selected input binding identifies the inputs chosen for updates.

Creation accepts an explicit mode selection, with Manual releases as the ordinary default.

Mode commands require an idempotency key and an expected revision:

| Command | Required behavior |
| --- | --- |
| **Switch to Manual releases** | Preserve the current version and invalidate pending publication. |
| **Enable Automatic updates** | Validate the inputs displayed to the user and atomically admit a fresh apply request, or report that the Deployment is already up to date. |

Report conflicts clearly when an operation is incompatible with the mode, a candidate is active, the expected revision is stale, or a required version is not ready. Long-running work uses the existing `202` and job contract.

An automatic upload/apply operation requires the appropriate source or configuration rights **and** build/deploy grants for the specified targets. An ingestion-only call must not secretly publish a version.

Studio and its generated SDK use these same commands. MCP remains limited to queries and receipts: it observes normal serving changes but does not gain a mode-administration tool.

**Compare remains explicitly requested in both modes.** A comparison freezes the selected versions and never pauses or controls automatic publication.

The exact default selectors and endpoint shapes remain implementation details to settle in the native OpenAPI 3.1.x contract.

#### Store user-entered outbound credentials

The first-use path must let users save credentials for outbound calls, such as calls to a model provider. Mounted secret references alone do not satisfy this requirement.

[ADR-0020](ADR-0020-persistent-outbound-credentials.md) selects encrypted credential storage using PostgreSQL and PyNaCl. This is distinct from the integration credentials customer applications use to call Inframeld.

### 7. Provide the complete Manual releases workflow inside Inframeld

Engineers create pipelines, maintain test cases, evaluate versions, and make release decisions **inside Inframeld**.

When this product describes its workflow as CI/CD, it means the RAG lifecycle:

```text
Change -> Build -> Evaluate/compare -> Canary -> Promote or reject -> Roll back if needed
```

Git branches, pull requests, and external CI runners are neither prerequisites nor the owners of this workflow. An external platform is not needed to store the test cases or provide the release approval button.

#### Worked example: Support Assistant currently uses P12

**Support Assistant** is a customer application. It already calls the stable `support` Deployment endpoint, which is in Manual releases. Its fixed integration credential allows it to query **SupportKnowledge**.

The application has supplied a stable, opaque end-user/session affinity key since its initial integration. It does not include P12 as a version choice in each production request.

**Mira** is the engineer making the following changes in Studio.

##### Step 1: Change the configuration and build P13

Mira opens Support's pipeline page, copies P12's configuration, changes the prompt, and clicks **Build candidate**.

Inframeld freezes the request, tracks the durable build, and reuses the unchanged ready index. P13 becomes ready after validation. Support Assistant continues receiving P12 answers throughout.

##### Step 2: Choose a benchmark and request a comparison

On the pipeline's Tests page, Mira maintains 30 questions, expected source labels where useful, and explicit expected abstentions where appropriate. An expected abstention identifies a case in which the pipeline should decline to provide an answer.

A **benchmark revision** is a saved snapshot of the test cases used for a run. Mira selects P12, P13, one saved benchmark revision **B7**, and an evaluator configuration. She explicitly clicks **Compare versions**.

The interface shows the bound corpus and access scope. Starting the comparison authorizes the model work; merely editing a prompt or test case does not.

##### Step 3: Inspect answers, evidence, and regressions

Inframeld runs both exact versions against B7, applies retrieval and citation checks, and uses the selected **context-support judge** to assess whether answers are supported by their supplied evidence. It stores the per-case results and the comparison.

**OpenEvals is selected for evaluation, and Luna is the baseline judge to qualify.** Qualification means testing its suitability against the product's requirements; selection is not evidence that this work has already passed.

Mira sees gains and regressions, not only an average. For example, three questions might improve while two previously supported answers now contain unsupported additions. These numbers are illustrative, not an automatic acceptance rule.

She can inspect both answers, final evidence, judge explanations, and failures. If she decides not to release P13, she leaves it undeployed and can build P14. The history remains available.

##### Step 4: Attach P13 and start a canary

Mira decides the evidence warrants a trial. She attaches P13 with the initial **0% allocation**, then explicitly requests **10%**. Each command carries the deployment revision she observed.

Support Assistant keeps its endpoint and credential. Stable affinity cohorts now receive P12 or P13 automatically.

Ten percent refers to affinity identities, not exactly ten percent of requests. Inframeld does not run both versions in the background for every production request; there is no shadow execution.

##### Step 5: Review operating observations and answer feedback

Studio shows a small per-version summary of observed request counts, failures, and latency beside the offline comparison and release history. It also provides the answer-feedback panel defined in [ADR-0017](ADR-0017-answer-feedback.md).

**Online ratings remain distinct from offline evaluation.** These observations are not continuous production judging or a statistically conclusive test of answer quality. Limited traffic may support only a cautious human decision, not a claim that P13 is proven better for all users.

Mira can explicitly rerun the benchmark when needed.

##### Step 6: Reject the candidate before promotion

If P13 behaves badly, Mira aborts the attached candidate. New requests route to P12, and the earlier previous target remains unchanged.

P13 and its evaluation evidence remain in history, subject to retention and access policy. If P13 was never attached, rejecting it simply means not releasing it. A separate approval/rejection state machine is unnecessary.

##### Step 7: Promote P13, then roll back if necessary

On the successful branch, Mira explicitly promotes P13. P13 becomes current, and P12 becomes the designated previous target.

If a later defect appears, she can explicitly roll back to P12, provided its dependencies remain available. An active candidate must be explicitly aborted before rollback.

The customer application still uses the same endpoint. Rollback changes serving pointers, not source history or the application database schema.

##### Step 8: Reject stale decisions rather than overwriting another operator

If another operator changed the Deployment after Mira loaded it, her command's expected revision is stale and the command is rejected.

Studio reloads the state and asks Mira to make a fresh release decision. It must not automatically replace the expected revision and overwrite the other operator's change.

Requests already admitted to P12 or P13 may finish on that version, subject to current authorization. Promotion or abort changes subsequent routing.

#### Make canary prerequisites visible before rollout

A canary requires the consuming application's affinity contract. Under [ADR-0009](ADR-0009-sticky-logical-canary-deployments.md), requests missing required affinity are rejected once candidate traffic is enabled.

Document and test affinity during initial integration. Do not promise transparent canary activation for a client that omits it, introduce an arbitrary routing fallback, or treat the routing key as delegated user authority.

#### Source changes use the same lifecycle

For a source change, Mira first obtains a new logical revision through upload or the existing bounded, manually requested S3 sync. She builds against that exact revision, and the comparison labels the corpus change.

In Manual releases, the new content leaves serving selection unchanged. Automatic updates instead publishes eligible complete results under ADR-0019.

A startup and a large enterprise use the same pages and application operations. Different permissions and model gateway endpoints do not require separate release products.

#### Separate the engineer's decision from the work it authorizes

**Admission** is the point at which Inframeld durably accepts the requested work. After that point, the backend performs the required steps without depending on an open browser.

| Step | Explicit engineer decision in Manual releases | Work Inframeld performs after admission |
| --- | --- | --- |
| **Configure and build** | Select the inputs to freeze and request a build. | Reuse compatible artifacts; perform missing parsing, embedding, and indexing; validate; report progress; publish readiness only when complete. |
| **Maintain a benchmark** | Add, edit, or remove cases and select a saved revision. | Preserve snapshots used by past runs and enforce scope and validation. |
| **Compare** | Select the baseline, candidate, benchmark, and evaluator, then start the run. | Execute both versions, score results, retain evidence and history, aggregate comparable paired cases, and show regressions and failures. |
| **Canary** | Attach a ready version and explicitly select or change its percentage. | Check authorization, readiness, and concurrency; route stable cohorts; record per-version operating observations. |
| **Release** | Explicitly promote, abort, or roll back, acknowledging missing or regressed evidence where required. | Validate the transition, atomically update pointers and audit state, protect retained dependencies, and preserve the endpoint. |
| **Return after an interrupted session** | Reopen the same pipeline, job, or run; explicitly resume only recoverable failed work. | Continue already-admitted jobs within their budgets and display durable results without silently executing them again. |

Build and Compare are separate explicit actions in Manual releases. Automatic updates can request a build and conditional publication from an authorized source/configuration action, but does not make Compare automatic.

**A higher evaluation score never authorizes promotion.** Structural and security checks run automatically. Metric thresholds, approval hierarchies, and autonomous traffic ramps do not form a new v1 policy engine.

This separation lets the engineer inspect what changed, find failed cases, test without customer traffic, and deliberately change the behavior behind an existing integration. It avoids hidden judge spending and does not require a conditional workflow designer.

### 8. Generate official SDKs and keep client transports thin

The generation flow is:

```text
FastAPI source
    -> Native OpenAPI 3.1.x artifact
        -> External SDK Kit
            -> Official client SDKs
```

Studio uses the **official generated TypeScript SDK** as its primary client for Inframeld application endpoints. It must not maintain a second handwritten application client or public model layer.

#### SDK Kit is an external dependency, not backend work

SDK Kit lives outside this repository. Its extraction and suitability must be resolved before Studio implementation starts. **This blocks Studio, not backend implementation.** Backend use cases and contract tests can proceed without a generator trial.

Do not bypass the Studio blocker with a handwritten client. This ADR does not authorize SDK Kit extraction, comparative trials, replacement-generator selection, or generator development. The [code-based extraction assessment](../reviews/sdk-kit-feasibility.md) records the existing findings.

Python, Java, TypeScript, and Rust remain intended SDK targets. Each needs working contract and runtime tests before it can be described as supported. SDK generation and runtime qualification take place in the external project; the TypeScript client must be qualified before Studio starts.

Generating and releasing an SDK package is repository-development work. It is unrelated to promoting a customer's PipelineVersion.

#### Preserve the user's identity in browser and server requests

The browser-safe TypeScript transport uses the same-origin Kratos session and the required **CSRF protection**, meaning protection against cross-site request forgery. It never embeds integration credentials, model-provider credentials, or infrastructure credentials.

Next.js server requests forward only the current verified user's allowed session context, with request-local configuration. They must not use a global administrator key to act on the user's behalf.

Account operations owned by Kratos use its maintained client and account-flow contract. Server rendering, framework caching, and redirects are legitimate transport integration work; they must not become a parallel application API.

A browser-wide SDK singleton—a shared client instance—must not retain a previous user's session or response data.

#### MCP invokes the same application behavior

**MCP**, the Model Context Protocol, is a second transport over the existing application use cases. It is not an OpenAPI-generated RAG engine.

Its tool **DTOs**, or data transfer objects, explicitly map to the same application commands and queries, permission checks, and receipt outcomes. Its initial scope remains query and receipt operations, not release or publication-mode administration.

The detailed contracts are defined in [ADR-0018: first-party MCP](ADR-0018-first-party-mcp-adapter.md) and [ADR-0017: answer feedback](ADR-0017-answer-feedback.md).

### 9. Provide the required screens without adding a workflow platform

The minimum product views are:

| View | Information and actions it provides |
| --- | --- |
| **Pipeline configuration and versions** | Pipeline settings, versions, and build progress or failure. |
| **Pipeline tests** | Test cases and the saved benchmark revision. |
| **Run history** | Evaluation runs associated with each pipeline version. |
| **Comparison and case detail** | Paired results, individual case details, and case history. |
| **Deployment** | Current, candidate, and previous targets; cohort allocation; explicit release-transition actions. |
| **Answer feedback** | The feedback panel from ADR-0017, kept distinct from offline evaluation. |

These screens read projections—data shaped for a particular view—from existing domain and application owners in PostgreSQL. They do not require separate services or new owners of business state.

[ADR-0008](ADR-0008-deterministic-evaluation-and-release-decisions.md) owns evaluation evidence and comparison rules. [ADR-0009](ADR-0009-sticky-logical-canary-deployments.md) owns release invariants: the rules every release transition must preserve.

The required actions and supporting views are settled. Layout details, polling intervals, and numerical budgets remain implementation choices to test.

#### Deliberately deferred capabilities

The current workflow does not require Inframeld to hand off work to an external workflow system. V1 therefore defers:

- **External workflow integrations:** webhook delivery, detached external notifications, GitHub and pull-request integration, runner coordination, and repository events.
- **General orchestration infrastructure:** a general-purpose scheduling or workflow platform.
- **Additional release automation and governance:** evaluation on every save or build, automatic promotion or rollback, traffic-ramp policies, continuous production judging, and multi-step approval governance.

Keep the existing hook/webhook interface boundary without shipping a delivery service.

These deferrals do not remove authorized in-app release decisions or durable history. The Automatic updates mode described above remains in scope as an authorized build-and-conditional-publication path; it is not evaluation-driven promotion or a general release-policy engine.

### 10. Verify the contract and the complete product workflow

The checks below are required qualification work. **This ADR records what must be demonstrated, not tests that have already passed.**

#### Backend contract tests

Test the native OpenAPI 3.1.x representation of nullable and union types, numeric constraints, file uploads, typed errors, first-answer versus retry/replay variants, and asynchronous `202` jobs.

These tests protect the backend contract independently of SDK Kit. They do not wait for Studio or external SDK qualification. Repository CI must also detect drift between the running application's generated schema and the committed artifact.

#### End-to-end product qualification

Before release, demonstrate the Support Assistant example entirely inside Inframeld while a separate customer client continues using its original endpoint.

| Area | What to demonstrate |
| --- | --- |
| **Browser recovery** | Closing and reopening Studio follows existing work without duplicating it. |
| **Immutable inputs** | Later edits do not change the inputs of an admitted build or run. |
| **Evaluation history** | Changed benchmark and evaluator identities are labeled, and partial judge failure is handled. |
| **Permissions** | Permission changes are respected, and a query-only integration cannot invoke release commands. |
| **Canary routing** | Affinity cohorts remain stable under the required integration contract. |
| **Release transitions** | Rejection before promotion and rollback after promotion behave correctly; unavailable targets are handled. |
| **Concurrent operators** | Two operators racing cannot silently overwrite one another's release decisions. |
| **Evaluation versus release authority** | Passing a metric never triggers a Deployment pointer change. |

## Consequences

### Positive

- **API changes are reviewable.** The generated contract shows the public effect of a backend change.
- **Contract drift fails CI.** The committed artifact cannot silently diverge from the FastAPI application.
- **SDK generation has a stable input.** Generators consume a defined public artifact rather than reconstructing the API independently.
- **Studio and external clients share one public model.** They use the same contract instead of maintaining separate request, response, error, and authentication definitions.

### Negative

- **API changes require regeneration and review.** Route and schema changes must include the corresponding contract update.
- **Reusable schemas require consistent implementation.** FastAPI declarations must express shared components consistently.
- **Generated JSON is a deliberate part of API changes in Git.** The artifact adds a repository change that developers must generate and review.
- **Public documentation exposes the API surface.** Documentation endpoints must never include secrets, tenant data, or internal operational details.

## Alternatives considered

### Hand-maintain an OpenAPI document

**Not selected.** A handwritten document provides editorial control, but creates a second authoring source beside the FastAPI implementation. The selected approach generates the document from the backend instead.

### Generate clients directly from Python models

**Not selected.** This keeps the public contract hidden inside Python implementation details and does not provide a stable artifact for non-Python consumers.

### Let each client define its own transport models

**Not selected.** Separate client-owned request and response models create contract drift. This is incompatible with the MVP's single, code-first OpenAPI contract.
